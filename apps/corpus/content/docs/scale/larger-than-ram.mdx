Writing a corpus of ten million vertices is a job that declares how much memory it may use, and the
operators inside honour it: they reserve before they allocate, and they spill when the answer is no.

```
fossil run mapping.fossil --dest file:///out --memory-gib 4
```

The number reaches both engines through one path. There is no environment variable — a number that
decides whether a job survives is declared by the command that launched it, not by the shell that
happened to be open.

## A budget is a protocol

*Try, and die if it does not fit* is not a mode any serious engine offers. The three references
implement the same shape: **DataFusion** (`MemoryPool`, greedy and fair-spill variants, a disk
manager), **DuckDB** (`memory_limit` plus `temp_directory`, with out-of-core hash join and sort) and
**Velox** (a memory pool with arbitration and spilling). The form is always: *the operator reserves
before it allocates, and knows what to do when told no.*

Two consequences follow, and both were found by measurement rather than by reading:

**A budget without somewhere to spill is an error where it could have been slowness.** The limit and
the temp directory are set together, or the first one turns a slow job into a failed one.

**A budget only means something if the operators can honour it.** The build side of a hash join
declares that it cannot spill; told it may not allocate, it has nothing to give back and it dies. A
sort-merge join spills. So the bounded configuration turns the hash-join preference **off** —
otherwise the budget is a promise the plan cannot keep.

That was not a hypothesis. The pool names its consumers when it refuses:

```
HashJoinInput[8]#125(can spill: false) consumed 387.7 MB, peak 387.7 MB,
HashJoinInput[9]#126(can spill: false) consumed 291.9 MB, peak 291.9 MB,
…five of them, on a ten-core machine: one reservation per partition
```

## What it costs and what it buys

At ten million vertices:

| | no ceiling | 4 GiB + sort-merge |
| --- | --- | --- |
| RSS leaving the graph build | 15.68 GiB | **5.56 GiB** |
| RSS entering the layout pass | 16.51 GiB | **6.82 GiB** |
| process peak | ~21 GiB | **9.87 GiB** |
| wall clock | 256.3 s | 290.9 s |

**Seventeen gigabytes for 13% of the wall clock, and the corpus comes out byte-identical** — 87
files, every md5 equal. A budget is not a degraded mode; it is the same artifact, produced within a
declared envelope.

## The floor is set by the machine, and that is part of the contract

A budget that is too small does not spill. It dies.

Each sort partition reserves a spill reservation up front and declares it non-spillable, so the
minimum viable pool grows with the number of partitions, which grows with the core count. On ten
cores: **384 MiB dies** with five merge operators holding 10 MB each; **480 MiB runs and spills**;
and it keeps spilling at 2 GiB.

So the floor is expressed **per core**, not as a round number. A 100 MB budget is not viable at any
corpus size, on any machine, and that is a property of the protocol rather than a bug to be fixed.

## Where the memory actually went

The number that opened this investigation — writing ten million vertices peaked at 17.0 GiB to
produce 713 MB, **23× the output, resident** — was discovered by accident while measuring something
else. Nobody was watching it.

Four hypotheses were proposed with confidence and all four were killed by measurement:

| candidate | why it looked right | what killed it |
| --- | --- | --- |
| per-community hash maps | a vector of maps, one per community, k in the millions | the whole core is 53 B/edge |
| the layout core | it had been predicted explicitly | 3.94 GiB in isolation, of 17 |
| the database during layout | no limit by default | capped at 2 GB: same total, **0 B spilled** |
| the data generator | it had a 12 GB heap | the writer alone reaches the same peak |

The instrumentation said something none of them predicted: **RSS was already 14.61 GiB before the
layout pass executed its first statement**, and the entire pass added 0.13 GiB net. Reading all 71M
edges into a vector measured **−3.12 GiB** — more was released than reserved.

And the graph itself is not the cost. Counted in Arrow, everything the boundary retains is
**1.64 GiB with 15.68 GiB resident**: the graph is a tenth of what the process holds when it hands
it to the writer. Releasing the execution context before encoding frees **0.00 GiB** — the tables
are the same Arrow buffers, not a second copy — and the same phase measured **+11.35 GiB** on one
run and **+7.67 GiB** on the next. Live data does not vary by 3.7 GiB.

It was operator memory that nobody had bounded.

<Callout type="warn" title="What is proved, and what is only bounded">
The budget is exercised by `crates/fossil-df/tests/spill.rs` — two passes over the same corpus,
which without a budget never touches disk and with one opens a spill directory and says so through
the log. That log line is the only evidence that survives the run: the files are deleted, the
disk-usage counter returns to zero, and the plan metrics do not leave the execution call. Both trees
come out **byte-identical**.

What that test does **not** prove: that ten million vertices fit in 4 GiB — it does not measure RSS;
and that a plan free to choose a hash join survives — it does not, which is why the bounded
configuration turns the preference off, and the test therefore only ever sees the plan that leaves.

**And the honest gap:** the ~14 GiB is *localised* — before the layout, in the write path — and not
*attributed*. The budget bounds it without explaining it, and a bound nobody can explain is a bound
that moves when the plan does. **What would attribute it is a per-operator accounting of the pool at
the moment RSS peaks**, against the phase table `FOSSIL_MEM_PROBE` already prints; short of that, the
spill test is the only thing standing between here and the same number returning unnoticed.
</Callout>

## What the corpus contributes, and what it does not

The corpus is written once and read many times, so the read side never faces this: a reader holds a
window and a footer, and both are flat in N by construction. The scale question lives entirely on
the write side.

And it lives there in one place the format does not help with. The corpus's own ordering bounds the
*edges* the community pass reads — the pass walks them as the CSR they already are, and that term
went from +2.09 GiB to +0.08 GiB ([Streaming](/docs/scale/streaming)) — but it does not bound the
**per-vertex state**, which is O(n) and resident, about 200 MB at ten million. That term is linear
in the vertex count and no convention on this site makes it otherwise.

Which is why *larger than RAM* is the claim on this site with the least evidence behind it. The
largest corpus measured is **ten million vertices**, and under a 4 GiB budget it peaks at 9.87 GiB —
under a machine, not under the budget, and still growing with N. The metric that decides the claim
is not the wall clock but the **peak heap**, and what would settle it is that curve staying flat
across a size the machine cannot hold.

**That fossil could not write a larger-than-RAM corpus would be a finding as important as any
reading result**, and stating it that way is the point of writing it down here.
