A corpus is written by a pipeline in which **no stage holds a whole value**. A batch arrives, is
transformed, is handed on and is dropped. Peak memory follows the working set — a batch, a window,
the O(n) state an algorithm genuinely needs — rather than the size of the corpus.

That is what makes a [memory budget](/docs/scale/larger-than-ram) into larger-than-RAM instead of a
lower ceiling. A budget bounds the operators inside the pool; everything outside the pool is bounded
by being a stream.

## The engine streams; the seams around it are the question

DataFusion hands `RecordBatch`es out lazily and its operators reserve, spill and release against a
pool. The unbounded parts of a write path are not the engine — they are the places where a stage
boundary is a whole value.

Three such terms were named here, all on the same reasoning: a structure that holds a value where it
could hold a stream. **They ended three different ways**, and that is the most useful thing on this
page.

| the seam | how it ended |
| --- | --- |
| the materialised graph holds every batch | **real** — 1.64 GiB at ten million, linear in N |
| the encoder builds every file before writing one | **refuted by measurement** — 0.02 GB, inside the noise |
| the layout reads the whole edge list | **removed** — −1.71 GiB of process peak |

### The one that was real

Every vertex batch, plus both orientations of every edge table, resident together before the writer
is called. Counted in Arrow it is 0.16 GiB at one million and **1.64 GiB at ten** — 10.3× for 10×,
exactly linear in N, and the cleanest evidence that the term is a term.

It is also the *smallest* of the three at the moment it exists, which is what made it misleading:
the process holds 15.68 GiB when the graph itself holds 1.64. That residency was operator memory,
and bounding it is the [budget's](/docs/scale/larger-than-ram) job.

### The one that was refuted

The encoder built the whole corpus into a list of files before the sink wrote a byte. It now builds
each file, hands it over and drops it. **Peak RSS at ten million moved from 10.60 GB to 10.58 GB.**
Two identical runs of the same path differ by more than that, so the number is not small — it is
absent.

The whole output is 713 MB across six files, so holding six of them was never what the +0.58 GiB
billed to that phase meant; that was the encoder's own working memory. The change stayed anyway,
and the reason has to be stated separately from the number, because mixing them is how a refuted
hypothesis quietly survives: holding N files in order to write them one at a time has **no reader on
that path**. It is indefensible per file. It is simply not worth any megabytes at this size, and
saying so is not the same as saying it saved some.

### The one that was removed

The layout read every edge into a `Vec<(u32, u32)>` — 568 MB at ten million — plus a
degree-counting pre-pass and an 80 MB cloned cursor scattering random writes over the 568.

**None of the three was ever asked for by the algorithm.** The community pass walks
`for v in 0..n { neighbours(v) }`, a sequential CSR scan; the only random access is per-vertex state,
which is O(n) and about 200 MB at ten million. And the file it reads from
[has been sorted since it was written](/docs/conventions/adjacency).

All three existed because of a type. The entry point took an unordered bag of pairs, so the ordering
the file already had could not be passed through it. **The signature said it did not know.**

| at ten million, under a 4 GiB budget | before | reading the CSR |
| --- | --- | --- |
| the community pass | +2.09 GiB · 135.0 s | **+0.08 GiB** · 168.0 s |
| process peak | 10.10 GiB | **8.39 GiB** |

The corpus comes out byte-identical and the three parity tests pass without being touched.

<Callout type="warn" title="The attempt that failed first, and what it actually proved">
The same change was implemented in full a day earlier — a weighted-CSR constructor merging two
streams, and the layout reading two statements instead of building the bag. It compiled. The three
parity tests passed without being touched, which was the declared definition of done.

And the peak went **up**: 17.0 GiB to 24.4 GiB.

The driver's ordinary query API does not stream — it materialises the entire result. Two statements
open at once are two full result sets resident, plus the CSR being built, where before there had
been one `Vec`. One copy was traded for two.

What it proved is not that the reasoning was wrong; the redone change demonstrates all of it. **It
proved the definition of done was wrong.** Three parity tests in green did not see a seven-gigabyte
regression, because they checked that the result was correct when the *cost was the entire
objective*. The second attempt carried the memory probe in its acceptance criteria, and that is the
only reason it is a result rather than a second revert.

The honest debit: the community pass went from 135 s to 168 s on a loaded machine, where the same
previous binary measured 151 s on another run. Walking two arrays per vertex instead of one has a
locality cost that is structural, and it is owed a measurement on a quiet machine before anyone
calls it free.
</Callout>

## What the corpus contributes

The format is not neutral about any of this. **The corpus is already in the order these systems work
to construct.** X-Stream and GraphChi are built on the observation that streaming edges sequentially
while keeping only per-vertex state beats random access over a resident adjacency, because sequential
bandwidth is orders of magnitude higher. Their difficulty is producing that order; here it is a
convention, verified as zero out-of-order rows across 71,024,690 edges.

And the mechanism that keeps it is a type rather than a comment: a constructor that takes offsets
and targets *cannot* need a counting pass, because its signature already asserts the order. One that
takes a bag of pairs has to rebuild it, because the bag asserts nothing.
