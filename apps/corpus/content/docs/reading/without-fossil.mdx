Reading a corpus needs a Parquet reader and this page. No fossil crate, no `@fossil-lang/*` package,
no wasm module, no service.

This is not an aspiration about the format — it is how it is already read. `kanzo-ui` reads
fossil-written corpora with no `@fossil-lang/*` dependency at all, reimplementing the read shape
against DuckDB and Mosaic, and three languages that do not know fossil exists read the same tree.
The examples below use DuckDB because it is the shortest way to write them down; nothing in them is
DuckDB-specific except the syntax.

## 1. Start at the index

A reader over HTTP cannot list a directory, so nothing is discovered by listing. One file is named
in advance:

```
graph.graph.yml
```

It names every per-type manifest. Each vertex manifest carries a `type`, a `vertex_count`, a
`prefix` and a `chunk_size`; each edge manifest carries `src_type`, `edge_type`, `dst_type`, an
`edge_count`, a `prefix`, and the `src_chunk_size` and `dst_chunk_size` that tie each orientation's
tiles to its own endpoint type's.

The manifests are small and flat. Reading them with a line scan rather than a YAML library is a
legitimate choice and the checker makes it — `apps/corpus/guards/manifest.mjs` is that scan, and it
refuses what it cannot parse rather than guessing at it.

## 2. Everything else is arithmetic

From `chunk_size` and the declared count:

```
shift       = log2(chunk_size)          # 12
tile(id)    = id >> shift
tile i       spans dense ids [i·chunk_size, (i+1)·chunk_size)
tiles        = ceil(vertex_count / chunk_size)
tail rows    = vertex_count − (tiles − 1)·chunk_size
```

No index file, no manifest of tiles, nothing to fetch. A reader knows where any id lives, and how
many there are of them, from two numbers in a document it fetched anyway — which is what lets it
compute every URL before it emits the first request. `chunk_size` is a power of two so that the
address is a shift; it is 4,096 in a corpus fossil writes, and a reader takes it from the manifest
rather than from that sentence.

**The count is not decoration, and it is the only field a truncated corpus fails.** Tiles are
addressed and never listed, so a tree holding `chunk0…chunk16` is indistinguishable from a corpus
that has seventeen tiles: a hole in the middle breaks the address of everything after it and is
caught, and **a missing tail breaks nothing**. Without the field the answer was to probe — `HEAD`
`chunk{k}.parquet`, doubling `k` until one misses, then bisecting — which is a dozen requests that
still cannot tell a short corpus from a complete one.

The count is declared rather than optional for the same reason. A count a reader may skip is a count
a reader may not depend on, and a reader that may not depend on it is exactly the one that cannot
detect the failure the field exists for. The border worth writing a test at is `vertex_count = 4096`
against `chunk_size = 4096`: that is **one** tile, and the off-by-one addresses a `chunk1.parquet`
that is not there.

## 3. Ask the footer which tiles intersect the window

Arithmetic gives the tiles that *exist*. The footer gives the ones that *intersect* — the row-group
statistics on `x` and `y` are bounding boxes, they arrive with the footer, and selecting on them is
the whole of viewport culling.

**Which file holds a tile is the second question, and there are two answers.** A corpus fossil
writes puts one tile in one file, `chunk{k}.parquet`, with the address in the name; the other
container is one file whose row groups are the tiles, addressed by row-group ordinal. The examples
here are the first, which is what the corpus under `apps/corpus/conformance/` is; against the second
one, drop the glob and the `file_name` column and read `row_group_id` as the tile number.

```sql
SELECT file_name, row_group_id,
       min(CASE WHEN path_in_schema = 'x' THEN coalesce(stats_min_value, stats_min)::DOUBLE END) AS x0,
       max(CASE WHEN path_in_schema = 'x' THEN coalesce(stats_max_value, stats_max)::DOUBLE END) AS x1,
       min(CASE WHEN path_in_schema = 'y' THEN coalesce(stats_min_value, stats_min)::DOUBLE END) AS y0,
       max(CASE WHEN path_in_schema = 'y' THEN coalesce(stats_max_value, stats_max)::DOUBLE END) AS y1
  FROM parquet_metadata('vertex/Person/chunk*.parquet')
 WHERE path_in_schema IN ('x', 'y')
 GROUP BY file_name, row_group_id;
```

Keep the tiles whose box intersects the window. Note `min_value`/`max_value` before `min`/`max` —
the deprecated pair is signed-comparison only and is empty for an unsigned column, which is every
addressing column there is.

The two containers are not equally cheap, and the arithmetic above is the reason: inside one file,
contiguous tiles are a **single** byte range, and one footer covers all of them. Measured on five
million vertices in 1,221 tiles, that is 5.6 requests per window against 22.3, for the same bytes —
[Addressing](/docs/conventions/addressing) has the table. A glob over `chunk*.parquet` is also a
listing, which is the thing an HTTP reader cannot do; over an origin, compose the names from the
count and the shift instead.

<Callout type="warn" title="Select the tiles; do not write the window as a predicate">
Handing the ranges to the query planner as a `WHERE` is the intuitive move and it is measured to be
slower than not pruning at all: a range join against 179 runs costs 237 ms and 179
`BETWEEN … OR …` predicates cost 189 ms wall and 2.3 s of CPU, against 5 ms for a plain join,
because the engine evaluates ranges per row instead of skipping row groups.

**Pruning is not a predicate. It is a choice of what to read.**
</Callout>

## 4. Read the vertices

```sql
-- tile 10 is the dense_id range [40960, 45056), and it is a file
SELECT dense_id, x, y, cluster_id
  FROM read_parquet('vertex/Person/chunk10.parquet');
```

Or, over HTTP, fetch the byte ranges the footer named and decode them directly. `x` and `y` come out
as separate arrays, which is what Parquet stores and what leaves the choice to the reader — a
consumer that wants them apart gets them apart, and one that wants a single interleaved
`[x0, y0, x1, y1, …]` buffer pays one pass. **The layout does not remove that pass, it moves it**;
see [Payload](/docs/conventions/payload).

## 5. Read the edges of those tiles

An edge lives in its **source's** tile, so the tiles a window already fetched are an exact superset
of the edges it can draw. No second round of addressing:

```sql
SELECT src_dense, dst_dense
  FROM read_parquet('edge/Person_knows_Person/by_source/tile10.parquet');
```

`by_source` is ordered by `src_dense` and `by_target` by `dst_dense` — CSR and CSC — and **both are
tiled the same way**, each by the endpoint it is ordered by. So a hop out of one vertex is two files
whose names are arithmetic, and nothing scans:

```sql
-- everything vertex 41000 touches: 41000 >> 12 = 10, in both directions
SELECT dst_dense AS far FROM read_parquet('edge/Person_knows_Person/by_source/tile10.parquet')
 WHERE src_dense = 41000
UNION ALL
SELECT src_dense FROM read_parquet('edge/Person_knows_Person/by_target/tile10.parquet')
 WHERE dst_dense = 41000;
```

Which prefix is which direction is in the edge type's manifest, as an `adj_lists` entry per
orientation: `aligned_by` names the column that addresses it, `prefix` names the directory. Do not
follow only `by_source` — in a knowledge graph "the papers by this author" is an in-edge, and half
the directions is a wrong answer rather than a partial one. A `WITH RECURSIVE` over the whole edge
relation is the thing this replaces: measured on 6.9M edges, one hop from one seed had not returned
after 45 seconds.

## 6. Name things by the subject IRI

```sql
SELECT v.subject
  FROM read_parquet('vertex/Person/chunk10.parquet') v
 WHERE v.dense_id = 41000;
```

`dense_id` is an address and changes when the layout is redone. Anything stored outside the corpus —
a selection, a bookmark, a foreign key — keys on `subject`.

## Prove your own writer

If you produce corpora rather than only consume them, the guards are the contract in executable
form:

```bash
node apps/corpus/guards/check.mjs /path/to/your/corpus
```

It needs `node` and the `duckdb` binary, and nothing else — no pnpm install, no Rust toolchain, no
part of this repository beyond the `guards/` directory, which is written to be copied. `--explain`
prints what each guard proves and, more usefully, what it cannot.

[The guards](/docs/guards) has the full list and the honest limits.

## Prove your own reader

The composition on this page — prefix, shift, orientation, and which of them a window may use — is
also published as code, and the two are checked against one table of addresses rather than against
each other's prose. `apps/corpus/conformance/` holds it: a corpus small enough to read by hand, four
manifest sets carrying the cases a whole corpus cannot, and `expected.json` naming every address
that must compose and every one that must be refused.

```bash
node apps/corpus/conformance/verify.mjs
```

That harness runs `reader.mjs`, which has no npm, no build and no fossil in it — the position this
page is written for. `resolveCorpus` in `@fossil-lang/graph` is the same table executed by the
published module, for a reader that would rather take the dependency than copy the arithmetic.
Neither is the authority; `expected.json` is.

`expected.json` is not the whole authority either, because nothing in it was written by the writer.
`writer.mjs` is the harness that closes that: it runs `fossil run` and checks the same reader against
the bytes, which is the only check here that would notice fossil and this page disagreeing.
