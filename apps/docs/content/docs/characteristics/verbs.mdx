## Six, and why six

`fossil-graph` defines the surface; MCP, HTTP, the CLI and the in-process TS package are bindings
over it. **The surface is six verbs, and it closed on 2026-08-05:**

| verb | what it answers |
| --- | --- |
| `read` | rows of one vertex type, filtered, ordered and capped |
| `expand{into\|all}` | the neighbourhood of a *set* of vertices, one hop |
| `path` | a route between two vertices |
| `aggregate` | a grouped, bounded summary — over values or over ranges |
| `schema` | what types, fields and relations exist, with field stats on request |
| `execute_sql` | the escape hatch, which a binding may hide behind a permission |

Six is not a tidiness target. It follows from a decision about what the surface is *for*: the
algebra answers questions and **does not draw**. Drawing is addressing — the camera works out which
level and which tiles it needs and asks for bytes, with no bbox in flight, no SQL and no database on
that path. Level-of-detail is not a filter but a different relation: a level-3 tile holds super-nodes
that do not exist at level 0. A `where` selects rows from a table; zoom changes the table.

Once that is settled, every verb whose job was to make a picture stops having a job.

<Callout title="The rule that keeps it at six">
A new verb enters only if it serves a case the single path demonstrably cannot, and that
demonstration is a measurement. Not an argument.
</Callout>

## `read`'s `where` is SQL, and carries `execute_sql`'s authority

This is the one thing on the page a binding can get wrong quietly. `read { vertex_type, where?,
order_by?, descending, limit }` takes `where` as a **raw SQL fragment**, evaluated by the same engine
`execute_sql` reaches. It is not a parsed predicate language.

So the permission travels with it: **a binding that gates `execute_sql` behind a permission must gate
`read`'s `where` with the same one.** Gating the escape hatch and leaving `where` open is not a
narrower surface, it is the same surface with a second door. That rule is written on the type in
`crates/fossil-graph/src/operations/discovery.rs`, not in a design note, so a binding author reads it
where they type it.

## What the seventeen became

Four commits on 2026-08-05, in order, and `exec.rs` went from **1,874 lines to 1,546**. This section
is history now, not a plan — read it for what each collapse cost, because the reasoning is what would
decide a seventh verb if there ever is one.

### Four introspection verbs to one — `bb775b3`

`list_vertex_types`, `list_edge_types`, `describe_field`, `describe_vertex_type` → **`schema`**.

All four are manifest reads. They differed in **what they cost**, not in what they were: two
listings, one batched query per type, one that sampled a column. `schema { vertex_type?, field? }`
answers all four, and the cost distinction becomes two optional fields — a bare call is the cheap
default, and that it stays cheap is asserted rather than described: its recorded SQL contains no
`DISTINCT`. Naming a field is what buys the samples and what costs the second query.

### Binning is grouping — `22006d6`

`histogram` → a parameter of **`aggregate`**.

A histogram was the same `GROUP BY` with the key computed from a range instead of read from a column.
`aggregate { bins }` is that difference. The binned arm is *more* general than the verb it replaced,
because it takes any aggregation rather than only a count — and it stays dense, one row per bin with
`0.0` where nothing landed, because a grouping over ranges knows how many there are and a gap is
information.

### `read`, `expand`, `path` — `d14e0c6`

| before | after |
| --- | --- |
| `get_vertex` | `read(where:)` — one vertex is a predicate, not a verb |
| `top_k` | `read(order_by:, descending:, limit:)` |
| `find_neighbors` | `expand`, whose `from` is now a **set** |
| `find_path` | `path`, unchanged in shape |

`get_vertex` and `top_k` were not different questions from each other: both were rows of one vertex
type, one under a predicate and one under an order and a limit. `expand` taking a set is not
cosmetic — an induced subgraph is a question about a set, and a single IRI could not ask it.

### `viewport` and `materialize_graph` leave — `c6c87fa`

Deleted, not absorbed, because neither had anywhere to go. `viewport` was the only verb that drew:
bbox in, vertices and edges out, with a detail mode and an aggregate mode selected by an `if` inside
the verb — relation selection wearing a predicate's clothes. `materialize_graph` was the same claim
without the bbox: the whole graph as renderable rows.

### And four that were deleted rather than written

`search_by_label`, `summarize_cluster`, `answer_with_communities` and `set_selection` were declared,
carried params and result types and wire schemas, and were never implemented — dispatch fell through
to a `NotImplemented` arm. Deleting them took `GraphError::NotImplemented` with them, so **the
`match` is now exhaustive and a verb can no longer be declared without being wired.** The compiler
says what a stub used to say at runtime.

<Callout type="warn" title="What the snapshot proves, and what nothing proves">
`backedBy` on this page is the operation envelope snapshot — the wire contract every binding
consumes. It enumerates exactly these six, so a seventh cannot land without it changing, and it is
why the count above is a fact rather than a recollection.

What it does **not** know is that six is the right number. Nothing on disk asserts a target count;
the closed set is a discipline, and [tooling for machines](/docs/design/tooling-for-machines) is
where the discipline is argued.
</Callout>

## The gap the closure opened, and it is real

<Callout type="warn" title="Nothing answers a camera today">
`viewport` was deleted **before its replacement existed**, and that is a decision rather than an
oversight — `c6c87fa` records the breakage as *expected and accepted*. There is still no tile store,
no tile index and no tile emission anywhere in `crates/`, and none of the six verbs answers a camera.

So the two registers genuinely diverge here. **Decided:** the camera is addressed, not queried, and a
downstream reader consumes the verb package while the camera does not — both argued in
[the corpus](/docs/design/corpus). **Undone:** the tiles both of those address. There is a reader
waiting on them, and bringing it across is the next piece of work rather than a regression to be
fixed here.
</Callout>

## The trap carried on `expand{into}`

`expand{into}` shipped, and the reasoning that first put it on the list does not hold on our engine.
It should be read with that attached — which is why the trap is now carried on `ExpandMode::Into`
itself rather than in a note somewhere.

The justification came from Kùzu (`SEMI_MASKER`) and Neo4j, which push a mask of candidate
destinations *into* the scan so the expansion never materialises neighbours it will discard. On
DuckDB that class of pruning is measured and unavailable. A window of 20,000 vertices at five million
is 179 contiguous runs of `dense_id` covering 20,007 ids — a 268× superset of the visible edges with
zero over-read, and **no way of asking for it in SQL wins**:

| how the prune was expressed | time |
| --- | --- |
| no pruning at all (plain join) | 5 ms |
| range join against the runs | 237 ms |
| 179 `BETWEEN … OR …` predicates | 189 ms, 2.3 s CPU |

Both attempts are slower than not pruning, because the engine evaluates the ranges per row instead of
skipping row groups.

**The verb is right as a shape. Its performance motivation is not available to us.** That is also why
`read(where: …)` cannot be how a window is asked for, now that `viewport` has gone: it would be a
return to the 237 ms. Pruning cannot be a predicate, only a choice of what to read.
