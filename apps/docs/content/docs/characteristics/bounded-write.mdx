## The destination

`fossil run` accepts a memory budget and stays inside it, at any corpus size. Exceeding the machine
means spilling to disk and taking longer, never dying. That is the ring-2 promise and it can only
live in ring 2, because ring 2 is the only one with a disk to spill to — a browser has roughly 4 GB
of address space and nowhere to put the overflow.

What is not reached is the *any N*. Everything below is inside that gap.

## What is true today, measured 2026-08-05

Four things exist and are measured. Take them in order, because each one made the next one
answerable.

### The probe reports RSS per phase

`FOSSIL_MEM_PROBE=1` on a `fossil run` prints resident set size at each phase boundary of the write
path. This one is an environment variable and staying one — it is diagnostic instrumentation, not a
parameter of the job, and nothing about a run's result depends on it.

It is what turned "seventeen gigabytes go somewhere" into a table, and it is why four plausible
hypotheses about where the memory went could each be killed by a number rather than an argument.

The finding that mattered: **RSS was already 14.61 GiB when `enrich_layout` executed its first
statement**, and the entire layout pass added 0.13 GiB net. The memory was spent before the pass
everyone suspected had even started.

### One budget, declared on the command, governing both engines

`fossil run --memory-gib <GIB>` — fractions accepted, non-positive rejected at parse time. It
descends as an `Option<u64>` of bytes through `fossil_engine::run` into `fossil_df::run_to_dir`.
Unset means unbounded, which is today's behaviour unchanged.

There is no environment variable. `FOSSIL_DF_MEM_GIB` was scaffolding for a measurement and it does
not exist any more — no alias, no fallback. A number that decides whether a job survives is declared
in the command that launched it.

Given that number, `bounded_context` builds the DataFusion runtime with a `FairSpillPool` of that
size wrapped in a `TrackConsumersPool`. Without one it falls back to `SessionContext::new()` — an
unlimited pool with no disk manager, and therefore a configuration in which larger-than-RAM is not
untested but impossible by construction.

**The same number also configures DuckDB.** ADR-0043's stage-4 table had said to delete DuckDB's
`apply_resource_limits` as a duplication; read against the code that turned out to be wrong, because
the layout pass still runs on DuckDB and deleting its `memory_limit` removes the only bound that
engine has. What was duplicated was the *way of declaring it* — three environment variables against
one flag. So the function became `apply_memory_budget(conn, bytes)`, takes the run's number and sets
`memory_limit` plus a `temp_directory`; the three variables are gone. One declared budget, two
engines, one place to declare it. The ADR was amended with the reasoning rather than followed against
the evidence.

### The join that would not honour it

The budget also **turns off `prefer_hash_join`**, and that is not a tuning preference. The first
attempt at a 4 GiB budget died, and the consumer tracking named the culprit without needing a
hypothesis:

```text
HashJoinInput[8]#125(can spill: false) consumed 387.7 MB, peak 387.7 MB,
HashJoinInput[9]#126(can spill: false) consumed 291.9 MB, peak 291.9 MB,
…five of them, on a ten-core machine: one reservation per partition
```

A hash join's build side declares `can spill: false`. Told it may not allocate, it has nothing to
give back, so it dies. A sort-merge join spills. **A budget only means something if the operators can
honour it** — declaring the pool and leaving the plan free to pick an operator that cannot obey it is
a budget in name.

### A test that demands a spill

`crates/fossil-df/tests/spill.rs`, `a_ridiculous_budget_spills_and_writes_the_same_corpus`. Five
thousand people and four hundred thousand orders, written twice: once unbounded as a control, once
under the budget. The bounded run must open a spill directory and say so, and the two trees must come
out byte-identical.

The control is what makes it evidence. The default pool has no disk manager and cannot spill, so
without that half a spill in the bounded run would not be attributable to the budget.

**And the test forced a measurement nobody had made: a budget below the floor does not spill, it
dies, and the floor belongs to the machine rather than to the corpus.** Each sort partition reserves
`sort_spill_reservation_bytes` (10 MB) and declares it `can spill: false`, so the smallest viable pool
grows with `target_partitions`. On ten cores: 384 MiB dies with five `ExternalSorterMerge` holding
10 MB each, 480 MiB runs and spills, and it still spills at 2 GiB. That is why the test asks for 64
MiB *per core* rather than a round number. A 100 MB budget is not viable at any corpus size, and that
is part of the contract rather than a detail of the implementation.

<Callout title="This page cites a test now, and this is what the test does not test">
`backedBy` used to point at `crates/fossil-df/src/lib.rs` — the implementation — because the spill
test ADR-0043 stage 4 specifies had not been written. It has been, so the citation is an assertion
now rather than the presence of a feature.

Read what it asserts narrowly, because the file says so itself: it proves that a declared budget
causes a spill and that spilling does not change the output. It does **not** measure RSS, so it says
nothing about whether ten million vertices fit in 4 GiB — the numbers below are still a hand-run
measurement. And it only ever sees the plan `prefer_hash_join = false` leaves behind; a plan free to
pick a hash join would still die, which is why that flag is cleared and not something the test would
catch.
</Callout>

## The numbers, at ten million vertices

| ten million | unbounded | 4 GiB + sort-merge |
| --- | --- | --- |
| RSS after `execute_graph` | 15.68 GiB | **5.56 GiB** |
| RSS entering `enrich_layout` | 16.51 GiB | **6.82 GiB** |
| process peak | ~21 GiB | **9.87 GiB** |
| wall clock | 256.3 s | 290.9 s |

**Eleven gigabytes off the peak for 13% more wall clock, and the corpus is byte-identical** — 87
files, every md5 equal. This is a memory result, not a different output.

It also settled what the sixteen gigabytes were. Counted in Arrow, the graph handed to the writer —
every vertex batch plus both orientations of every edge table, 10M vertices and 71,024,690 edges — is
**1.64 GiB**, while the process holds 15.68. Dropping the `SessionContext` before encoding frees
**0.00 GiB**, because its `MemTable`s are the same Arrow buffers rather than a second copy. And the
edge collect measured +7.67 GiB on one run and +11.35 GiB on the next of an identical corpus. Live
data does not vary by 3.7 GiB. It was operator memory nobody had bounded.

### And then the layout stopped asking for two more gigabytes

`97efc79` made `enrich_layout` read the CSR the artefact already is, instead of building a
`Vec<(u32, u32)>` to feed a parameter that took an unordered bag.
[Streaming](/docs/characteristics/streaming) has the shape of it; the result belongs here:

| ten million, 4 GiB budget | before | with the CSR |
| --- | --- | --- |
| `community_hierarchy` | +2.09 GiB · 135.0 s | **+0.08 GiB** · 168.0 s |
| process peak | 10.10 GiB | **8.39 GiB** |

**−1.71 GiB, against the ≈ −1.7 GB the ADR predicted**, and the corpus is byte-identical again: 87
files, all 87 md5s equal to the previous binary's, and the three parity tests in
`crates/fossil-runtime/tests/layout_renumber.rs` passed without being touched.

The `community_hierarchy` row is the whole finding. The step used to cost +2.09 GiB because it built
the CSR on entry; now the CSR already exists and the step costs +0.08. **The memory did not move
somewhere else — it stopped being asked for.** Which also retires a claim this page used to carry,
that the +2.09 was Louvain's O(n) community state. It was not. It was the CSR Louvain built on the
way in.

<Callout title="Two baselines, 0.23 GiB apart, and that is the resolution">
The unbounded-versus-budget table above measured the pre-CSR peak at 9.87 GiB; the CSR table
measures the same binary at 10.10 GiB. Two runs of one build, on a machine other agents were also
using. Nothing reconciles them and nothing should — **the spread between two identical runs is about
0.2 GiB, and every number on this page is only as sharp as that.** It is also why the encode-phase
result on the streaming page reads as no result at all.

The wall clock moved the wrong way in the CSR table, 135 s to 168 s, and it is not a clean number
either: the same previous binary measured 151 s on another pass. Walking two arrays per vertex
instead of one has a locality cost that is structural rather than noise, and it is written down as
something to measure on a quiet machine before anybody calls it free.
</Callout>

## What is not true: the peak still grows with N

A bounded executor is not larger-than-RAM, and the same budget at two sizes says so plainly. The only
variable below is the corpus:

| under a 4 GiB budget | 1M | 10M | ratio |
| --- | --- | --- | --- |
| retained in Arrow | 0.16 GiB | 1.64 GiB | **10.3×** |
| RSS after `execute_graph` | 2.02 GiB | 5.56 GiB | 2.8× |
| RSS entering `enrich_layout` | 2.13 GiB | 6.82 GiB | 3.2× |
| process peak | **2.43 GiB** | **9.87 GiB** | **4.1×** |
| wall clock | 17.8 s | 290.9 s | 16.3× |

Ten times the corpus, four times the peak. The pool caps the executor and nothing else, and the terms
outside it follow N.

That table is the **pre-CSR** binary at both sizes, which is the only reason it is still a
comparison: one million has not been re-measured since. Ten million peaks at 8.39 GiB now, and
dividing that by 2.43 would be arithmetic rather than measurement, so the ratio is left where it was
taken. The shape of the finding does not depend on the missing run — 1.64 GiB of retained Arrow at
ten million against 0.16 at one is exactly linear, and nothing bounds it.

What remains outside the pool is ours, and it is the same shape in every case: **a stage boundary
that is a whole value rather than a stream.** `GraphArData` holds every batch before a byte is
written. The engine streams — DataFusion hands batches out lazily — and our seams collect.
[Streaming](/docs/characteristics/streaming) takes each one in turn, including the two that were
settled after this table was written: one turned out not to be a seam at all, and the other has since
landed.

<Callout>
So the claim that survives today is narrower than the destination, and the difference is the whole
point of separating the two registers: **the write path can be given a memory budget it will honour,
and a test in CI says so.** Whether a corpus larger than the machine can be written is untested, and
on these numbers the answer at 100M is no.
</Callout>
