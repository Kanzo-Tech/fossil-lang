fossil has one access operator, and it means one thing.

> **`.` means *member of*, and the type on the left decides what is on the right.**

| On the left of a `.` | Its members are |
| --- | --- |
| a **namespace** — `io`, `str`, `parse`, `clean` | its functions |
| a **type** — `User`, `Person` | its fields |
| a **relation** — `Users`, `Adults` | its operations — `where`, `select`, `join`, `distinct`, `union` |

Two more glyphs, and they are different acts rather than two spellings of one:

| | |
| --- | --- |
| `:=` | introduces a name — a shape, a source, a derived relation; the left-hand side says which |
| `=` | fills a slot the shape declared — `name = User.name`, inside a mapping body |

Reading any fossil expression needs the type on the left and nothing else. The obvious alternative is
Rust's, where `::` walks a path known at compile time and `.` reaches into a value at run time; it
has no referent here. A fossil program does not execute — it is elaborated into
[an operator tree](/docs/design/algebra) and lowered, so `User.age` is a column reference that
becomes SQL rather than a field read. There is no moment at which one side of that distinction is
happening and the other is not, so the second operator would be a rule whose justification a reader
can never observe.

## Verbs are rows, not grammar

`where`, `select` and `join` are not keywords. They are catalogue entries whose receiver type is a
relation, in exactly the way `lower` is an entry whose receiver is a string.

> **A new capability is a row, never a production.**

Adding an operation over relations touches neither the grammar, the parser, the checker's dispatch
nor the editor's completion, because none of them knows the name of a verb — they know how to ask a
type what it has. That is the same mechanism as [the provider registry](/docs/design/type-providers)
and as completion after a dot: one property seen from three sides, not three properties.

A row is enough only if it declares **everything** the verb takes, including whether an argument is
written with its name. A join's condition is `on = …`; with the name missing from the signature the
binder would fill `on` from the second positional slot and `join(User, a == b)` would start
compiling. Five kinds fill a position and two of them name rather than evaluate
(`crates/fossil-hir/src/stdlib.rs:311`):

| kind | what fills it | verbs |
| --- | --- | --- |
| `Rows` | the receiver relation itself | every verb's position 0 |
| `Scalar(T)` | an expression of that type | `take`, `drop` |
| `Predicate` | a condition over the receiver's rows | `where`, a join's `on` |
| `Column` | a qualified column reference — a NAME, not a value | `select`, `sort`, `group_by` |
| `Binding` | the name of a source binding | `join`, with `X as Y`; `union`, without |

## The alternative grows as *n · m*

The established mapping languages spell an operation per shape of data: "filter" is not a function
over a row type, it is a configuration construct with its own vocabulary, and everything new you
might do to a source arrives as new vocabulary in the format.

| *n* operations, *m* kinds of data | constructs needed |
| --- | --- |
| one construct per operation per shape | ***n · m*** |
| one generic catalogue entry per operation | ***n*** |

A configuration format with no type system has no mechanism for generalising, so it tends towards the
product: those surfaces grow monotonically and nothing is ever removed from one. Here `where` takes a
relation of any row type and a predicate over that same row type, so the *m* dimension disappears
into the receiver — and the predicate is an ordinary expression passed as an argument, which makes a
filter comparing a string to a number a compile error where it is written.

## Why you declare no functions of your own

A user-defined function has to survive the lowering. Admitting one means answering — permanently, and
in the type system — what happens to recursion, to a function that closes over a relation, to a
function used where the engine below has no corresponding construct. Every answer is either a
restriction the user learns or a capability the engine grows.

Not having them keeps the promise checkable: everything callable has a signature, every signature has
a known lowering, and *if it compiles, it runs* is a property of the whole language rather than of
the fragment that happens to lower cleanly. What replaces them is composition of catalogue entries,
which works because the entries are generic — and an entry lands when the second program that needs
it arrives and not before, an admission rule that is
[in the discard list](/docs/design/discarded) with the evidence that produced it.

This design has one price, paid in the corpus rather than in the compiler: **one entry is reachable
by two paths.** `x.trim()` and `str.trim(x)` are both correct and both appear in real programs, so a
corpus of fossil carries two spellings of one idea — a genuine exception to the house rule against
exactly that. What makes it acceptable is that it is a **resolution rule** rather than two
constructs: one entry, one signature, one implementation, which is `s.len()` ≡ `str::len(&s)` in Rust
and `s.upper()` ≡ `str.upper(s)` in Python. It is spelled out once, in
[one catalogue row, two ways to reach it](/docs/design/expressions#one-catalogue-row-two-ways-to-reach-it).

## What would reverse this

1. **A type whose members cannot be decided statically** — a source whose columns vary per row, a
   dynamically assembled record. That breaks the premise under the syntax rather than the syntax.
2. **The two paths used for different things.** The moment `str.lower(x)` means something `x.lower()`
   does not, they are two spellings rather than one entry. Observable in the corpus, not arguable.
3. **A vocabulary whose short names collide so often that renaming is the norm.** Then the short name
   has stopped being the name, and [the rename](/docs/design/type-providers) goes with it.

## What is still open

**Where `select` lives when the relation came from a join.** A join's row type is the union of two
schemas; which side qualifies, and whether the qualification survives into the mapping body, has more
than one defensible answer.

**Whether `io` should also name the destination.** A destination is an operational decision belonging
to whoever launches the job, and it is also the one part of a program's meaning that lives outside
the program. A program whose output location is part of what makes it that program would settle it.
