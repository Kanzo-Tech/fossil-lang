---
title: One engine
description: The language runs on DataFusion, and DuckDB leaves the compiler.
---

fossil compiles to relational algebra and something has to execute it. Two things
did: DataFusion in `fossil-df`, and DuckDB — bundled, compiled from C++ — in
`fossil-runtime`, `fossil-engine`, `fossil-mcp` and `fossil-cli`.

**The language runs on DataFusion. DuckDB leaves the compiler.**

## Why it is not a preference

`fossil-runtime` and `fossil-engine` each carry a `compile_error!` for `wasm32`,
and the reason named in both is bundled DuckDB. So the sentence this project is
built on — *fossil is a compiler consumed as a WASM library* — is true of
`fossil-wasm` and false of the layout pass and the engine. One dependency is
what makes it half true.

Remove it and the whole compiler is WASM-capable. That is the decision; the rest
is consequence.

## What it costs, measured

`libduckdb-sys`'s build script is **98.14 s of a 165 s cold build — 59 % of the
wall clock**, because `features = ["bundled"]` compiles DuckDB from C++. It is
one shared unit, not one per binary; the sixteen test binaries that link it link
a static library already built. Removing it removes that unit.

## What has to be rewritten, and it is three things

1. **The layout pass — done.** It reads and writes Parquet with `arrow-rs` and
   holds no connection. The finding is that **none of the algorithm was in SQL**:
   Louvain and Morton were already Rust, and the SQL only read, applied arrays
   that Rust had computed, sorted, and wrote. What replaced it is three Arrow
   kernels — `concat_batches`, `lexsort_to_indices`, `take` — plus the encoder
   `fossil-df` already had.
2. **The corpus verbs' native executor.** `DuckRuntime` runs the verb SQL
   `fossil-graph` produces. DataFusion reads Parquet natively.
3. **The assertions.** `fossil-cli` and `fossil-engine` open an in-memory DuckDB
   to read the Parquet they just wrote. That is a test convenience, not a
   dependency of the language.

## What the first piece cost, and it is not measured yet

The memory budget no longer reaches the layout. `--memory` used to open the
connection and cap it with `apply_memory_budget`, and DuckDB's sort spilled to
`temp_directory` when it hit the cap. The Arrow sort does not spill: the
adjacency is `concat_batches`'d whole and `lexsort_to_indices` runs over all of
it. At ten million edges the arithmetic is roughly **+2 GB of peak** and there is
no valve.

This is stated rather than measured, and it is the first number owed before the
piece is called good. The budget still reaches the DataFusion half of the run
(`bounded_context`), which is where the joins and the aggregation are; what is
uncapped is the post-pass.

## The one measured gap, and it is closed

**DataFusion's `read_json` is NDJSON only; DuckDB's reads arrays.** It was the
`sightings` conformance program, failing with `Json error: Not valid JSON: EOF
while parsing a list`, and the choice it forced was named here before it was
made: either the program declares NDJSON, or something supplies an array reader.

The program does not declare NDJSON. Letting the engine's reader decide what
`io.json` MEANS is the accident redefining the design — a `.json` file
ordinarily holds an array, and DuckDB, which still reads the corpus on the other
side, reads one. So `read_json_source` sniffs the first non-whitespace byte and
reads both shapes, and `a_json_array_and_ndjson_read_the_same` holds the two
against each other.

**An array materialises, and that is the format's property and not the
reader's.** You cannot find the end of record N without parsing from the start,
so any array reader is bounded by the file — which is why NDJSON exists and why
it keeps the streaming path untouched. It is the one exception to
`read_source`'s «never pre-materialised», and it is forced rather than chosen.

## What is NOT affected, and it is the half that looks like it should be

The corpus **read** side keeps DuckDB, and it is not our dependency there. In
the browser `@fossil-lang/graph` delegates execution to a host-provided
DuckDB-WASM callback: the host brings the engine, the binding brings the SQL.
Native, `fossil-mcp` is the same shape. Nothing about this decision asks a
consumer to stop using DuckDB to read a corpus — it asks the *compiler* to stop
containing one.

## The measurement that does not decide this, and why

F7 measured `arrow-rs` against `COPY` in the layout post-pass and reverted: it
did not pay. That was a **performance** measurement of a writer, taken when the
goal was a faster writer. The goal here is one engine and a compiler that builds
for `wasm32`, and a throughput number does not answer it. If the rewrite turns
out to cost real time on a real corpus, that is a number worth having beside
this page — it is not a reason not to try.

## What it buys the catalogue

One dialect. A function's lowering is one SQL template rather than one per
engine, which is most of what makes a multi-dialect function catalogue (Malloy's,
for instance) expensive to build and to keep honest.
