---
title: A privacy bound with no chokepoint
description: Why the classification is a document rather than a shape annotation, why the program binds it rather than a flag naming it, why the language names no anonymisation operator, and what four vocabularies leave to a six-term profile.
---

A fossil corpus is files, handed over. The recipient reads every column with any Parquet reader.
**That is not fixable, and this page is what follows from accepting it.**

## The consequence, taken rather than fought

There is no chokepoint. No process of ours stands between the files and whoever has them, so **no
read-time privacy control is possible** — not a masked column, not a row filter, not a permission on
a verb.

The temptation is to answer this by withholding the escape hatch: gate `execute_sql` and the problem
looks smaller. It is not smaller, it is hidden. [`read`'s `where` is a raw SQL
fragment](/docs/design/corpus#reads-where-is-sql-and-carries-executesqls-authority) evaluated by
the same engine, so gating one and not the other is the same surface with a second door — and even
with both gated, the recipient has the Parquet.

The systems that genuinely do this have a chokepoint and still do not put the control on SQL.
Snowflake applies dynamic data masking and row access policies inside the query planner; BigQuery
does column-level ACLs and row-level security the same way; Databricks likewise. The control is
**below** the query language, which is exactly the position a file format does not have.

So:

- Protection is **total at write time**. The bytes that would violate the bound are never written,
  and every reader preserves it for free.
- What travels with the artifact is a **declaration plus a verifiable property**, never an
  enforcement. [The declared bound](/docs/format/conventions/privacy) is the format.

<Callout type="warn" title="Two products, and only one of them is this">
A corpus that is **served** — the operator keeps the files, access is only through their engine —
does have a chokepoint, and it admits what this cannot: query-time perturbation, differential
privacy, a budget that runs out. It also costs what this does not: a trusted operator, and an answer
that degrades with use.

That is a different product and nothing here is built for it. Nothing here assumes it away either:
the manifest states what the *bytes* guarantee, and a served deployment is free to guarantee more on
top.
</Callout>

## The language names no anonymisation operator

There is no `anon.generalise`, no `anon.mask`, no `anon.hash`. The reason is not that they are hard.

**An obligation an author discharges by remembering to call a function is one they can forget**, and
the failure is silent in the worst possible way: the program compiles, the corpus writes, the
manifest seals, and the missing call is discovered by the recipient. Nothing in the pipeline is in a
position to notice, because a mapping that does not call a function looks exactly like a mapping
that had no need to.

The bound is stated instead, and the writer refuses. The author's obligation becomes "reach k",
which is checkable, rather than "remember to anonymise", which is not.

**The writer also reaches it.** The policy declares a generalisation hierarchy per
quasi-identifier — `fossil:generalization`, below — and the write path derives the generalisation
that meets the bound before it verifies one. That is not a retreat from the paragraph above, and
the distinction is the whole of why it is safe: a hierarchy is a **parameter**, declared once beside
the bound it exists to reach and applied on every run, and there is still no call for an author to
forget because there is no call.

What it replaces is worse than an operator. For as long as the policy could name a `k` and no
hierarchy, nothing in the system could produce a generalised column — so the verification could
only ever **refuse**, and a corpus passed exactly when its source data happened to be k-anonymous
already. A bound nothing can satisfy is not a stricter design; it is half a mechanism.

## The classification is a separate document, and not an annotation on the shape

A program already binds one external document per output type — `type { Person } :=
io.shex("persons.shex")` — and [shapes](/docs/design/shapes) is where that stands. The obvious
place for a privacy classification is inside it: ShEx and SHACL both have annotation mechanisms, and
the shape already enumerates every predicate.

**It must not go there, and the reason is reuse.** A shape says what a `Person` *is*: which
predicates it carries, with what cardinality, at what datatype. That is a property of the
vocabulary, and it holds in every jurisdiction and every deployment. Whether `birth_year` is a
quasi-identifier is none of those things — it depends on what else is released, on who the recipient
is, and on which regulator is reading.

Putting the second inside the first produces one shape per deployment, differing only in
annotations. That is how a vocabulary stops being shared.

So it is a second document, bound the same way, and the two are joined by **the predicate IRI they
both name**.

## The program binds it, and a flag is a thing you forget

`policy := "people.jsonld"` is a top-level form (`grammar.bnf, PolicyDef`). It is the same argument
as the missing anonymisation operator, one level up: `fossil run --policy <path>` was the only way to
name a bound for as long as the production sat in the grammar unparsed, and **an obligation
discharged by remembering a flag is one that can be forgotten**. A binding lives in the file that
gets reviewed, diffed and committed; a flag lives in whatever invoked the run, which is a CI job
somebody edits under time pressure.

Forgetting stays survivable rather than becoming impossible, and the mechanism is unchanged: a
release nobody declared a bound for seals `privacy: undeclared` rather than omitting the field, so a
corpus that was never checked never looks like one that was.

### Both given is an error

`--policy` is not deprecated by the binding, because the two answer different questions. A binding is
how a **producer** carries the obligation in the artifact; the flag is how a **recipient**, or a CI
gate, imposes a bound on a program they did not write and cannot edit. Where both are given the run
refuses, and the two losing answers are the argument:

- **If the flag won**, an operator could weaken a bound the program declares by passing a looser
  document, and the corpus would seal with the looser number and no trace of the one the program
  asked for. That is the failure this whole page exists to make impossible.
- **If the program won**, `--policy` would be accepted and silently inert — worse than the first,
  because the operator then holds evidence they were checked against a document nobody opened.

Refusing costs one message and is repaired by deleting one of the two. It is the shape this design
takes everywhere else: a type the policy is silent about is an error rather than an exemption,
because silence is indistinguishable from a judgement that there was nothing to protect.

### Not through `io`, and that is not a spelling preference

Every other external document a program names arrives through the `io.` registry —
`io.shex("persons.shex")` — so `io.policy("people.jsonld")` is the obvious form, and it is
[discarded](/docs/design/discarded). `io` is the **type-provider** registry
([type providers](/docs/design/type-providers)): a row there runs at *compile* time and its output is
types. The compiler never opens a policy document. The **writer** does, after the check and
immediately before it seals — so `io.policy` would join a registry whose defining property it lacks,
and `fossil providers`, whose JSON populates a connector UI, would advertise a policy as a data
source.

What the analogy with a shape binding was ever about is **who supplies the document**: the program,
not the host. That half is exactly what landed. The `io.` half was the accident of there having been
only one kind of external document until there were two.

The reference is a plain string and goes through the one resolution rule (`fossil-locator`: `@conn`,
a scheme, an absolute path, else the program's directory), which is what a shape document's reference
goes through too — the rule reads a string, and the `io.` call around it never contributed anything.
The cost is one token of extra lookahead at the top level and nothing else: the token after `:=`
decides, so `policy := io.csv("p.csv")` still binds a source and `policy` remains an ordinary
identifier in every position (`grammar.bnf, § DISAMBIGUATION RULES`, rule 8).

## Three vocabularies, and the gaps that forced a fourth

| | what it supplies | where it stops |
| --- | --- | --- |
| **ODRL 2.2** | The structure: `Policy`, `Permission`, `Prohibition`, `Constraint`, and the `leftOperand`/`operator`/`rightOperand` triple | `odrl:target` names an `Asset`. There is **no granularity below it** — no column, no attribute, no field, no schema |
| **DPV 2.3** | Classification values: `dpv:IdentifyingPersonalData`, `dpv:SensitivePersonalData` | It names privacy *techniques* and **cannot parameterise them**, and it has no quasi-identifier at all |
| **ISO/IEC 20889:2018** | The definitions the terms stand for | It is a paywalled standard, not a vocabulary — nothing dereferences |

The two gaps are load-bearing and both were checked rather than assumed.

**DPV cannot hold a number.** Not one `xsd:decimal`, `xsd:integer`, `xsd:float` or `xsd:double`
appears in DPV core, `dpv-tech` or `dpv-risk`, and every `has*` property is concept-valued —
`dpv:hasScale`'s range is `dpv:Scale`, an enumeration, not a magnitude. `dpv:DifferentialPrivacy`
exists as a bare class you assert or do not; **there is nowhere in DPV to put an ε or a k.**

**DPV has no quasi-identifier.** Case-insensitive search across all eight DPV 2.3 serializations for
`QuasiIdentifier`, `IndirectIdentifier` or `DirectIdentifier` returns nothing. The combination case
— which is the whole of k-anonymity — is absent.

### The profile is six terms

ODRL sanctions the extension in as many words. Information Model §3.3: *"Additional Constraint left
operands: Create an instance of the LeftOperand class."* And §3.2 buys the property worth having:
*"if the ODRL Processing system does not recognise the ODRL Profile identifier(s) then it MUST stop
processing the policy."* A runtime that does not know this profile is **required to stop, not to
guess**.

| term | why it is not somebody else's |
| --- | --- |
| `fossil:attribute` | ODRL has no sub-asset granularity. This is the term that does most of the work |
| `fossil:classification` | The dimension a `Constraint`'s single triple cannot carry alone |
| `fossil:anonymityK` | DPV has no numeric range |
| `fossil:absentQuasiIdentifier` | Likewise, and it is the parameter the whole check turns on |
| `fossil:suppressionBudget` | Likewise |
| `fossil:generalization` | The hierarchy that reaches the `k`. DPV has `dpv:Generalisation` as a bare class you assert or do not, and nowhere to put the levels |

Plus two `skos:Concept` values — `fossil:QuasiIdentifier` and `fossil:NoDisclosureRisk` — where DPV
has nothing to borrow. The classification values that DPV *does* have are DPV's.

**The ceiling is a test, and the sixth term is what it was for.** Catena-X is the one production
European data-space profile and it ships **four** `odrl:LeftOperand`s — `FrameworkAgreement`,
`Membership`, `ContractReference`, `UsagePurpose` — for an entire automotive industry, and not one
of them is schema-aware. For as long as there were five here, this page said a sixth needed an
argument. The argument is the paragraph above: five terms could *state* a bound and not one of them
could *reach* one.

Catena-X's four are the wrong bar for this term specifically, and the reason is worth stating rather
than treating "four is the bar" as arithmetic. All four are about **contract eligibility** — who may
use the asset, under which agreement, for what stated purpose. None is schema-aware, so none could
parameterise a transformation even in principle; a profile that reaches inside the asset is
answering a question that profile never asks. The bar it *does* set — do not mint a term for
something an existing vocabulary can say — is the one applied, and it is met.

A **seventh** now needs an argument. The one that will be asked for first is a generalisation
margin — "derive to k times this", as a mitigation for the minimality attack below — and the answer
is that `fossil:anonymityK` already expresses it: a producer who wants a table that is not minimal
for `k` declares a larger `k`, and the number they chose is published on the artifact instead of
hidden in a multiplier.

The `rightOperand` of `fossil:generalization` is the **hierarchy itself, inline** — the object
`fossil-kanon`'s `hierarchies/*.json` files already hold. Not a registry name, which would undo the
reason those hierarchies are files a statistician revises rather than constants a programmer
recompiles; and not an IRI to fetch, which is the one thing the policy reader refuses on principle.
See [discarded](/docs/design/discarded) for both.

<Callout type="warn" title="The interoperability claim is narrower than it is usually made">
The reason normally given for minting into ODRL is that the Dataspace Protocol leaves `leftOperand`
open. **It does not.** DSP's `contract-schema.json` pins `LeftOperand` to a closed `enum` of exactly
the 34 ODRL Core instances — no extension slot, no `pattern`, no `anyOf` — so a policy carrying
`fossil:attribute` fails that schema.

What is true is narrower and still worth having. DSP's SHACL shapes constrain `odrl:target`,
`dspace:timestamp`, `odrl:assigner` and `odrl:assignee` and place **no** constraint on
`leftOperand`; its prose says nothing about it either. The closed enum is one artefact of three, and
the same file carries `odrl:term-lteq` in its `Operator` enum — an HTML anchor pasted where the term
IRI goes — which is a fair indication of how much load it is bearing. Eclipse EDC shipped the enum
as a Java type, had it filed as *"a severe blocker"* because the model *"cannot express constraints
other than those defined in the enum class"*, and moved to free-form.

So: an ODRL profile in ODRL's own sense, readable by anything that reads ODRL, and rejected by a
**strict** DSP validator until DSP's schema catches up with ODRL's extension point. That is a defect
in one JSON Schema, not a reason to invent a fifth format.
</Callout>

## Verification is the part that is easy to get wrong

The check is not `GROUP BY qi HAVING count(*) < k`. [The declared
bound](/docs/format/conventions/privacy#three-ways-to-compute-k-and-a-group-by-picks-one-by-accident)
specifies the three traps and what the manifest publishes about each; the short version is that
nulls have two defensible readings that disagree on the same file, that a suppression limit is part
of what k-anonymity means in practice, and that a corpus of tiles makes a per-tile aggregation the
easiest wrong answer available.

The verifier **measures and refuses**. It derives nothing: no generalisation search, no recoding, no
rows dropped and no cells blanked. A verifier that also repairs is a verifier whose failures nobody
ever sees.

The derivation is a **separate pass immediately before it**, over the same in-memory batches, and
the separation is load-bearing rather than tidy. Nothing flows from the deriver into the verifier —
not the achieved `k`, not the class count, not the column list, not a hint that derivation happened
at all. So the release is measured **twice by two implementations that share no code**: once inside
`fossil-kanon`, which re-reads its own output before returning it, and once by a DataFusion
aggregate over the written columns that was handed nothing. The manifest records the second. If the
two ever agreed by construction rather than by measurement, the guarantee would be circular.

A consequence worth stating plainly: the deriver is allowed to fail. A derivation that does not
reach the bound produces exactly the refusal an ungeneralised corpus would. It is best-effort; the
verifier is the guarantee.

<Callout type="warn" title="Minimal generalisation is not the safest generalisation">
Wong, Fu, Wang and Pei (VLDB 2007) showed that publishing the table an algorithm generalised
*minimally* leaks: an adversary who knows the algorithm reasons backwards from where it stopped —
"one more cut would have left a class below k, so that class had this shape" — and recovers values
the k-anonymous table appears to protect. Mondrian stops as soon as it can, so this is exactly such
a table, and **it is not defended against**. Defending means m-invariance or a descendant, which is
a different algorithm and not a flag.

Three things are done instead, none of them a defence and all of them visible. Observed-range
numeric output is **refused** — Mondrian's own `[min, max]` is two values real records hold, in the
column being generalised — so every published cell is a node of a *declared* hierarchy. That partly
mitigates the attack, because a declared bucket is a function of the hierarchy and not of the
partition, so the cut position the inference reasons back from is not in the released bytes.
Partial, and not a reason to call the release defended. And the manifest says what was done: see
`generalization` in [the format](/docs/format/conventions/privacy).
</Callout>

Its refusals name counts, column names and type labels, and **never a cell**. A diagnostic about a
privacy violation that prints the violating row has moved the disclosure out of the artifact and
into the log, the terminal scrollback and whatever CI captured — none of which was ever going to be
checked by a guard.

## What is claimed, and what is merely declared

The honest split, because the two are easy to blur:

**Checked, by anyone, from the files:** that the classes over the declared quasi-identifiers reach
the declared `k`; that the aggregation spanned the release; that the suppression is inside the
budget; that the manifest's numbers are the bytes' numbers.

**Declared, and checkable by nobody:** that the quasi-identifier set is the right one; that
`subject` is opaque; that anything a producer chose not to write was ever there. Those are stated on
the guard as what it cannot prove, because a guard that overstates its reach is worse than a missing
one.
