Static types are usually sold on the errors they prevent. In a mapping language the more immediate
return is in the editor, and it is not a general claim about typed languages — it is a claim about
this design specifically.

## The receiver decides, so completion is exact

Because [the dot means *member of*](/docs/design/the-dot), the set of things that may follow it is
decided by one type. Completion after `.` is not a ranked guess over everything in scope; it is that
type's member list. Two consequences follow directly, and neither needs a heuristic.

**Offering something that will not compile stops being possible.** A completion list assembled from
a catalogue of names has to guess which entries apply, and guessing wrong is the ordinary case — a
namespace-shaped catalogue offers string operations after an integer, because it has no way to know.
A list derived from the receiver's type offers exactly the applicable entries, because the same index
that answers *does this member exist* answers *what members are there*.

**An unknown member searches the right space.** When a member does not exist, the suggestion is drawn
from that type's members rather than from the whole catalogue — so the candidate set is a handful of
plausible names rather than the entire language:

That is the same mechanism producing a better message, not a second feature that has to be kept in
step with the first.

## Filling a mapping body from both ends

The concrete thing this design makes possible, and it is the clearest single demonstration that
[both ends of a program are types](/docs/design/types).

At that moment the language server knows two things it did not have to be told. It knows what
properties `Person` declares and with what cardinality, because the shape document is a constraint
table and the checker already holds it. And it knows what fields are available on the right-hand
side, because `Adults` is a relation of `User`s and `User` is a named type generated by
[a provider reading the file](/docs/design/type-providers).

So it can write the body's skeleton — one hole per property the shape requires:

**The names come from the shape. The holes are filled by the author. And inside each hole, completion
offers the fields of the source.** Two halves of the mapping completed from two opposite extremes,
and neither half is a heuristic: it is the type answering.

The precedent is rust-analyzer's *implement missing members*, and the comparison is instructive
because there the two ends are a trait and an implementation — both written by programmers, in the
same language. Here they are a shape document and a data file, written by other people in other
formats, and the affordance is the same because the compiler has turned both into types.

## Responsiveness is a property of the design, not of the effort

An editor experience is a latency claim, and latency claims rot unless something holds them.

Two things hold this one. The first is structural: **the language layer carries no engine.** Parsing,
name resolution, checking and diagnostics have no dependency on a database, which is what lets the
language server start in milliseconds and compile to wasm — so the same checker that runs in a
terminal runs in a browser tab, and the browser one is not a reduced imitation of it.

The second is incrementality, and it comes with one invariant worth stating in the open: **editing
one mapping re-runs work for that mapping and not for its neighbours.** That bound is the entire
reason the compiler has an incremental core at all, and it is the property every subsequent decision
about the compiler's internals has had to preserve. A design that re-checks a file per keystroke does
not need incrementality; it needs a smaller file.

The measurements that pin it are worth reading for their *shape* rather than their values. A warm
round trip on a two-hundred-line fixture measures around **0.12 ms**, and the worst cold case around
**3 ms** — both an order of magnitude under the hundred-millisecond target that makes an editor feel
immediate.

The interesting part is the gate. It is set at **400 ms, not at 100**, and deliberately:

- A bare assertion of *under 100 ms* flakes on a shared runner with a debug build, and a flaky gate
  is one that gets disabled.
- An asymptotic regression over a two-hundred-line fixture is measured in **seconds**, not in a few
  milliseconds, so it clears a 400 ms ceiling unambiguously.
- **The declared cost**: a gate at 400 cannot catch a thirty-percent regression that stays under the
  margin. That is what the advisory benchmark alongside it is for, and on a shared runner it does not
  block.

A gate that catches the failure it was built for and says what it cannot catch is worth more than one
whose threshold implies a precision the runner does not have.

## Interruption, and what a test of it must prove

An editor generates work faster than a compiler can finish it, so the compiler has to be
interruptible — and "interruptible" is a word that hides a distinction.

The mechanism is a cooperative checkpoint inserted at every query boundary, so an in-flight
computation notices a newer edit at the next boundary it reaches and unwinds. The consequence that
falls out of it, and that anyone writing a long-running loop inside a single query has to know: a
hand-written hot loop **contains no query boundaries**, so it contains no checkpoints, and it will
hold up the next edit until it finishes. The cooperative design makes this a non-problem for ordinary
work and a real obligation for the exception.

And the test for it has to prove **interruption**, not a request to interrupt. It is easy to write a
test that asserts a cancellation flag was set. The one that means something asserts that work placed
*after* the checkpoint never ran — and carries a negative control proving the sentinel is not
vacuously green. Timing-based versions of this test are the usual approach and they measure the
machine rather than the mechanism; rendezvous points prove the property with no sleeping at all.

## The cost this inherits, named

Reading real sources at compile time has a documented price and it falls exactly here. The most
mature system in this family — F#'s type providers — has its live pain in the IDE rather than in
batch compilation: providers re-running under an editing loop, sustained high CPU, and maintainers
describing the mitigation as a band-aid over deeper architectural issues.

A provider whose input is a **file** rather than a network call escapes most of that. "Most" is not
"all", and the residue lands on the editor — which is also where the benefit lands, and that
symmetry is the honest way to state it: the editor is where compile-time source reading is paid for
and where it is worth paying for.
