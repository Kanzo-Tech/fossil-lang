title: Three hosts
description: A language designed to be embedded, cut by where the code runs rather than by what it is about — because three destinations and one unbounded promise contradict each other the moment all of them are read as "run the engine here".
---

fossil is designed to be embedded. Three destinations have to work, and they are not variations of
one another:

- a **native command**, run from a terminal or from a job scheduler;
- **wasm in a browser**, where the editor and the checker live next to the person typing;
- a **product embedding it**, which supplies credentials, storage and a job lifecycle and wants the
  language to be a component rather than a subprocess it has to understand.

Add the promise that a corpus has [no ceiling on its size](/docs/design/larger-than-ram) and the four
requirements contradict each other — but only under one reading. If "this destination works" means
*run the whole engine here*, then the browser must be larger-than-RAM, and it cannot be: wasm32 has
roughly four gigabytes of address space and nowhere to spill.

The resolution is to stop treating the destinations as configurations of one program, and to cut the
code by **where it runs**, giving each layer a different promise.

## Three layers, three promises

**The language layer knows no engine.** Parsing, name resolution, types, diagnostics, elaboration
into [the operator algebra](/docs/design/algebra), and the language server that surfaces all of it.
It has no dependency on any execution engine, and that single negative fact is what buys two positive
ones: it starts in milliseconds, and it compiles to wasm. The checker in a browser tab is the same
checker, not a reduced imitation of it.

**The compiler layer has a disk.** It takes the elaborated program and the sources and produces the
corpus. *No ceiling* lives here and only here, because the promise is a budget plus spill and spill
requires somewhere to spill to. A layer without a disk cannot make that promise, which is precisely
why the promise must not live in a layer the browser shares.

**The host layer decides the inputs of a run.** A memory budget, a credential, a destination. These
are not properties of a language — nobody thinks a program means something different because it was
given more memory — they are **inputs of a command**, and they belong to whoever issues the command.

Gluon is the model here, and for a reason more specific than admiration: it is a small language whose
entire problem statement is being embedded in a host application, and its documentation is organised
around that fact. This is the same problem.

## Why not cut by subject matter

The obvious alternative is to organise the code by topic — parsing here, types there, the graph over
there. Three reference compilers were examined for how they actually do it, and the finding is more
interesting than the answer.

| | cuts by |
| --- | --- |
| Gleam | **IO and purity** — a core that is entirely pure, with IO supplied by the crates that wrap it |
| Gluon | **compiler phase** |
| rust-analyzer | **semantic richness**, with explicitly declared API boundaries |

**None of the three cuts by deployment target.** But all three cut by *what a piece of code is
allowed to know*, and what they forbid is always the same thing: **knowledge of the outside world.**
Deployment target is a proxy for that — a browser is exactly a place where the outside world is not
available — so the cut fossil makes is the same cut those three make, expressed in the terms that
make its constraint checkable.

The other finding is what happens when the cut is right: **the shells collapse.** Gleam's entire wasm
surface is around 352 lines, its binary six, its language-server transport sixty-nine. rust-analyzer's
command-line entry point is not even a crate of its own. A thick shell is a symptom that the layer
underneath is missing something, and a thin one is the evidence that the boundary is in the right
place.

And a caution taken from the same reading: **none of the three enforces its architecture with a
test.** rust-analyzer's most-cited layering rule is held up by a comment in a manifest, repeated
verbatim in two files. What actually does the work is a document that states the invariant **and its
reason** — the reason being the part that survives contact with somebody who wants to break it. The
one boundary that project defends hardest costs it roughly 3,180 lines of translation code, under one
percent of its source, and that ratio is the honest price of a boundary worth having.

## A boundary that is a threat model, not a taste

One layer boundary here is not a matter of design preference at all, and it is worth naming because
it looks mergeable.

Resolving a source path can require credentials: fetching from an object store, signing a URL,
holding secret material. That work needs facilities a browser does not have, and — more importantly —
**the threat model deliberately keeps credential material off the wasm boundary.** So the layer that
does it refuses to compile to wasm, by construction, and merging it into the layer that must compile
to wasm would do two things at once: break the browser target, and place credential handling inside
the browser.

The proposal to merge them, when it was made, came from comparing two header comments that both
described their file as a host-injection seam. Both comments were accurate. The constraint was
elsewhere, in a conditional compilation directive, and it took seconds to check.

> **The rule that came out of it: do not read prose where there was a checkable constraint.**
> A dependency query, a search for a compile-time refusal, or a build against the target answers in
> seconds a question that prose answers confidently and wrongly.

## The test for the host boundary

Embedding raises a question this design answers with a single criterion. The host owns credentials,
storage, job lifecycle, multi-tenancy and its own interface. fossil owns *what this program computes
and what it produces*. Where does a specific piece of work belong?

> **Anything in the host that re-parses, re-derives or re-models the language's own knowledge is a
> boundary violation.** And a program whose meaning — which graph it produces — changes with an
> external flag is not self-contained; the definition of the output belongs **in** the program, next
> to its sources and its transformations.

That criterion is unusually productive, because it turns architecture arguments into deletions. A
host that walks the compiler's intermediate representation to summarise a pipeline is re-deriving
what the compiler already knows; the repair is not a better walker, it is the compiler emitting a
description and the walker going away.

The clearest instance was one capability — *given a program and access to its sources, produce a
description of each source's type* — existing in **four** places, in two languages, in two
repositories. The cost is not the duplication itself:

> **Each copy has to agree about how a source's types map to the language's types, or the checker
> silently disagrees with the editor.** Four copies are four chances to drift, and the drift is
> invisible because each copy is individually correct.

The shape that resolved it is the general answer for an embedded language: **the logic has one home,
and the host injects the data plane.** The binding knows how to ask for a description and how to
build a type from the answer; the host supplies *how to reach the source* and *what executes the
query*. The entire argument about whether the schema read should happen in the browser or on the
server then dissolves into "what does the host pass in" — and the binding does not care, which was
the point.

## One implementation, and one wire

The criterion above turns architecture arguments into deletions, and it authorises a larger one than
it first appears to. If the embedding host is a browser, a capability only a native binary can perform
is a capability the product cannot reach. So the direction is that **every capability has one
implementation, in a crate that compiles to `wasm32`, and each host is a transport over it** — the
command line, the language server, the wasm shim and the machine-facing server are projections, and
none of them is the API. A verb that exists only behind the binary is not a smaller surface; it is a
surface with no embedding.

What is true today: `cargo xtask wasm-check` derives the gated set and checks it, and the
compile→run pipeline is inside that set. **The number is deliberately not written here** — this page
carried *seventeen* from a measurement on 2026-08-16 and it was eighteen by the time anyone read it
again, which is the same failure that retired the two hand-kept `-p …` lists xtask replaced. The
mechanism is worth knowing and cannot drift: the roots are the cdylib crates, **plus** any crate
declaring `[package.metadata.fossil] wasm = true`, which is how `fossil-layout` entered a closure
that nothing wasm depends on yet. `fossil
run` executes on DataFusion through `fossil_df::run_to_dir`; the browser executes on DataFusion
through `fossil-df-wasm`; and `crates/fossil-df/src/files.rs` is one Arrow→Parquet encoder shared by
both, so the native filesystem sink and the browser's signed `PUT` differ in where the bytes go and in
nothing else.

Sharing the implementation is only half of the promise, and the other half is where the drift got in.

> **Two hosts that share a function still disagree if they serialize it differently.** One
> implementation guarantees one *answer*. It does not guarantee one *wire*.

Measured, in the pair of exports built precisely to be one capability in two hosts: `fossil refs
--output-json` writes its result with `serde_json`, and `fossil_wasm::refs` writes the same Rust value
with `serde_wasm_bindgen::to_value`, whose `serialize_missing_as_null` defaults to `false`. A reference
with no `@conn` alias is therefore `"connection": null` from the command and an **absent key** from the
browser, because `undefined` does not survive `JSON.stringify`. The same default drops `count` from a
`RunStatus` the browser produced and keeps it as `null` on the one the command produced.

Neither test over that capability can see it. `crates/fossil-cli/tests/refs.rs` asserts
`plain["connection"] == Null` against parsed JSON — after the wire. `crates/fossil-wasm/tests/refs.rs`
asserts `plain.connection == None` against the Rust value — before it. They are otherwise the same
test over the same fixture, so between them they prove the shared logic agrees with itself and leave
the one place the two hosts can differ unexamined.

> **A capability offered to two hosts owes a test that crosses each host's wire, not each host's
> function.** Where the logic is already shared, a test of the function proves only that the sharing
> compiled.

## The one-home repair has to be earned

The worked example above — one capability in four places — records a repair: the logic gets one home
and the host injects the data plane. `packages/introspect` is that home.

A home is not an agreement, and for a while the one was read as the other. Until 2026-08-17 the
package's comment on `extractSourceRefs` said that it and `fossil-engine`'s `extract_source_refs`
were "character-for-character the same and must move together", and the two had drifted in **both**
directions at once: the TypeScript matched `io.(csv|json)` where the Rust matched
`io.(csv|json|parquet)`, and a second sentence in the same comment recorded a dispatch that read
every source with `read_csv_auto`, which the Rust had already replaced with `read_csv_auto` /
`read_json_auto` / `read_parquet`. The DuckDB→primitive table — the part anyone would expect to rot
first — agreed exactly, in both directions, which is what made the two that drifted hard to see.
What the drift cost is one sentence long: an `io.parquet` binding got no field completion in the
editor, because the browser side never recognised it as a source at all.

> **A repair that ends at "the logic has one home" has stopped one step early.** Two hosts that
> cannot share an implementation have two, and the second one is not watched by the first one's
> tests. What the home buys is that the disagreement is now between two files instead of four.

What closed it, on 2026-08-17: `packages/introspect/tests/rust-parity.test.ts` reads the Rust half,
derives three tables out of it — the source-binding pattern, the reader each `io.` constructor picks,
the DuckDB→primitive table — and compares each against what the package *does*.

**Two of the three have since stopped being an agreement, and one of them stopped being in that
crate.** The Rust half is `crates/fossil-introspect/src/lib.rs` now: `fbd1102` moved the `DESCRIBE`
out of the compiler, and the guard's own constant records where it went rather than being repointed
by hand. And which constructors exist and which reader each names are now two generated projections
of `catalogue.bnf`, written by two emitters — so the test compares `providers/generated.rs` against
`describeSql` instead of scraping a hand-written `match`. The type table is the one that is still
written twice by hand, and it is still read out of the Rust.

It restates no Rust value as a TypeScript literal, because a copy of the answer
cannot notice the answer changing, and every extraction throws when the shape it expects is gone, so
a rewritten crate fails the test rather than quietly matching nothing. It was proved red six ways,
the last of which is the crate being absent altogether: that exits 1, rather than reporting no tests
and looking like a pass. It runs under `pnpm`, so the Rust it reads carries a comment saying so —
`cargo test` will not tell you.

The fix that would have looked right is worth naming, because it was measured too. Widening the
TypeScript pattern **alone** leaves `io.parquet` with no field completion: the `DESCRIBE` goes out as
`read_csv_auto`, DuckDB's CSV sniffer fails on a Parquet file, and introspection is best-effort, so
the source is logged and skipped — which is indistinguishable, from the editor, from the source never
having been recognised. The description would have been satisfied and the behaviour unchanged.

There is a third answer, and no guard above touches it. `ExecutorSystem` in `fossil-df-wasm` leaves
`System::descriptors` at its trait default, so the browser path that *produces* the dataset introspects
no source at all and types its columns from defaults, while the browser path that *checks* the program
types them from the data. Two answers in one host, from one capability, is the same failure as two
answers in two hosts.

> **A parity claim written in a comment is prose where there was a checkable constraint** — this page's
> own rule, turned on the repair instead of on the proposal. It survived as long as nothing checked
> it, and both sentences it was made of were false by the time anyone read them closely. The comment
> is deleted rather than corrected: the guard makes the claim now, or nothing does.

## An open question this page does not settle

A product embedding fossil is named above as the third destination. Whether the *server* of such a
product is a host in its own right, or is the browser host wearing a server's clothes, is deliberately
left open here.

The evidence that it is its own host: it owns credentials, storage, job lifecycle and multi-tenancy,
which is exactly the list this page assigns to the host layer, and none of that runs in a tab.

The evidence that it is not: as of 2026-08-16 keasy's server spawns no fossil binary, and its images
declare themselves free of one. Every fossil capability it exposes is computed in the browser and the
server stores the result. On that reading the server is a data plane — signatures, bytes and rows —
and the host that fossil is embedded *in* is the tab.

Settling it decides something concrete, which is why it is worth leaving until someone means to decide
it: if the server is a host, it is owed a surface of its own, and today it links one Rust type and
consumes the rest as TypeScript.

## What this document deliberately does not contain

The layers are a design, not an inventory. Which units of code sit in which layer is a fact about the
tree, it changes as the tree changes, and a list of them printed here would be wrong before it was
useful — the same failure this document exists to stop repeating. The embedding surface itself is
generated from the code that defines it, for the same reason.
