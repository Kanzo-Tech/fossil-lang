A fossil program produces a **corpus**: a graph written to disk as columnar files with a manifest
that names them. Not a database to connect to, not a stream to consume, not an endpoint. Files.

The consequence that matters is what a reader has to do to use one. A reader that wants a slice of
the graph works out which byte ranges hold it and fetches those ranges — from a local path, from an
object store, from a plain web server. **There is no service in the path**, and therefore no query
language between the reader and the data, no process to keep alive, and no version of the writer the
reader has to match.

## Addressable, and what that buys

"Addressable" is the load-bearing word, and it means something narrower than "readable".

An address is computed, not discovered. Given the manifest, a reader derives the location of every
piece it wants **before it issues a single request** — arithmetic on identifiers and sizes, not a
lookup that has to be answered first. That property is what makes the corpus work over a plain
origin, and the evidence for it is a constraint that catches people out: **you cannot list a
directory over HTTP.**

That is why the shape of a naïve reader is wrong in an interesting way. Expanding a wildcard over
files *is* listing a directory. It works against a local filesystem, and it works against an object
store whose API offers listing, and it fails in a browser against a plain origin — which is the
worst possible distribution of a failure, because every environment a developer tests in succeeds and
the deployment target does not. A corpus is therefore designed so that nothing is discovered by
listing: what exists is derivable from what the manifest declares.

The lineage here is explicit and worth naming, because this pattern was solved elsewhere first:
**Cloud-Optimized GeoTIFF → GeoParquet → PMTiles.** One file or a small set, an embedded directory,
data laid out in an order that makes spatial locality into byte locality, and a client that issues
HTTP range requests with no server-side component at all. Copying that schema is cheaper and more
correct than inventing one.

## The artifact is the API

The design stance follows the table formats — Iceberg, Delta Lake, Lance — where a manifest plus a
set of files is the interface, *many* engines read the same table, and **none of them is the
contract**. The specification is the contract; an implementation is one reader.

That stance imposes obligations most projects discover late.

**Arithmetic that a reader must reproduce has to be published as arithmetic.** Iceberg is the good
example: it publishes the hash function, the seed, and a table of test vectors per type — searching
for one of those constants finds it in the tests of independent implementations that copied it.
PMTiles is the counterexample: it dispatches its space-filling curve with a link to an encyclopedia
article, and every port re-derives it. A reader that computes a different address from the same
manifest is not a bug report; it is a divergence nobody notices until the data is wrong.

**Two implementations before a format change, not after.** Arrow requires a second implementation
and integration tests *before* a format change lands, which is why its gaps show up as skipped lines
rather than as incorrect answers. A format whose test corpus does not round-trip through two
independent readers is a format whose reference implementation is normative by accident.

**And "by accident" is the specific fate to avoid.** Parquet's enduring problem is thirteen years of
files that cannot be withdrawn, with a reference implementation that became normative without anyone
deciding it and writer-version strings parsed against tables of known-bad releases. Every one of
those is the cost of the same missing decision, taken too late.

Which is why **capability negotiation is not built into a corpus that nobody else reads**, and why
the trigger for building it is written down rather than left to judgement: *the day a corpus leaves
this machine towards somebody who cannot regenerate it.* Before that day the mechanism answers a
question nobody has asked. After it, it is late.

## What is borrowed from GraphAr, and where borrowing stops

The corpus did not invent its manifest vocabulary. **GraphAr's YAML field names are borrowed
wholesale** — three files named the way GraphAr names them, `<name>.graph.yml`,
`<label>.vertex.yml` and `<source>_<edge>_<destination>.edge.yml`, carrying GraphAr's own keys:

| file | the keys, all of them GraphAr's |
| --- | --- |
| graph info | `name`, `prefix`, `vertices`, `edges`, `version` |
| vertex info | `type`, `chunk_size`, `prefix`, `property_groups`, `version`; per property `name`, `data_type`, `is_primary`, `is_nullable` |
| edge info | `src_type`, `edge_type`, `dst_type`, `chunk_size`, `src_chunk_size`, `dst_chunk_size`, `directed`, `prefix`, `adj_lists`, `property_groups`, `version`; per adjacency `ordered`, `aligned_by`, `prefix`, `file_type` |

And `version: gar/v1`, which is GraphAr's own string. Every one of those is in
`docs/specification/format.md` in `apache/incubator-graphar`, and none of them was invented here.
**Three keys are fossil's and are not in that document at all** — `iri`, `vertex_count` and
`edge_count` — and each is an entry in the list below rather than a quiet addition.

> **fossil follows GraphAr as far as GraphAr specifies, and no further** — because past that point
> there is nothing left to follow but a C++ implementation.

That is the rule, and it is worth stating as a rule because it answers questions nobody has asked
yet. Is the thing in the specification? Then fossil spells it the way the specification spells it,
and a difference is a defect. Is it only in that repository's `cpp/`? Then it is somebody's code: it
binds nobody, it is not a contract fossil is failing to meet, and the decision is taken here on this
project's own evidence. **This is not a GraphAr-conformant corpus and does not claim to be.**

### The count is why the rule is worded that way

GraphAr's specification never defines a count. `docs/specification/format.md` contains the word
"count" **zero times**: nothing it describes lets a reader learn how many vertices a type has.

The reference implementation stores one anyway, and *how* it does it is the argument.
`cpp/src/graphar/graph_info.cc` puts it at a path the specification never names —

```cpp
Result<std::string> VertexInfo::GetVerticesNumFilePath() const {
  return BuildPath({impl_->prefix_}) + "vertex_count";
}
```

— and `cpp/src/graphar/filesystem.cc` writes it as raw memory:

```cpp
RETURN_NOT_ARROW_OK(ofstream->Write(&value, sizeof(T)));
```

The only explicit instantiation of that template is `WriteValueToFile<IdType>`, and `IdType` is
`int64_t` (`cpp/src/graphar/fwd.h`); the three call sites are in `cpp/src/graphar/arrow/chunk_writer.cc`.
So a count is **eight raw bytes in the writing machine's byte order**, in a file with no declared
width, no declared endianness and no test vector. A corpus written on a big-endian machine is
misread on a little-endian one, and nothing in the artefact says so.

That is precisely the pathology [the corpus contract](/docs/characteristics/corpus-contract) names
about somebody else, and it sits *below* the line that page draws: PMTiles documents its curve badly
and every port re-derives it, while this documents nothing at all and is normative by accident —
Parquet's `created_by`, with the thirteen irrevocable years still ahead of it rather than behind.
Following it would mean copying a byte layout out of a C++ template, which is the one thing this
project has already decided it will not do.

### The divergences, each one pointing at something

None of these is a bug to be fixed. Each is the rule above applied once.

1. **`data_type` spellings GraphAr's own reader refuses.** Every vertex manifest fossil writes
   declares `dense_id` as `uint32` and marks it `is_primary`, and adds `cluster_id` as `uint32`
   (`crates/fossil-df/src/lib.rs`). The specification's built-in list is Boolean, Int32, Int64,
   Float, Double, String, Date, Timestamp, Time and List — no unsigned type. `TypeNameToDataType` in
   `cpp/src/graphar/types.cc` accepts eight spellings plus five `list<…>` and throws
   `Unsupported data type` on everything else, so it throws on the primary key of the first vertex
   type of every corpus fossil writes. Two more spellings leave by the same door: `time`, which the
   specification lists and that function never implemented, and `binary`, fossil's fallback for an
   Arrow type with no mapping, which is in neither the specification's list nor the parser.
2. **A count is a manifest field, not a file.** The reference writes three files — `vertex_count`
   per vertex type, `vertex_count` per adjacency, and `edge_count{k}` per vertex chunk. fossil
   writes none of them, because the specification asks for none of them. It declares
   `vertex_count` and `edge_count` in the YAML instead, for the reasons in the callout below.
3. **No offset table.** The specification does ask for this one: *"there would be an offset table
   for **ordered_by_source** or **ordered_by_dest** edges… The first row of each offset chunk is
   always 0."* fossil emits no offset table of any kind: there is no `offset/` anywhere under
   `apps/corpus/conformance/corpus/edge/Person_knows_Person/`, which holds the edge info, the ten
   tiles of `by_source/` and `by_target/`, and the two single-file containers of the same rows. A
   vertex's run is found instead by filtering the tile that was fetched anyway on the endpoint
   column that ordered it, which is a predicate rather than a second request. **This is a real
   divergence from a specified thing**, and it is on this list rather than hidden in it.
4. **`chunk_size` on an edge is not a row count.** The specification defines it as one — *"the
   number of edges in an edge chunk"*, recommended 2²² — and pairs it with `src_chunk_size` so that
   a sub-table splits again by rows. Here it *equals* `src_chunk_size` and is the addressing unit:
   `by_source/tile{k}.parquet` holds every edge whose source is in vertex tile `k`, so its row count
   is the total out-degree of those 4,096 vertices and nothing bounds it
   (`crates/fossil-sinks/src/manifest.rs` says so on the field itself). Same key, different meaning
   — the sharpest edge on this page, because a reader that takes the borrowed name at its borrowed
   value gets a number instead of an error.
5. **One flat tile per orientation, and a file naming rule that is ours because there is none to
   borrow.** The reference composes `<prefix><property group prefix>chunk{k}` for vertices and
   `<adjacency prefix>adj_list/part{vertex chunk}/chunk{edge chunk}` for edges, both extensionless.
   fossil composes `<prefix>chunk{k}.parquet` and `<edge prefix><adjacency prefix>tile{k}.parquet`,
   one level, extension in the name — and carries one property group holding every column rather
   than the per-group directory the specification's prose implies. **The specification names no
   data-file path anywhere**, which makes this the clearest case the rule decides: there is nothing
   here to diverge from.
6. **`chunk_size` is a power of two, and it is 4,096.** GraphAr requires nothing of the value and
   recommends 2¹⁸ vertices and 2²² edges. The constraint is fossil's, because the address is
   `dense_id >> 12` and not a division, and the number is measured rather than recommended — on
   five million vertices over a plain HTTP origin, against requests and bytes at once, with the
   table on the corpus site's own addressing page.
7. **`iri` on the vertex info and the edge info.** The RDF type or predicate IRI, which GraphAr has
   no field for; its one escape hatch, *"extra information for the graph"*, is on the graph info
   only. It is omitted from the YAML when empty, so a non-RDF corpus is exactly the borrowed shape
   and nothing more.
8. **An `adj_lists` entry with no `prefix` has no address.** The specification's prose names a
   per-adjacency prefix and **its own worked example omits it from all three entries**. fossil
   reports such an orientation as absent rather than composing a URL from convention — conformance
   case `unaddressable`. So the specification's own example manifest reads here as a corpus whose
   adjacency nobody can address, which is the borrowing rule biting in the direction that costs us.

<Callout title="The count is a declared field">
**A row count is a field of the manifest** — `vertex_count` on the vertex info, `edge_count` on the
edge info — a decimal integer in a YAML document the reader fetches anyway to learn the prefix. Both
sit immediately before `chunk_size`, because `tiles = count.div_ceil(chunk_size)` reads in that
order.

The contrast with the thing it replaces is the whole reason it is a field and not a file. GraphAr's
count is eight bytes with no name in any specification, no declared width, no declared byte order
and nothing that checks it. A YAML integer has a width because YAML integers have one, has no byte
order because the question cannot be asked of a decimal string, and is checked against the rows on
disk — `conformance.rs` reads both declarations back off the tiles rather than off the value the
writer computed.

It is `u64` and not `Option<u64>`: **a count a reader may skip is a count a reader cannot depend
on**, and a reader that cannot depend on it is exactly the one that cannot detect the failure the
field exists for. Tiles are addressed and never listed, so a tree holding `chunk0…chunk16` is
indistinguishable from a corpus that has seventeen tiles. A hole in the middle is caught by the
addressing; **a missing tail is caught by nothing** — `apps/corpus/conformance/writer.mjs` reaches it
only sideways, through edge endpoints that point at vertices no tile holds. With a declared count a
reader knows how far the corpus goes before it opens a file. The border that makes the number worth
anything is the conformance corpus's own shape — **300 vertices in five tiles of 64, the last of
them holding 44** — because a count that divides the tile size exactly never exercises the boundary.

Landed in `c573e73`, and the count survives the layout post-pass only because the pass writes one
row out for every row it reads. That is why the check does not take the writer's word for it: the
declaration is compared against the tiles **after** the pass has re-read, renumbered, re-tiled and
deleted its input.
</Callout>

<Callout type="warn" title="What would reverse all of this">
GraphAr specifying what it presently leaves to `cpp/`: a data-file path, a count with a declared
width and byte order, and a table of vectors. On that day the eight items above stop being decisions
and become defects, and borrowing resumes where it stopped. The other trigger is the one
[discarded alternatives](/docs/design/discarded) already records against conforming to a graph
interchange format at all — **a second reader that is not ours and already speaks it** — and it is
the stronger of the two, because a specification nobody reads is not interoperability.
</Callout>

## Why write-once/read-many is not an implementation detail

A corpus is written once and read many times. That is a topology, and it is the reason two things
elsewhere in this document are possible at all.

**The whole-program checks.** [Identity is unique per type](/docs/design/identity) because a fossil
program is compiled in one piece, by one compiler, with every mapping in front of it. That check is
unavailable to any system whose parts are deployed independently — which is exactly why the one
federation system that shipped an equivalent check removed it. The check exists here because the
topology is the opposite one, and the topology is a consequence of write-once.

**The absence of concurrency in the write path.** A dataset with no concurrent readers while it is
being written does not need atomic renames, lock files, visibility protocols or a transaction log.
Those mechanisms exist to protect a reader from seeing a half-written state; when there is no such
reader, they are cost without benefit. Removing them is not a shortcut — it is declining to pay for a
guarantee the topology already provides.

## What a corpus can carry

RDF terms, quads, and named graphs. A graph is not restricted to triples, and the container is not
restricted to one graph — which is the difference between a corpus and a file of statements.

It is worth being precise about the boundary, though, because a columnar layout imposes a real one.
**A cell in a columnar file carries a value, not a term with its trimmings.** Everything that makes
an RDF literal more than a lexical form — its language tag, and in RDF 1.2 its base direction — is
information that has to be carried explicitly by the layout or it is gone at the pivot into columns.

And it is not a comfortable loss, which is why it is stated here rather than filed as a detail. Base
direction exists precisely because the first strong character of a string does **not** determine how
it should be laid out. A value returned without it is not an impoverished value; it is a value the
host will render backwards, and there is nothing in the cell that lets a downstream consumer detect
that it happened. Any part of the design that widens what a term can carry has to answer this
question first, because the answer is what decides whether a round trip is lossless.

## Where the format lives

The corpus is documented as a format in its own right — the conventions, the measurement behind each
one, and executable guards that check a corpus on disk against them — on its own site, in
`apps/corpus`. That site is written for somebody implementing a reader, and it deliberately requires
no knowledge of the language.

The division is the same one this whole document rests on. **The language is one product and the
corpus is another, and the seam between them is the artifact.** A reader with a Parquet
implementation and the specification can read a fossil corpus without any part of fossil — which is
the strongest available statement that the artifact really is the interface, rather than a
serialisation of somebody's object graph that happens to be documented.
