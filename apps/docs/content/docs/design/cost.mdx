A window that returns the right answer looks exactly like a window that returns it cheaply. That is
not a figure of speech: `openCorpus` opened every tile in the corpus on every window for as long as
it existed, answered correctly each time, and eighty-eight green tests never saw it. It was found by
someone outside the repository timing the same rectangle against two corpus sizes.

So the claims are collected here, and each one is written as a **shape** — a relationship to N —
rather than a number. A pinned number would not have caught that defect, because the number was
always correct; only the slope was wrong.

## What the obligations are

| # | obligation | shape | today |
| --- | --- | --- | --- |
| R1 | A window opens a bounded number of files | O(1) in N | met, asserted; opening a corpus is **not** |
| R2 | A window is one query per orientation | constant | met, asserted |
| R3 | A window's cost follows its answer | O(rows) | met |
| R4 | An answer names every gap in it | exact | met |
| W1 | The write path's peak is independent of the corpus | O(1) in N | **not met** |
| W2 | The declared budget encloses the whole write path | — | **not met** |
| W3 | Every stage declares what it holds | — | partial |

The reading half is nearly a system; the writing half is a budget around one stage of four.

## R1 · A window opens a bounded number of files

One rectangle covering 1% of the extent, best of three, warm, against corpora this writer produced
at `chunk_size` 4,096 with both orientations tiled. Measured from kanzo-ui with DuckDB-WASM under
`NODE_RUNTIME`, 2026-08-25.

| corpus | answer | files, before | files, now | warm, before | warm, now |
| --- | --- | --- | --- | --- | --- |
| 1,000,000 | 812 v / 7,293 e | 245 | **1** | 75.6 ms | **13.6 ms** |
| 5,000,000 | 771 v / 5,316 e | 1,221 | **1** | 1,000.8 ms | **15.2 ms** |
| 10,000,000 | 3,152 v / 34,172 e | 2,442 | **2** | 4,738.5 ms | **64.7 ms** |

Before, the vertex half was handed every tile URL and pruned with a `WHERE`; DuckDB skipped the rows
and still opened each footer. The tiles are read once per corpus now and the boxes kept.

**Cold, the obligation is still unmet, and over HTTP that is the whole story.** Driven through the
native `duckdb` CLI with httpfs against a plain file origin — ranges, a 206, no listing, no
coalescing, which is what a bucket looks like from the reader's side:

| corpus | tiles | opening it | one window |
| --- | --- | --- | --- |
| 2,000 | 1 | 10 req · 0.03 MB | 17 req · 0.21 MB |
| 50,000 | 13 | 34 req · 0.23 MB | 22 req · 0.40 MB |
| 200,000 | 49 | 106 req · 0.82 MB | 25 req · 0.39 MB |
| 1,000,000 | 245 | 498 req · 4.03 MB | 28 req · 0.42 MB |
| 5,000,000 | 1,221 | 2,450 req · 20.02 MB | 61 req · 0.89 MB |
| 10,000,000 | 2,442 | **4,892 req · 40.03 MB** | **71 req · 0.97 MB** |

**A window is bounded and opening a corpus is not.** Seventeen requests to seventy-one across a
five-thousandfold range of corpus, against ten to 4,892 — two range requests and about 16 kB per
tile, because reading a footer is a length read and then the footer. At ten million that is forty
megabytes and nearly five thousand round trips before a single vertex can be drawn.

Two O(N) sweeps became one on the way here: `extent` swept the same footers on its own, so opening a
corpus and framing it each paid for every tile. It is the union of the boxes and now reads them.

**What would meet it is a decision already on the table.** The obvious fix is to publish the boxes —
`tile, min_x, max_x, min_y, max_y`, 2,442 rows and about 100 kB at ten million. It is the wrong fix,
because the **row-group container** in
[Addressing](/docs/format/conventions/addressing) subsumes it: one Parquet file whose row groups are
the tiles has **one footer**, 496 kB at five million, and the boxes are already in it. No index to
publish, no sweep to pay, and the same bytes.

That container was costed from the writer's side and won on the per-window figure — **5.6 range
requests against 22.3** for the same tiles as separate files. This is the second number, from the
reader's side and over the wire, and it is the larger one: it does not make opening a corpus cheaper,
it **removes the O(N) term from opening altogether.** A file-per-tile corpus has `ceil(N / 4096)`
footers to find; a row-group corpus has one.

The two measurements are of different things — that one is per window and this one is per corpus —
and they point the same way, which is worth saying because they were taken a repository apart and
neither knew about the other.

## R2, R3 · One query per orientation, and cost that follows the answer

A window issues three statements: the vertices, then `by_source` and `by_target` addressed from the
tiles the vertex answer reported. That was already true of the edge half before R1 was fixed, which
is what said the addressing worked and one statement did not use it.

With R1 met, the clock follows the answer rather than the corpus: 812 vertices cost 13.6 ms at a
million and 771 cost 15.2 at five, while 3,152 cost 64.7 at ten — 4.7× the answer for 4.3× the time.

## R4 · An answer names every gap

`complete` is not "nothing was truncated", because nothing truncates. It means every edge incident
to a vertex in the answer is in the answer, and `gaps` names the orientation that was not read. On a
corpus whose `by_target` is not tiled, every window reports `dst: not-declared` and `complete: false`
— correctly, and loudly enough that a viewer counted 19–32% fewer incident edges and could say so.

## W1, W2 · The peak follows the corpus, and the budget does not reach it

`--memory-gib` is a `FairSpillPool` around `execute_graph`, and for a long time it was nothing after
it: `enrich_layout` took the run's `memory_bytes` and discarded it, so three stages sat outside the
pool and a declared 4 GiB run peaked at 8.39 GiB. The number reaches the layout pass now, and is
honoured there by **refusing** rather than spilling — `estimated_peak_bytes` over the staged Parquet
footers, checked before the first column chunk is decoded. That closes the *declaration*; it does not
close the shape below, and the two should not be confused. **The peak still grows with N, and a
refusal is what happens when it grows past what was declared.**

The whole build, `/usr/bin/time -l` over the generator plus `fossil run`, unbounded, 2026-08-25:

| N | peak RSS | wall |
| --- | --- | --- |
| 200,000 | 0.56 GiB | 3.4 s |
| 1,000,000 | 3.35 GiB | 20.7 s |
| 5,000,000 | 11.91 GiB | 154.5 s |
| 10,000,000 | **20.72 GiB** | 404.4 s |

For 1.5 GB of corpus. There is no spill path in the pass, so exceeding the machine is a failed run
rather than a slow one, which is the opposite of what [streaming](/docs/design/streaming) promises.

**The line got shallower, and that row above predates it.** The layout pass on its own was 7.22 GiB
at ten million — 0.72 per million — and is **3.80**, or 0.38 per million (0.31 at two million, 0.35
at four), after the Louvain contraction stopped building one hash table per community. The
`/usr/bin/time -l` table is the *whole* build, generator and executor included, and it has not been
re-run against the smaller pass; what changed underneath it is a layout half that now asks for less
than half of what it asked for. **Re-measuring the whole build is outstanding.**

**And the shape was never intrinsic — but not for the reason this page gave.** It said Louvain's
levels collapse at the first one, ten million vertices becoming 22,171 communities and then 2,736
and 1,365, so that the whole cost is level zero and a level-zero pass keeping only `community[u]`
would hold 40 MB against 0.41 GiB per million. Two corrections, both measured:

- **The collapse is not at level zero on the fixture the budget is calibrated on.**
  `examples/enrich_memory` at ten million and mean degree 14 goes 10,000,000 → **3,757,900** →
  8,832 → 2,081 → 1,487. Level zero stops on the 32-sweep cap without converging; the planted
  communities appear at level *one*. The 22,171 is `examples/layout_memory`, whose planted blocks are
  128 wide rather than 1,000 — a different graph, and the conclusion does not carry across.
- **The 0.41 GiB per million was not the graph.** It was `Weighted::contract`'s `vec![HashMap::new();
  k]`, one hash table per community and `k` in the millions, measured at +3.41 GiB of the +3.82 the
  step billed. That is gone and the step is 0.19 GiB per million.

What is left of the level-zero argument is real and much smaller. The graph *is* still fully
resident while Louvain runs — `read CSR + CSC` is +0.78 GiB at ten million and Louvain holds it for
all 136 s — so a pass that streamed the sorted CSR from disk instead would still save about 0.8 GiB.
That is a 20% decision rather than the 50% one this paragraph used to describe, and it is unmeasured.

<Callout type="warn" title="One row of the streaming page does not reproduce">
That page bills `community_hierarchy` at **+0.08 GiB** at ten million after the CSR landed, and
concludes *"the memory did not move somewhere else — it stopped being asked for"*. Run through
`examples/enrich_memory`, the same post-CSR code path bills it +0.39, +0.89, +1.79 and +3.30 GiB at
one, two, four and eight million — 0.41 per million, linear, and three to five times every other
phase in the pass.

What reconciles them is the measurement rather than the code. An RSS *delta* only sees a phase that
makes the process ask the OS for more, and in the full run the pass starts at 6.82 GiB with
gigabytes of freed pages in hand. In the example it starts at 0.24 G and every byte shows. **The
peak falling to 8.39 GiB is real; the sentence drawn from that row is not.**

Both figures are the old contraction's. On the current code the same example bills
`community_hierarchy` **+1.92 GiB at ten million**, 0.19 per million, and it is no longer the largest
phase of the pass — `remap adjacencies + write edge tiles` is.
</Callout>

## How a claim on this page stays true

The one capability this package asks a host for is a `query` callback, so everything a reader does
passes through one function and counting is a decorator around it rather than instrumentation
inside anything:

```ts
const counted = counting(query);          // queries, parquet paths, rows, ms
const corpus = await openCorpus(url, { query: counted });
await corpus.window(box);
counted.report();                         // { queries: 3, files: 2, rows: 3152, ms: 64.7 }
```

An obligation is then two corpora an order of magnitude apart and one comparison, which is what
`packages/graph/tests/cost.test.ts` is. It writes both with the checker's own fixture — JavaScript
against the published conventions, importing nothing of ours — at 20 and 196 tiles, and asks the
same rectangle of each: fixed ground, ten times the density.

Four assertions, and not one of them compares against a recorded figure:

- the vertex statement **never names every tile in the corpus**
- it opens the tiles its own answer landed in, and about one more — the overshoot is a tile whose
  box meets the rectangle and whose rows do not, which is geometry and not a term in N
- **the share of the corpus a window opens falls as the corpus grows**
- a window is one statement for the vertices and one per orientation

Three of the four go red when the defect is put back; the fourth does not, because it never changed
the number of statements. That is worth stating: each assertion covers a different property, and a
guard nobody has watched fail is a sentence rather than a guard.

The write half has its probe already — `FOSSIL_MEM_PROBE=1` and the two examples under
`fossil-layout` — and what it lacks is the same discipline: W1 is `peak(10N) === peak(N)`, and it is
red, and being red in public is the point of writing it down.
