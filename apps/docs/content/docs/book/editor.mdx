fossil ships a language server, and it is the same code that checks your program on the command
line. Nothing it tells you is an approximation of what `fossil check` would say.

## Switching it on

The server is one binary, `fossil-lsp`, installed alongside the compiler:

```bash
cargo install --git https://github.com/Kanzo-Tech/fossil-lang fossil-lsp
```

Then tell your editor to start it for files ending in `.fossil`. In Neovim that is an `lspconfig`
entry naming the binary and the filetype; in Helix a `[[language]]` block with
`language-servers = ["fossil-lsp"]`; in any editor that speaks the protocol, the equivalent. It reads
the program on stdin and stdout and needs no configuration of its own.

It advertises hover, definition, completion, document symbols, semantic tokens and code actions, and
every handler is a thin adapter over a `fossil-ide` free function. The browser calls the same
functions, which is why the two cannot answer differently.

## Completion

Three sources merge into one list (`crates/fossil-ide/src/completion.rs:59`), and it is worth knowing
which of them looked at your cursor.

**The shape's properties**, when the enclosing mapping's target shape resolves — your program named
its output document and the editor could read it. The entries are that shape's own
`constraints[].predicate`, each with the value type the document declares, so the list is what
`Person` requires and nothing else.

**The source's columns**, when the cursor is on a `.` inside a mapping body and the source that
mapping reads has been introspected:

```
name = User.        →  id   email   name   age
```

Each entry carries the inferred type. With no introspection there are no entries at all — the editor
says nothing rather than guessing column names.

**Every row of the standard library**, and this one does not look at the cursor. `str.trim`,
`seq.join` and `io.csv` are all offered wherever completion fires, spelled in full and carrying no
`sortText`, so your editor orders them by label and your editor's own prefix filter is the only thing
narrowing them. `seq.join` is on the list after a string, and `str.upper` is on it after a relation.

That last paragraph is a gap, not a design. Every row already carries the receiver it hangs off —
`Scalar(ScalarTy::String)` for `str.trim`, `Relation` for `seq.where`, `Namespace` for `io.csv`
(`crates/fossil-hir/src/stdlib.rs:181`) — and the bare member name beside it
(`crates/fossil-hir/src/stdlib.rs:186`). Nothing in `crates/fossil-ide/` reads either field. Filtering
by the receiver's type, and offering `trim` rather than `str.trim` once the receiver is known, is the
step that would make the list exact; the argument for why it should be is
[tooling for humans](/docs/design/tooling-for-humans), and `stdlib_completions`
(`crates/fossil-ide/src/completion.rs:81`) is the function that would change.

## Hover

Hover anywhere in a property line and you get two type blocks
(`crates/fossil-ide/src/hover.rs:120`): the type of the expression you wrote, with where it came from
— an input descriptor names the binding and the column — and, below it, the type the shape demands
of the predicate that property's key names. Two blocks because a property is a meeting of two
documents, and seeing only one of them is how you end up arguing with the checker.

The second block appears only when the shape resolves. A program that names no output document, or
one whose document the editor could not read, gets the first block and no error: the missing document
is the checker's diagnostic to report, not the hover's.

The cursor's exact column inside the property does not change the answer — hover resolves to the
whole property, so the key and its right-hand side give the same two blocks. The predicate IRI is
resolved to find the constraint and is not itself displayed, and neither is the constraint's
cardinality; if you want either, go to the definition, which opens the document at the line that
declares it.

## Go to definition

Three positions, and the first two leave the `.fossil` file entirely
(`crates/fossil-ide/src/goto_def.rs:123`):

- On the **shape name** in a mapping header, it opens the shape document, at the shape. When the
  document is not registered it falls back to the `type { … } := io.shex("…")` line that introduced
  the name — the honest degraded answer rather than nothing.
- On a **property key**, it opens the same document at the predicate the key names. `@subject` is
  deliberately not one of these: a shape declares a node's predicates, and in RDF the subject *is*
  the node.
- On a **mapping name**, it stays in the program and resolves through the open files. This is the one
  position that never left the language.

A source name and a relation name resolve to nothing today. The index behind the third case walks
only `MAPPING` nodes (`crates/fossil-ide/src/symbol_index.rs:75`), so `User` in
`User := io.csv("data/users.csv")` and `Adults` in `Adults := User.where(…)` are not in it, and a jump
from either returns no target. Both are `:=` bindings a few lines up in the same file, which is why
the gap has been survivable; it is still a gap.

## Quick fixes

Two, and both hang off a diagnostic you can already see
(`crates/fossil-ide/src/code_action.rs:53`) — there is no action that fires on a clean file.

- **Did you mean.** A column that is not a field of the row a mapping reads carries its nearest
  candidate as a structured field, not as prose in the message, so the fix replaces exactly the span
  that was wrong with exactly the name that was meant. The candidates are that row's own fields,
  which is what makes it a short list — see [when it does not compile](/docs/book/diagnostics). It is
  offered only when the caret is on the name: where the compiler recorded no span finer than the
  whole right-hand side, an edit would delete `User.` along with the typo, so none is generated.
- **Split the mapping.** A value disjunction in the shape is not supported in v0.1, and the repair is
  one mapping per branch. The diagnostic already carries that rewrite — the same header, the same
  `from` clause, the same identity, one mapping per disjunct — so the action inserts what the
  checker generated rather than regenerating it.

## Diagnostics as you type

The squiggles are the diagnostics from
[when it does not compile](/docs/book/diagnostics), at the same spans, with the same `help:` text —
folded onto the end of the message, because LSP has no field for it
(`crates/fossil-lsp/src/main.rs:735`). A diagnostic's secondary labels travel too, as
`relatedInformation`, so an error whose whole content is *these two spans disagree* arrives with both
halves rather than as one underline with no context.

An edit republishes for the file you edited. A missing required property appears against the header
the moment the body stops satisfying the shape; an unknown column appears as you finish typing it.

## In a browser

`fossil-lsp` itself is native — it is a stdio transport, and it refuses to compile for wasm32
(`crates/fossil-lsp/src/main.rs:35`). What compiles to WebAssembly is everything under it:
`fossil-ide` and the compiler crates it calls carry no engine, so the browser serves the same six
requests — hover, definition, completion, document symbols, semantic tokens, code actions — by
calling the same functions, dispatched in `crates/fossil-wasm/src/lsp_worker.rs:209` instead of over
a pipe.

Checking a program needs a parser, a shape document and the columns of a file — none of which needs a
machine somewhere else — so what this page describes is available in a page, with nothing on the
other end of it.
