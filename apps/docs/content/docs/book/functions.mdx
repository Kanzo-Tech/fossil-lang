You do not write functions in fossil. There is no syntax for it and no place to put one. What there
is instead is a library of them, and everything the language does to a value it does by calling one.

That sounds like a limitation and it is really a division of labour: the library is where the generic
machinery lives, and your program is where the decisions live.

## Passing one

Some functions take a function. `where` is the one you meet first:

The thing inside the parentheses is an expression over a row, and `where` applies it to each one.

happens to take an expression where `trim` takes a string.

## Reading a signature

The catalogue writes signatures like this:

```
trim         (text: String) -> String
split        (text: String, separator: String) -> Seq<String>
where        (rows: Relation, keep: Predicate) -> Relation
```

Inside the parentheses is what goes in, right of the arrow is what comes out. `Seq<String>` is a
sequence of strings.

**Every parameter carries a name, including the first**, and the name is what a named argument
writes to reach that position. So `str.split(x, separator = ",")` is a call and `sep = ","` is an
error naming the parameters the row actually has:

```
`str.slice` has no parameter called `begin`. It takes `text`, `start`.
```

The first parameter is the receiver — the thing to the left of the dot when you call it that way —
which is why `x.trim()` and `str.trim(x)` are one row.

`where` over a relation of `User`s gives a relation of `User`s; `where` over a relation of
`Purchase`s gives a relation of `Purchase`s. One entry in the catalogue, every source. That is why
the library is as small as it is: there is no `filter_users` and no per-format verb, because `where`
was never written against a format at all.

The signature does not say that in type-variable notation, and today it could not: the catalogue's
types are scalar, so `Relation` and `Predicate` stand for *the receiver's own* relation and a
condition over one of its rows, and `core.require` — the row that would most want a `forall T. T? ->
T` — is written `(value: String) -> String`. [The standard library](/docs/book/stdlib) says what that
approximation costs.

## Where they live

[The standard library](/docs/book/stdlib) lists every function with its signature, grouped by what it
attaches to: the operations of a relation, the operations of a string, the readers under `io`, and
the namespaces for parsing, validating, anonymising, arithmetic and the two in `core`.

Because the receiver decides the members, the **catalogue** half of your editor's completion list
after a dot is exactly the functions that apply — after a `String`, the string operations; after a
relation, the relational ones. A receiver it cannot name contributes nothing rather than the whole
catalogue, which is what it used to do. The other half of that list is not narrowed and is not yet
honest about it; [in your editor](/docs/book/editor) says which half is which.
