Every fossil program begins by naming the document that describes its output. Property names come
from there, so it is not an optional line: without it there is nothing to call a property.

Three things happen on that line. The document is read; two of its shapes are pulled into scope under
the names you chose; and from then on `Person` and `Order` are types, with a known set of properties, a
known kind of value on each, and a known number of them allowed.

The bare keys `label` and `price` come out of `sh:path shop:label` and `sh:path shop:price` exactly as
`email` and `name` come out of a ShEx triple constraint. Whichever document you write, every property
of the type you get carries the same three things: a name, a kind of value, and a count.

## Binding is by position

The names on the left are yours. They bind to the shapes **in the order the document declares them**,
never by matching what they are called. `Person` is the first shape in `shop.shex`, `Order` the
second. Call them `Buyer` and `Sale` and the output is byte for byte the same, because the IRI written
into the graph is the one in the document.

| what you write | what you get |
| --- | --- |
| as many names as the document declares | the Nth name takes the Nth shape |
| **fewer** names than shapes | a prefix binds, the rest of the document is ignored, and that is not an error |
| **more** names than shapes | the surplus binds nothing — *`Extra` is declared and bound nothing: the binding names 2 shape(s) and the document declares 1*, reported at the **use** of the name and silent if you never use it |
| the same names, after the document is reordered | the program rebinds, quietly |

The last row is the cost, and it is worth knowing the day you go and tidy a document up; shape
documents are files you version and review, which is what makes it a fair trade.

What the local name buys is the rest of your program — the header that says `from`, and the diagnostic
that has to name something — which is also what lets two documents live in one program without
arguing. A Spanish register and an English one, each with its own vocabulary:

## What a name looks like once you have it

A property key in a mapping body is a bare word: **the last segment of the predicate IRI**.
`https://shop.example/voc#email` is `email`. `http://xmlns.com/foaf/0.1/name` is `name`.

The rule is narrow on purpose. The name depends on the label and nothing else — not on how many of the
property there may be, not on what kind of value it holds, not on where it sits in the document — with
no plural-to-singular guesswork and no numbered suffix, so a small edit to a document never renames
something you were already writing.

The rename lives in your program rather than in the shape document for one plain reason: **the
vocabulary may not be yours.** `foaf:` belongs to somebody else, and a local naming problem should not
turn into an edit to a document other people share.
