title: The MCP surface
description: A dataset server, not a language server. One tool over stdio, the six verbs in one envelope, secrets that never touch argv.
---

`crates/fossil-mcp` serves the [six verbs](/docs/format/reading/verbs) over the Model Context Protocol,
against a corpus that is **already written**.

That is worth saying plainly, because the name invites the wrong reading: this is not a language
server and it has nothing to do with compiling anything. It opens a dataset, registers views over
the Parquet the corpus already holds, and dispatches a verb. **It is a dataset server**, and it
belongs to the corpus half of fossil.

## One tool, one envelope

The transport is stdio, and the surface is a single tool called `dispatch_verb`, taking two opaque
JSON values:

```json
{
  "dataset":   { "dest": "s3://bucket/prefix", "manifest_files": { "graph.graph.yml": "…" } },
  "operation": { "verb": "aggregate", "params": { "vertex_type": "Person", "group_by": "city",
                                                  "agg": "count", "limit": 50 } }
}
```

One generic tool covers all six verbs, because the `{ verb, params }` envelope is already the whole
dispatch. It is the minimal surface that is still the complete verb service; per-verb tools shaped
for a model's tool loop are a separate design with a separate audience.

## The dataset context

Three fields, and each one is a decision:

**`dest`** — where the corpus lives. A local path, or `s3://`, `az://`, `gcs://`.

**`manifest_files`** — the manifest YAMLs, keyed by dataset-relative path, passed **by value**. The
server does not go and fetch them. A host that already serves a manifest to its front end hands the
same blobs here, so the two cannot disagree about what the dataset contains.

**`secret`** — a provider-typed cloud credential: a `type` naming the storage provider and a map of
parameters. It rides the MCP message on **stdin**, never argv and never the environment, which is
the same invariant the CLI holds with `--creds-stdin`. Process arguments are world-readable on most
systems and the environment survives into every child process; stdin is neither.

## What it holds and what it does not

**No memory budget.** A budget is an input of the command that declares it, and an MCP dataset call
declares none. Reads over an existing corpus are bounded by the verbs themselves — `aggregate` is a
constant-memory grouping, `read` carries a limit, `execute_sql` carries a row cap. The budget
belongs to the [write path](/docs/format/scale), where a job either survives or does not.

**Views come from the manifest, not from a convention re-derived here.** The reader asks
`VertexInfo::prefix` for the directory the writer says it emitted into, rather than assembling a
path from what it knows about tile naming.

<Callout type="warn" title="The failure that produced that rule">
A reader here hard-coded `<dest>/vertex/<Type>.parquet` — the staged single file the layout pass
consumes and then **deletes**. When the layout pass began emitting tiles and removing the staged
file, every verb over a freshly written corpus stopped finding its vertices, and nothing went red,
because the test asserted the stale path too. Four call sites named a path that no longer existed.

That is the general shape of every failure a corpus format has, and it is why the guard
`exactly-once` asserts the staged file is *gone* rather than merely that the tiles are present: a
second, stale copy of every vertex is exactly what a reader picks up by globbing and never questions.
</Callout>

## Threading, for anyone binding it

The native executor is single-threaded by design and `!Send`, so setup and dispatch run together on
a blocking thread and only the JSON result crosses the await. The verb future never actually
suspends — the native executor returns ready values — so it is driven to completion in one poll
rather than parked on a runtime.

Nothing about that is visible to a caller, and none of it is part of the corpus format. It is here
because the alternative is a binding author rediscovering it.
