**A tile is a fixed range of 4,096 rows of `dense_id`**, and tile `i` *is* the range
`[i·4096, (i+1)·4096)`. Its address is arithmetic:

```
tile = dense_id >> 12
```

That is the entire index. There is no directory to fetch, no tile tree to walk, no listing to
perform. The tile of a vertex is a shift; the tile of its ancestor at level `L` is
`dense_id >> (12+L)`; the lowest common ancestor of two vertices is the common prefix of their ids,
which is an `XOR` and a count of leading zeros. **A reader computes every URL it wants before it
emits the first request.**

## Two questions, one arithmetic

The shift answers both things a reader asks for, and the second one is why the corpus carries the
adjacency twice:

| the question | the address |
| --- | --- |
| the vertices of a window | `chunk{k}.parquet` for each `k` in the window's runs of `dense_id` |
| the edges drawn in it | `by_source/tile{k}.parquet`, the same `k` — every drawable edge has its source on screen |
| the out-edges of `v` | `by_source/tile{v >> shift}.parquet`, filtered to `src_dense = v` |
| the in-edges of `v` | `by_target/tile{v >> shift}.parquet`, filtered to `dst_dense = v` |

The last two are a **hop**, and they are the reason both orientations are tiled. The alternative —
asking the edge relation for a neighbourhood with a recursive query — was measured in a reader at a
million vertices and **did not return in 45 seconds**, because the adjacency term materialises the
relation before the recursion starts and no `limit` on the answer bounds the cost of finding it. The
directions are separate addresses rather than one undirected one for the same reason the camera is
addressed at all: a union of two relations is a scan, and a pair of URLs is not.

Which prefix carries which direction is [declared per edge type](/docs/format/conventions/adjacency), never
conventional — `aligned_by` gives the column and `prefix` gives the URL.

## A set of tiles says what it is complete for

The second row of that table is complete for **drawing** and incomplete for **incidence**, and the
difference is invisible in the picture. Every drawable edge has its source on screen, so the
`by_source` tiles of a window are an exact superset of what can be drawn — but an edge whose
destination is drawn and whose source the window never selected is not in any of them. Measured on
20M and 40M edges, that is **19,892 edges per window at degree 4 and 39,849 at degree 8**: a layer
missing them renders identically to a complete one.

So an answer built out of tiles carries **which orientations it read**, and a reader may state
completeness only for the ones it has:

| the orientations read | the answer is complete for |
| --- | --- |
| `aligned_by: src` | every edge whose **source** is in the window — the drawable set |
| `aligned_by: dst` | every edge whose **destination** is in the window |
| both | every edge **incident** to the window |

And a missing orientation has two causes that are not the same fact, so they are not reported as
one. *The caller did not ask* is a choice — a drawing read asks for the source half and pays for
nothing else. *The corpus does not publish it* is a property of the artefact: an edge type with no
`adj_lists` entry for a direction, or one declaring the direction with no `prefix`, has tiles nobody
can address, and the answer that names it says so rather than composing a URL that 404s.

**A vertex answer already works this way**, which is where the shape comes from: it carries how many
rows matched as well as how many came back, so a truncated read cannot look like a complete one. An
edge answer that carried neither was the asymmetry.

The orientations that apply to a window are the ones whose **own `dense_id` space is that window's**.
On a self-edge both apply. On `Author authored Paper`, `by_target` tile `k` addresses `Paper`'s tile
`k` — a different set of vertices — so a window over `Author` that read it would answer a question
nobody asked. Guard: `declared-tiling` for the addresses; conformance case `cross-type` for which of
them a window may use.

## Why the camera does not ask

Pruning cannot be expressed as a predicate. That is measured, and it is the finding the whole
addressing scheme comes from.

A window of 20,000 vertices on a five-million corpus is **179 contiguous runs of `dense_id`
covering exactly 20,007 ids** — 0.4% of the corpus, with zero over-read. Those runs contain
**130,516 of 34,974,279 edges — 268× fewer** — and they return the same 120,103 visible edges. It is
an exact superset, not an approximation.

And no way of asking for it in SQL gets it:

| how the runs are asked for | cost |
| --- | --- |
| a plain join | 5 ms |
| a range join against the runs | 237 ms |
| 179 `BETWEEN … OR …` predicates | 189 ms wall, 2.3 s CPU |

Both attempts are **slower than not pruning at all**, because DuckDB evaluates the ranges per row
instead of skipping row groups. A `WHERE` clause selects rows from a table; it does not select which
bytes get read.

So the camera is addressed and the algebra is queried, and they are two different surfaces. The
camera computes a level and a set of tiles and asks for bytes — no bbox in flight, no SQL, no
database on that path. The [verbs](/docs/format/reading/verbs) answer questions and return Arrow, and they
do not draw. When a filter has to change the picture it returns **ids**, and the canvas applies them
as a mask over the tiles it already holds.

## Why 4,096

Measured on the five-million corpus served over a plain HTTP origin, counting every request that
answers, against an ideal payload of 0.6–0.9 MB per window that is flat in N:

| `chunk_size` | requests | bytes | vs ideal |
| --- | --- | --- | --- |
| 1,024 | 178 | 1.11 MB | 1.73× |
| **4,096** | **78** | **1.48 MB** | **2.31×** |
| 8,192 | 47 | 1.89 MB | 2.95× |
| 32,768 | 25 | 4.61 MB | 7.20× |
| 122,880 | 35 | 11.73 MB | 18.3× |

The two curves have no common optimum — bytes bottom out at 1,024–2,048 and requests fall
monotonically — so what chooses is `λ·β`, the bytes a link moves in the latency of one request:
32,768 in series, 8,192 with six requests in flight, **4,096 fully multiplexed**. An addressed
reader is fully multiplexed by construction, because it computes every URL before it emits the
first.

**And the byte curve is flat from 1,024 to 8,192, so the emitter is not tuned inside that band.** A
change there is not an improvement; it is noise with a `git blame` on it.

<Callout title="A power of two, and refused otherwise">
122,880 is Pareto-dominated on both curves at once — more requests *and* four times the bytes,
because a 122,880-row edge tile crosses several row groups and costs 9.4 requests. It is also not a
power of two, which forces a division where a shift does. `chunk_size` is a power of two or the
corpus does not have an address. Guard: `declared-tiling`.
</Callout>

## There is no tile tree

A tree of tiles would only earn its keep by **containing** something that does not fit in a leaf.
The one candidate was the edge that crosses tiles — hoisting it to the deepest tile holding both
endpoints — and that costs more than it saves by a wide margin
([Adjacency](/docs/format/conventions/adjacency#csr-not-lca)). With nothing to hoist, the interior nodes are
empty, and there is nothing to materialise.

**The level-of-detail pyramid is not that tree either.** Zoom does not filter; it reads a different
relation. A tile at aggregation level 3 holds super-nodes that do not exist at level 0. So each
level is its own relation, with its own `dense_id` space, its own Morton renumbering and its own
flat tiling of 4,096 rows. It is not a tree of `k` levels; it is **`k` flat tilings**, and inside
each one the address is a shift.

## Two containers, one address

A tile is a range of rows. Which container carries it is a second question, and both answers are
addressed by the same arithmetic:

- **one file per tile** — `chunk{k}.parquet`, the address in the name;
- **one file, one row group per tile** — the address is the row-group ordinal.

They are not equally cheap, and the difference is measured on five million vertices in 1,221 tiles:

| container | requests/window | bytes/window | total footer | index a reader must hold |
| --- | --- | --- | --- | --- |
| one file per tile | **22.3** | 1.40 MB | 1,150,490 B | 1.33 MB (1,221 footers) |
| one file, row groups of 4,096 | **5.6** | 1.38 MB | **496,373 B** | 675.8 kB (1 footer) |

A request is one file when a tile is a file, and a **maximal run of consecutive row groups** when it
is not: inside one file, contiguous tiles are asked for in a single byte range. The 22.3 selected
tiles coalesce into **5.6 runs**, so the file boundary is the only thing preventing the merge.
**One file per tile costs 4× the requests and does not save a byte.**

The checker classifies rather than judges, and reports which container it found. What it refuses is
*both at once*: two ways to address the same rows is one way too many, and a reader that globs finds
both. Guard: `tile-of`, checked in whichever form the corpus uses.

## The address is published, not described

Everything above is arithmetic over four manifest fields — `prefix`, `chunk_size`, `aligned_by` and
the adjacency's own `prefix` — and a reader that re-derives it from this page has copied a
convention no compiler compares against the corpus. Change a prefix or a shift and the copy composes
URLs that 404 at runtime, in a browser, with no type error and nothing red.

So the composition ships as code, in `@fossil-lang/graph`, beside the verbs and sharing nothing with
them but the manifest:

```ts
const corpus = resolveCorpus({ manifestFiles, base: '/bench/1000000' });
const { vertexUrls, edgeUrls, complete, gaps } = corpus.window({ tiles, directions: ['src'] });
```

It is **synchronous, and that is the claim rather than an omission** — no `fetch`, no connection, no
promise. The camera is addressed, not queried, and a request between the camera moving and a URL
being computable is the `viewport` verb this format does not have. It is also the whole of what
moves: bytes, tile caches, debounce, supersede-cancellation and sampling stay in whatever draws.

Three things it refuses to compose, each because the manifest does not say them:

- **an orientation the corpus does not publish** — `adjacency('dst')` is `null`, never a string;
- **a tile size that disagrees with the vertex type addressing it** — `src_chunk_size` against the
  source's `chunk_size` is checked once, when the corpus is opened, because every URL still composes
  and most of the files still exist;
- **which tiles a rectangle touches** — that comes from the per-tile `x`/`y` boxes in the Parquet
  footers, and reading a footer is a Parquet reader's job. The reader has one and hands the tile
  numbers back.

<Callout title="The alternative, and what would bring it back">
**A schema instead of a module** — publish the manifest's shape as JSON Schema and let every reader
generate its own composition. It is the smaller artefact and it is language-neutral, which is the
whole reason the corpus is documented rather than typed.

It is rejected because a schema constrains the *fields* and the failure is in the *arithmetic*: a
schema that pins `prefix` to a string cannot say that the edge tile under it is
`<prefix>tile{dense_id >> shift(src_chunk_size)}.parquet`, nor that the destination half is a
different `dense_id` space, nor that a window over one orientation is incomplete. Those are the four
things a re-derivation gets wrong.

What brings it back is the same thing that would retire the module: the addresses becoming
**derivable from the manifest by a rule a schema can carry**, so composing a URL stops being
arithmetic and becomes substitution. Three things stood between here and there, and the manifest's
declared row count is one of them delivered — `vertex_count` and `edge_count` are fields, so how far
the corpus goes is read rather than probed. The two that remain are one container and one naming
rule: nothing in the manifest distinguishes a tile that is a file from a tile that is a row group,
and a schema that cannot say which cannot say what the URL is. The conformance corpus is the measure
of the rest: while `expected.json` holds a case a schema cannot express, the schema is not the
answer.
</Callout>

The seam is tested by the question it exists to answer: **can a reader that is not fossil's open the
same corpus with only what fossil publishes?** `apps/corpus/conformance/reader.mjs` is that reader —
plain Node, no npm, no build. It has two harnesses: `verify.mjs` runs it against the same table of
addresses the module does, and `writer.mjs` runs it against a corpus `fossil run` has just written.
The second exists because the first cannot catch two readers being wrong *together*, which is what
they are whenever the convention they both copied has moved.

## The published vectors

The arithmetic ships as a formula **and a table of vectors**, because the vectors are what gets
copied.

Iceberg specifies its bucket transform as Murmur3 x86 32-bit with seed 0 — the formula, the widths,
the sign — and a table of vectors by type, of which `34 → 2017239379` is one. Searching for that
constant finds it in the tests of independent implementations that copied it. PMTiles dispatches its
Hilbert curve with a link to Wikipedia, and every port re-derives it differently.

Every value below is a border. They live in `apps/corpus/guards/vectors.json`, the guard
`published-vectors` executes that file, and these tables are rendered from it — so the documented
vectors and the executed ones are the same bytes.

The last two rows are not decoration. `2^31` is where a port that took the shift as signed gives a
negative tile; `2^53` is where a port that ran the id through a JavaScript `Number` stops being
exact. Both exceed the width a `dense_id` column carries in any corpus that has been written, and
they are published for exactly that reason — they are where a wrong implementation is still right.

`count = 4096` at `chunk_size = 4096` is the row that catches ports: that is **one** tile, and an

one empty one, and a reader that assumed at least one pays a request to be told 404. Guard:
`declared-count`.
