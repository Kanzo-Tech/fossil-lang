# ADR 0014: SC#1 cross-engine SQL parity is two-tier (automated native baseline + manual WASM harness)

**Date:** 2026-05-20
**Status:** accepted
**Decider:** Angel Iglesias
**Cite:** ROADMAP SC#1; 04-RESEARCH.md §"Validation Architecture" + Pitfall 6 (version asymmetry); plan 04-07 (SC#1)

## Context

SC#1 requires that every SQL statement the compiler generates "executes
identically (same result-set bytes) on native DuckDB 1.10502 **and**
DuckDB-WASM 1.33.x". Two forces are in tension.

First, **cost**: DuckDB-WASM ships a ~6.4 MB MVP WebAssembly bundle. Running it
in CI on every PR — instantiating the module, registering fixtures, executing
the corpus — is heavy and flaky relative to a native `duckdb` test, and the
WASM toolchain is a different dependency surface than the Rust workspace. We do
not want to gate every PR on a 6.4 MB download + WASM instantiation.

Second, **version asymmetry** (RESEARCH Pitfall 6): the native runtime is
`duckdb` 1.10502 (the bundled C++ pin) while DuckDB-WASM tracks a different
release train (1.33.x). The two engines are deliberately different versions, so
"they run the same SQL" is a claim that must be *mechanically checked*, not
assumed — a portable-SQL discipline plus a diffing harness is the only honest
way to assert byte-identical results across the two.

We considered (a) full DuckDB-WASM-in-CI per PR (rejected — cost/flakiness), and
(b) trusting SQL-text snapshots alone as a proxy for execution parity (rejected
— identical SQL text does not prove identical results across engine versions).

## Decision

We will validate SC#1 in **two tiers backed by a checked-in digest baseline**:

1. **Automated tier (every PR, `cargo test`):**
   - *Snapshot* — `fossil-codegen/tests/corpus.rs` locks the 30-mapping corpus'
     generated SQL text (CI fails on any diff).
   - *Native execution* — `fossil-runtime/tests/corpus_exec.rs` runs the
     executable subset on native `duckdb` 1.10502, asserts the ordered
     result-set bytes, AND writes the cross-engine baseline
     `crates/fossil-codegen/tests/wasm_parity/native_baseline.json`
     (`{name, sql_sha256, row_count, result_sha256}` per entry) plus a
     single-sourced `corpus_sql.json` (`{name: sql}`).

2. **Manual tier (on demand / phase close):**
   - `tests/wasm_parity/run-parity.mjs` reads the baseline + `corpus_sql.json`,
     re-runs each SQL on `@duckdb/duckdb-wasm` 1.33.x, recomputes the digests
     with the IDENTICAL serialization (rows in `ORDER BY` order, cells
     pipe-joined UTF-8, rows newline-joined, SHA-256), verifies `sql_sha256`
     first, then diffs `row_count` + `result_sha256`, and exits non-zero on any
     mismatch.

The digest serialization is documented in both `corpus_exec.rs` and the harness
README so the Rust producer and the JS consumer stay byte-for-byte in sync. The
corpus SQL is restricted to portable constructs (`read_csv_auto`,
`CAST AS VARCHAR`, `ORDER BY`, `GROUP BY`, `UNION`, `DISTINCT ON`) so the two
engine versions agree.

## Consequences

- **Per-PR cost stays native-Rust-only.** The expensive WASM run is a documented
  manual phase-close command (`cd tests/wasm_parity && npm install && node
  run-parity.mjs`) whose PASS is recorded in the Phase 4 SUMMARY (plan 04-08).
- **The parity claim is mechanized, not asserted.** The baseline is a real
  artifact checked into the repo; the harness is a real, runnable diff (verified
  PASS on all executable entries during plan 04-07), not hand-waving. A future
  divergence between the native and WASM engines surfaces as a concrete per-entry
  digest mismatch.
- **Single-sourced SQL.** `corpus_sql.json` is regenerated by the native test, so
  the harness can never run stale or hand-copied SQL — it always diffs the exact
  text the native tier executed (guarded by the `sql_sha256` pre-check).
- **Maintenance:** when the corpus SQL or fixtures change, the native test
  rewrites the baseline (a reviewable diff) and the harness must be re-run at
  phase close. The DuckDB-WASM npm pin (`latest` ≈ a 1.33.x dev build until a
  1.33.x final ships) is documented in the README; bumping it is a one-line
  change re-validated by re-running the harness.

## Alternatives considered

- **Full DuckDB-WASM execution in CI per PR.** Rejected: ~6.4 MB bundle +
  WASM instantiation per run is slow and adds a second toolchain to the
  hot path; the value (catching a rare cross-engine divergence) does not justify
  the per-PR cost. The manual tier captures the same evidence at phase close.
- **SQL-text snapshots as a parity proxy.** Rejected: identical SQL text does
  not prove identical *results* across two different engine versions; the digest
  baseline + WASM re-execution is what actually closes the SC#1 claim.

## Amendments

- **2026-05-23 (ADR-0025):** The PLAYGROUND-side `@duckdb/duckdb-wasm` pin is now
  exact `1.32.0` (the last fully-stable npm tag; `1.33.x` is `dev`-only at the time
  of writing). The PARITY HARNESS (`tests/wasm_parity/package.json`) retains the

  train, and the digest baseline catches any divergence at phase close. The
