Every fossil program begins by saying what it produces: the types its mappings write, each with its
properties. Property names come from there, so it is not an optional line: without a type there is
nothing to call a property. A type is **imported** from a shape document somebody maintains, or
**declared** in the program itself; below the parser the two are the same thing.

<Program src="shop/shop.shex" title="shop.shex" />

<Program src="shop/shop.fossil" region="shapes" title="shop.fossil" />

Three things happen on that line. The document is read; two of its shapes are pulled into scope by
their names; and from then on `Person` and `Order` are types, with a known set of properties, a known
kind of value on each, and a known number of them allowed.

SHACL is the other half of the same door — a different reader, the same program:

<Program src="catalogue/catalogue.ttl" title="catalogue.ttl" />

<Program src="catalogue/catalogue.fossil" title="catalogue.fossil" />

The bare keys `label` and `price` come out of `sh:path shop:label` and `sh:path shop:price` exactly as
`email` and `name` come out of a ShEx triple constraint. Whichever document you write, every property
of the type you get carries the same three things: a name, a kind of value, and a count.

## Importing by name

A name between the braces is the **local name** of a shape the document declares — the last segment
of its IRI, so `shop:Person` and `<https://shop.example/voc#Person>` are both `Person`. `as` gives it
another name in the program, and the IRI written into the graph is still the document's:

<Program src="declared/declared.fossil" region="import" title="declared.fossil" />

`declared.shex` declares `Region` and then `Place`; the import takes `Place`, wherever it sits, and the
program calls it `City`.

| what you write | what you get |
| --- | --- |
| a local name the document declares | that shape |
| `Place as City` | the shape `Place`, called `City` in the program |
| a name the document does not declare | an error listing the ones it does — *`Town` is not a shape `declared.shex` declares — it declares `Region`, `Place`* |
| a name two of its shapes share | an error naming both IRIs; declare the type instead |
| the same names, after the document is reordered | the same program |

The renaming is also what lets two documents live in one program without arguing. A Spanish register
and an English one, each with its own vocabulary, the English one's `Person` renamed:

## Declaring the type

When the vocabulary is yours, the type can be written in the program instead — a name, its fields,
their types, and every IRI, whole, in a string: the type's above it, each field's on the field's line.

<Program src="declared/declared.fossil" region="declaration" title="declared.fossil" />

A field's type is written as the checker prints it. A primitive — `String`, `Integer`, `Float`, `Bool`,
`Date`, `DateTime`, `Time`, `GYear`, `AnyUri` — is exactly one value of it; `Option<T>` is zero or one;
`Seq<T>` zero or more; and `Ref<City>` is a reference to a node of the type `City`, declared or
imported, which is an edge. The count is said once, outermost, so `Option<Seq<T>>` is refused rather
than read as one of the two things it could mean.

A mapping that produces a declared type is checked exactly as one that produces an imported shape —
a required field never written, a key the type does not declare, a value of the wrong type — and the
graph cannot tell them apart:

<Program src="declared/declared.fossil" region="mappings" title="declared.fossil" />

There is no base IRI and no prefix: a missing `@iri` is an error, so a name nobody wrote never becomes
an IRI. [Types declared in the program](/docs/design/declared) argues the form.

## What a name looks like once you have it

A property key in a mapping body is a bare word: **the last segment of the predicate IRI**.
`https://shop.example/voc#email` is `email`. `http://xmlns.com/foaf/0.1/name` is `name`.

The rule is narrow on purpose. The name depends on the label and nothing else — not on how many of the
property there may be, not on what kind of value it holds, not on where it sits in the document — with
no plural-to-singular guesswork and no numbered suffix, so a small edit to a document never renames
something you were already writing.

## When two of them collide

Vocabularies mix, and two of them can perfectly well end in the same word:

<Program src="errors/shape/name-collision/shape.shex" title="shape.shex" />

`shop:name` and `foaf:name` both want to be called `name`. fossil does not pick, and it does not
number them. It stops, and it names both IRIs:

<Program src="errors/shape/name-collision/expected/diagnostic.txt" title="program.fossil" />

The repair is to [declare the type](#declaring-the-type) in the program rather than import it, so
that each field writes its own name beside its IRI and two IRIs ending alike are two fields with two
names — `name` and `handle` above, `schema:name` and `shop:name`.
