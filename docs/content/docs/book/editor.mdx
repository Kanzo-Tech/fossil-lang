The editor is a browser one. The compiler is built to WebAssembly (`@fossil-lang/wasm`), and
`@fossil-lang/codemirror-fossil` turns its answers into CodeMirror 6 extensions — one call,
`fossil(program, options)`, handed to whatever editor the host already has:

```ts
import { fossil } from '@fossil-lang/codemirror-fossil';
import { open } from '@fossil-lang/wasm';

const program = await open('hello.fossil', { host, text });
const extensions = fossil(program, { onNavigate: (target) => console.log(target) });
```

There is no native language server. One existed, and why it went and what would bring it back is on
[discarded](/docs/design/discarded).

## What it answers

| you ask for | and it answers |
| --- | --- |
| a property key, in the body | the target shape's own predicates, each under its last segment, with the full IRI as the entry's detail |
| a column, after `Source.` | the fields the host read off the source with DuckDB-WASM, each with its inferred type |
| a member, after any other dot | only the catalogue rows that receiver has, spelled bare: `where`, not `seq.where` |
| a name, away from any dot | every row, spelled in full, because there is no receiver to narrow by |
| hover, anywhere in a property | the type of what you wrote and where it came from, and the type the shape demands of that predicate |
| go to definition | the shape document at the shape, the document at the predicate, a mapping, or the `:=` binding that introduced a name |
| quick fix, on an unknown column | Replace with… — the nearest field of that row, swapped into exactly the span that was wrong |
| quick fix, on a disjunctive shape | Split mapping… — one mapping per ShEx `OneOf` disjunct, as the checker already generated it |
| diagnostics as you type | the diagnostics of [when it does not compile](/docs/book/diagnostics), at the same spans, each with its code and `help:` under the message |

No quick fix fires on a clean file: both hang off a diagnostic you can already see, and both travel
on the checked row as data — `didYouMean` and `suggestion`. And hover's second block appears only when
the shape resolves — a program that names no output document gets the first block and no error,
because the missing document is the checker's diagnostic and not the hover's.

Four things narrow the list further than you might expect, and each is deliberate:

- **A property key is offered only in key position** — an identifier the grammar lets a key go in.
  `str.trim` cannot be a property key, so no catalogue row is offered there either.
- **A receiver that is an expression resolves nothing.** `User.email.trim().` has a `)` to its left
  and no name to ask about. Nor does a binding reached through a derivation, or a join alias.
- **A source the host could not read is not introspected.** It is a warning at its `io.csv(…)` under
  the code of what stopped it — `source/not-found`, `storage/unreachable` — with no columns.
- **A shape document open beside your program is not checked as one.** A URI some `io.` row reads is
  an input, and an input is not drained — without that rule the parser blames a perfectly good
  `ShExJ` file for every complaint it has.

## One set of answers, not a protocol

The wasm workspace is not a language server and has no wire. A page that already calls the checker
in-process should not have to stand up an LSP client, an id table and a second copy of every buffer
to ask what type is under a cursor — so check, hover, completion and definition are plain methods on
the workspace, each a `fossil-ide` free function underneath. Two rules fall out of that and both are
enforced rather than asserted: those methods take a *shared* borrow, because none of them mutates and
an editor asks at three different rates; and every one of them owes the caller's current text, because
they answer about the last edit that was pushed.

Checking a program needs a parser, a shape document and the columns of a file. None of those needs a
machine somewhere else, so all of it is available in a page with nothing on the other end of it.

A diagnostic's secondary labels carry the file each one is in, so a label pointing into the `.shex`
lands on that file — which is what makes the two-file report an editor feature and not only a terminal
one.
