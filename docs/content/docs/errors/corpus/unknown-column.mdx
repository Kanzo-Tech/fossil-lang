---
title: Not a column of this table
description: "`corpus/unknown-column` — a scan's projection or filter names a column the table does not declare."
---

A scan names columns in two places — `select`, and the columns its `filter` compares — and each must
be one the table declares in `fossil.json`. Here neither `nope` nor anything like it is a column of
`Person`:

```ts
corpus.scan({ table: 'Person', select: ['dense_id', 'nope'] });
corpus.scan({ table: 'Person', filter: { column: 'nope', op: '=', value: 1 } });
```

```text
Person does not declare nope — its columns are dense_id, subject, name, x, y
```

A host sees `data: { table, column, columns }`: the table, the first column that is not declared, and
every column the table does declare, in manifest order. It is thrown synchronously by `scan`, when the
scan is built — by the projection check, or by the filter binder for a leaf comparison or for the
two position columns a `bbox` expands to.

## Why fossil refuses it

The manifest declares each table's columns with their types, and the filter binder needs those types
to bind a comparison correctly ([one door](/docs/design/one-door)). A column it does not know has no
type to bind against, and a projection of it would reach the engine as a statement over a column that
does not exist and come back as the engine's error, with no list of what was there. Refusing before
any statement is sent keeps the scan's failure a value with the alternatives in it.

## How to repair it

- **Use a name from `data.columns`**, or from the table's `properties` in `corpus.manifest`.
- **Columns are matched exactly.** The names are the manifest's, which are the writer's, not the
  property IRIs.
