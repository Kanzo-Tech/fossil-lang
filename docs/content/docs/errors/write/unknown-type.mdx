---
title: A relation names a missing vertex type
description: "`write/unknown-type` — the graph handed to the writer has a relation whose endpoint type has no vertex table."
---

The writer lays out the graph the executor materialised: one table per vertex type, one per
relation. Before it does, it resolves each relation's source and destination type to a vertex table,
and one of them has none:

```text
relation `Review_author_Person` references vertex type `Person`, which has no table
```

`data.relation` is the edge table's name, `<Src>_<label>_<Dst>`, and `data.vertex_type` the type it
could not find.

## Why fossil refuses it

An edge is a pair of `dense_id`s, and a `dense_id` is a row of a vertex table. An edge table whose
endpoint type has no vertex table would point into nothing — `fossil.json` would declare an endpoint
that `references` a table the corpus does not have, and no reader could resolve it. The writer checks
this before writing a single file. See [the corpus](/docs/design/corpus#one-graph-one-id-space) for
why endpoints are ids in one shared space.

In the executor as it stands, the vertex types are exactly those some mapping emits, and an edge is
built by joining against the vertex tables of both endpoint types — a join that fails, as
[`engine/failed`](/docs/errors/engine/failed), when one of those tables does not exist. So a program
run through the executor stops before the writer sees such a relation. This code is the writer's
own guard on the graph it is given.

## How to repair it

- **Make sure the type is emitted.** If the destination type of a relation has no mapping, no
  vertex of that type exists and no edge can point to it. Add a mapping that emits it.
- **If the program does emit the type**, the graph fossil built is inconsistent, and that is
  fossil's fault rather than yours. Report it, with the program, as you would an
  [`internal/bug`](/docs/errors/internal/bug).
