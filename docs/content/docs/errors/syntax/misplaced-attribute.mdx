---
title: An attribute in the wrong place
description: "`syntax/misplaced-attribute` — a known attribute written where it does not belong: `@subject` outside a mapping body, `@iri` above an import or with no declaration under it, or `@iri` in a mapping body."
---

fossil has two attributes, and position decides which one a line may hold. `@iri("…")` goes above a
`type` declaration and before each of its fields; `@subject` is the first line of a mapping body.
Written anywhere else, the attribute is refused, and the message names it and the place:

```fossil
@subject = "https://example.org/person/{Users.id}"
type { Person } := io.shex("person.shex")
```

```text
syntax/misplaced-attribute
  × `@subject` does not belong at the top level
  help: the attribute at the top level is `@iri("…")`, above a `type` declaration. `@subject =
        <expr>` is the first line of a MAPPING BODY — it assigns the identity of the rows a
        mapping writes, and outside one there are no rows.
```

The whole line is taken by the refusal, so the binding under it still parses and nothing else is
reported about it. There are five places it is reported:

- **At the top level**, any attribute but `@iri` — usually `@subject` written outside its mapping,
  as above.
- **Above a `type { … } := …` import**: `` `@iri` does not belong above a `type` import ``. An
  imported type takes its IRI from the document that declares it.
- **An `@iri` with no declaration under it**: `` `@iri` does not belong anywhere but above a `type`
  declaration ``. The next line has to be the `type Name` it names.
- **Before a field of a declaration**, any attribute but `@iri`.
- **In a mapping body**, any attribute but `@subject`: `` `@iri` does not belong in a mapping
  body ``, with the help *the only one is `@subject = <expr>`, the mapping's identity; `@iri` goes
  above a `type` declaration and before each of its fields*. The property is not written.

## Why fossil refuses it

Both attributes lex as the same token, and the position is what gives each its meaning. An `@iri`
names the IRI of the type or the field written after it, so it means nothing without one.
`@subject` assigns the identity of the rows a mapping writes, and the row is introduced by the
mapping's header — outside a body there is no row for it to read ([mappings](/docs/book/mappings)).
The `@` exists to mark the language's own slots apart from the property names a shape declares
([identity](/docs/design/identity)), so an attribute in the wrong slot is a known name in the wrong
place, not an unknown name, and the message says so rather than reporting an unexpected token.

## How to repair it

- **`@subject` outside a body**: move it into the mapping it identifies, as the first line under the
  header — `@subject = "https://example.org/person/{Users.id}"`.
- **`@iri` above an import**: delete it; the document already says what the type's IRI is. To write
  the IRIs yourself, declare the type instead ([Types declared in the program](/docs/design/declared)).
- **`@iri` with no declaration under it**: put `type Name` and its fields directly under it.
- **`@iri` inside a mapping body**: a property's IRI is its field's, in the declaration of the type
  the mapping produces, not in the body.
