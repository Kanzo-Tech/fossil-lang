---
title: One engine in the compiler
description: The compiler runs on DataFusion and links no database. Why wasm32 is the reason rather than a preference, what holds it, and why the corpus read path keeps DuckDB on purpose.
---

fossil compiles to relational algebra and something has to execute it. Two things did: DataFusion in
`fossil-df`, and DuckDB — bundled, compiled from C++ — across the layout pass, the engine and the
hosts. **The compiler runs on DataFusion; DuckDB leaves the compiler and stays in the hosts.** The
argument is four sentences:

1. **wasm32 is the reason, not taste.** *fossil is a compiler consumed as a WASM library* was true of
   `fossil-wasm` and false of the layout pass and the engine, and one dependency is what made it half
   true. Both `compile_error!` tripwires named bundled DuckDB.
2. **Keeping it is not free.** `libduckdb-sys`'s build script is **98.14 s of a 165 s cold build**,
   59 % of the wall clock, because `features = ["bundled"]` compiles DuckDB from C++.
3. **`deny.toml` is the ratchet.** `cargo deny check bans` denies both engines workspace-wide and
   names the crates permitted to wrap each, so adding a name is the review the rule exists to force.
4. **The read side is untouched**, deliberately — the last section.

## Where each engine is reachable from

Measured 2026-08-25 with `cargo tree -e normal -i <engine> --workspace`, the authority here and never
prose.

| crate | reaches `duckdb` | `wasm32` | what it is |
| --- | --- | --- | --- |
| `fossil-introspect` | **directly** | no | the `DESCRIBE`, and the credentials that reach a cloud source |
| `fossil-lsp` | via `fossil-introspect` | no | a host: it checks a program against the columns it reads |

**There is no native write host** ([discarded](/docs/design/discarded#the-tooling) says why and what
brings one back). The one host that writes is `fossil-df-wasm`, in a browser tab or in Node, so the
compiler and the write path are both the wasm32 build and neither links a database. **DuckDB is still the engine that `DESCRIBE`s**: natively
in the language server, and as DuckDB-WASM in a browser editor.

## How DataFusion reaches storage

Through `object_store`, which is DataFusion's own IO: `fossil-storage` turns each credential a host
vends into a store, routed by the longest prefix that covers a path and renewed before it expires,
and the executor registers those stores. The browser reads a cloud source by range requests and
writes its output through the job's store — measured 2026-09-29 in Chrome against MinIO with
credentials keasy vended: a ranged GET, a PUT, a three-part multipart upload, and a 403 outside the
prefix. A host with no storage hands the executor `InMemory` stores, and the run
cannot tell.

## Why this does not reopen "unifying the two execution engines"

[Unifying the two execution engines](/docs/design/discarded) is a discarded alternative, and it is a
different decision from this one rather than the same one taken twice.

That row is about the corpus **read** path, where `@fossil-lang/corpus` creates views in TypeScript
and the host's DuckDB-WASM runs every read. Putting DataFusion there adds a wasm build of several megabytes to
a path that loads none, and loses the range-request file system that makes reading a corpus over
plain HTTP work at all. Still rejected.

This page is the **write** path, and it asks the compiler to stop *containing* an engine rather than
asking any consumer to stop using one. The host brings the engine to the read side, which is what the
[host boundary](/docs/design/three-hosts) says everywhere else. What it buys the catalogue is one
dialect: a function's lowering is one SQL template rather than one per engine.
