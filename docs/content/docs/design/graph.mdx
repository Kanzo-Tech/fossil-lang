A fossil program produces a **graph**: a property graph written as columnar files, with the
mapping that says what its tables mean as RDF. Not a database to connect to, not a stream to
consume, not an endpoint. Files. The graph is an
[Apache GraphAr](/docs/design/graphar) graph — YAML information files and Parquet chunks — and
`mapping.ttl`, laid out as [/docs/format](/docs/format) specifies.

**The word is *graph*** (owner decision, 15 October 2026). What a run writes was called a corpus while its
format was fossil's own, and it is an Apache GraphAr graph now, so `GraphFile`, `memory://graph/`,
`SinkRef::Graph` and the pages that say what a run writes say graph; the in-memory location of a
run, `memory://corpus/`, was a consumer-visible string and changed with them. *Corpus* is kept where
it is a different thing: the body of programs the documentation and the tests run
(`docs/programs/`), and the names of what was deleted (`@fossil-lang/corpus`, `corpus.bnf`), which a
page cites by the name it had. **What would reverse it:** nothing about the word; a consumer that
cannot edit a string would, and there is none at `0.x`.

A reader opens the graph document and reads the tables it names — from a local path, an object
store, or a plain web server. **There is no service in the path**, so no query language between
reader and data beyond the engine the reader already has, no process to keep alive, no writer version
to match.

## Files, and the one that commits them

```
<dest>/
  fossil.graph.yml                                          written last
  <Type>.vertex.yml, <Src>_<label>_<Dst>.edge.yml           one per type and per relation
  vertex/<Type>/<group>/chunk0, vertex/<Type>/vertex_count
  edge/<Src>_<label>_<Dst>/ordered_by_source/…              adjacency, offsets, counts
  mapping.ttl                                               RML-Core
```

`fossil.graph.yml` names every information file, and each of those names its property groups, its
types and its prefix. It is written **after** every other file, so its presence is the commit: a
directory without it is a write that did not finish, and a reader that finds it can trust every path
it names. GraphAr defines no commit; this is fossil's. The shape is `graphar_info::GraphInfo`, built
by `crates/fossil-df/src/layout.rs, layout`, and [/docs/format](/docs/format) specifies the files for
a reader who has none of this repository.

**Nothing is computed from a path that the information files do not give, and no path is listed.** A
reader composes each path from a `prefix` and a chunk number as GraphAr's libraries do. The constraint
that forced the old arithmetic addressing — **you cannot list a directory over HTTP** — is met by the
YAML naming every group and the count files naming every size.

**What would reverse it.** A table too large to be one chunk. Then `chunk_size` is set below the row
count and a table is several chunks; a reader's views already read every chunk, and the rule — named,
never listed — does not move.

## One index per type, and the global id is the reader's

Every vertex has an index within its type, `0..count−1`, and an edge is a pair of indices into the
types it joins. The executor still numbers every vertex of the graph `0..V−1` in a `dense_id`; the
writer subtracts the type's first id, so the files carry GraphAr's per-type index and nothing global.
A viewer's buffer index is the **global id**, which is arithmetic over the types
([identity](/docs/format/conventions/identity#the-global-id-is-the-readers-arithmetic)): the prefix sum of the
counts before a type, in `graphar_vertex_types.ordinal` order, plus the index.

The types take their order from [the order of shapes](/docs/design/shapes#the-order-of-shapes), and
inside a type the indices follow the subject. Every table is written sorted by its key. The order
carries no geometry: [where a vertex is drawn](/docs/design/position) is the view's choice.

**What would reverse it.** A reader that has to address a subset of the graph smaller than a type by
arithmetic on ids — which is what the Hilbert order the writer used to number in bought, and only the
deferred [cells](/docs/design/later/cells) used it. Or a reader that needs global ids in the files
with no query between it and them, which then gets a `dense_id` property beside GraphAr's index.

### A reader is handed the subject IRI, because an address is not something to key on

A lookup by identity is `WHERE subject = ?`, the IRI. The alternative is the index, and it is the
cheap one. It is refused because **the index is an address**: a new subject renumbers every vertex
after it in its type, so an index held anywhere outside the graph names a *different vertex* after
the next write. A bookmark, a selection, a link from another system and a row in somebody else's
database all key on something, and an address is not something to key on.

The information files say which property is the identity — `is_primary: true` on `subject`, first in
the group of every vertex type — so a reader keys on the field rather than on a column name it was
told.

What would reverse it is a graph whose ids survive a rewrite — a stable id property written beside
the address. Nothing writes one, and adding one is a format change and not a reader change.

## The artifact is the API

The stance follows the table formats — Iceberg, Delta Lake, Lance — where a manifest plus a set of
files is the interface, *many* engines read the same table, and **none of them is the contract**. A
fossil graph is plain Parquet and YAML: `read_parquet` on a path the information files name is a
whole reader, and [reading one without fossil](/docs/format/reading/without-fossil) is the recipe.
Here the contract is not even fossil's: it is Apache GraphAr's, and a reader of any GraphAr graph
reads this one.

**Two implementations before a format change, not after** — the Arrow rule. Parquet is the warning:
thirteen years of unwithdrawable files and a reference implementation that became normative without
anyone deciding it. The two here are `graphar-parquet`, which writes, and `@kanzo-tech/graphar-duckdb`,
which reads, and neither is a fossil crate.

<Callout type="warn" title="One clock, running one way">
**If a graph reaches a reader outside the release that wrote it, the option is gone.** Until then
the format changes in place, as the next section says; the day a third party reads a graph, the
conventions fossil adds to GraphAr's start to mean a contract.
</Callout>

## One format, changed in place

The format has no version string of its own. A fossil graph is identified by `fossil.graph.yml` —
graph `name: fossil`, `version: gar/v1` — with `mapping.ttl` beside it, and the only version fossil
owns is the `version: 1` inside `fossil:stats`. **The format changes in place: a writer and the
reader that reads what it writes ship in one release**, and no reader branches on which writer wrote a
graph.

The reason is who reads a graph. Every reader of one is `@kanzo-tech/graphar-duckdb` or a
GraphAr reader, released apart from fossil, and the one host — keasy — takes the writer and the
reader together. A second format string would be a branch in every reader to protect a reader that
does not exist, and an old reader kept alive beside a new one is the backwards compatibility the
products built on fossil have ruled out.

A change that only adds — a key a reader may ignore, an optional property — leaves every graph already
written readable by the new reader. A change that would make an older graph unreadable is paid for by
**writing the graphs a host keeps again**, which costs a run because a graph is a function of its
program and its sources, and never by a reader that knows two layouts. Where a non-additive change to
a fossil convention records itself is a design question: the candidate is `extra_info` keyed by a
namespace IRI, never by a fossil word.

**What would reverse it:** a reader outside the release train — a third party's, or a graph kept and
read by a reader older than the writer that wrote it — that must keep reading every graph. Then the
version rule is Delta Lake's ([discarded](/docs/design/discarded) carries it): a field a reader may
ignore stays in the version, anything else raises it, for the graphs that use it.

## The vocabulary is GraphAr's, and SQL/PGQ's is declared nowhere

The graph names its tables the way GraphAr does — a vertex *type*, an edge *type* with a `src_type`,
an `edge_type` and a `dst_type` — because that is the vocabulary of the format a reader opens it with
and of the libraries that write it. SQL/PGQ's `CREATE PROPERTY GRAPH`, which the earlier manifest
borrowed the names of, is not declared: nothing in fossil issues a graph query, the door attaches
views and every read is the host's SQL, and DuckPGQ — the extension that would run `GRAPH_TABLE` — does
not load in DuckDB-WASM 1.5.x, the engine a browser reader has. A traversal is SQL over
`_graphArSrcIndex` and `_graphArDstIndex`, written by whoever needs it.

**What would reverse it.** A host engine that runs SQL/PGQ where the reader runs. Then the attaching
reader issues the `CREATE PROPERTY GRAPH` the information files already describe, and nothing in the
format moves. The alternatives are [discarded](/docs/design/discarded#the-graph), with what would
bring each back.

## The width of an address, and what actually runs out first

The executor's `dense_id` is a `u32`, and a reader's global id is cast to `UINTEGER`, which puts a
hard ceiling of **4,294,967,295 vertices in one graph** — every type together, since the id space is
a sum — and the question the number invites is whether that ceiling is close.

**It is not close, and what is close is something else.** The whole write at ten million vertices
took **404.4 s** on a 14-core machine with 48 GiB, so 2³² vertices is on the order of two days of
wall clock — and the wasm writer, the one there is,
[refuses long before that](/docs/design/three-hosts#what-the-wasm-writer-holds-and-how-it-says-no):
its budget is 2 GiB, and a `shop` graph of a million people and three million orders is over it. The
width is not what stops a graph. Past it the executor refuses by name, `run/too-large`, where it
numbers the ids.

The cost of the other choice is on the column every read takes, and it is in memory more than on
disk. GraphAr's index is `int64`; delta-encoded as the writer writes it, it costs 1–3% more on disk
than a 32-bit one, but a reader that does not cast it back holds twice the Arrow: 32 MB instead of
16 MB for two million edges ([the graph as Apache GraphAr](/docs/design/graphar) has the
measurement). So the reader casts the global id to `UINTEGER`, and the Arrow stays at 16 MB.

### The contiguous `0..V−1`, and the price of keeping it

The other half of the same commitment is contiguity, and it is the convention a writer is most
tempted to trade. The temptation is concrete: the writer assigns ids after holding every batch, and
handing each partition a **preassigned range** removes that — at the price of holes wherever a
partition does not fill its range. A hole in a type's indices makes the reader's prefix sum
non-injective, and `attachGraph` refuses such a graph as `invalid`.

Both exits were priced on the ten-million graph before any code was written, and neither is taken.

- **How many holes.** The split is a hash's, not the data's: fourteen partitions on `subject` come
  out within **0.526%** of each other. A quantum sized to the largest leaves **35,200 holes, 0.35% of
  V** — but that quantum is known only *after* the run. The one a writer can pick beforehand is
  source rows over partitions, and the dedup collapses 8.1 rows into one: **71,027,072 holes, 710% of
  V**.
- **What compacting them costs.** **9.6 s and 3.72 GiB**, against a whole write of 404.4 s and 20.72
  GiB — 2.4% of the wall clock standing alone, with output byte-identical to compacting the gapless
  numbering.
- **And the premise did not survive the measurement.** Holding the batches is not where the peak
  comes from: the sort is **13.72 GiB** and the aggregate beneath it **13.85**, and that term is the
  dedup, which no range scheme touches.

The two harnesses were `dense_id_ranges.rs` in `fossil-df`'s examples and `compaction_pass.rs` in
`fossil-layout`'s, at `ac1801d4`. **So the convention stays, and the reason it stays is the third
bullet rather than the first two.**

## Why write-once/read-many is not an implementation detail

[Identity is unique per type](/docs/design/identity) because a fossil program is compiled in one
piece with every mapping in front of it — a check unavailable to any system whose parts deploy
independently, which is why the one federation system that shipped an equivalent removed it. And
atomic renames, lock files, visibility protocols and transaction logs exist to protect a reader from
a half-written state; with no such reader they are cost without benefit. The one ordering the writer
keeps is the graph document last, and it is the only one a reader could observe.

## The camera has a renderer, and it is not fossil's

The door does not draw, which leaves one thing unstated: *something* has to put a million points on a
screen, and fossil does not ship it. What draws is `@kanzo-tech/graph`, a WebGL canvas over
cosmos.gl, and it is the only viewer. **The view owns the picture and every policy over it; fossil
owns the bytes and the files that name them.**

A graph is drawn whole, every vertex and every edge, at a place the view chooses
([where x and y come from](/docs/design/position)). At two million edges the read was measured in
DuckDB-WASM, one thread, a local file: `src` and `dst` to **16 MB of Arrow in 51–127 ms**. The tiled
read it replaced is on [the tiled graph](/docs/design/later/graph-tiles), and what brings it back is
a graph that does not fit the tab, measured.

## Conformance reads the bytes with an engine nobody here wrote

The files are checked by engines nobody in this repository wrote. `Kanzo-Tech/graphar`'s CI opens
a graph fossil writes with GraphAr's own C++ and PySpark readers, and fossil's tests read the
Parquet back with native DuckDB through the information files, and compute the mapping's triples with
`rml::sql` over the same files (`crates/fossil-df/tests/mapping.rs`). **An assertion there can only be
satisfied by agreeing with the bytes**, never by agreeing with another implementation of the same
arithmetic — the gap through which GraphAr's fourth implementation landed green and wrong. What the
tests cannot prove is what the engines cannot see: a graph with a `langString` property is not opened
by GraphAr's C++ and Java readers at the revision read ([the datatypes](/docs/format/conventions/datatypes)).

## A multi-valued property is a property of its owner

A property a shape declares `*` or `+` is **a property of the vertex type that owns it, with
`cardinality: set`**, a list in the chunk; a language-tagged one is a list of `langString`. The vertex
row carries it and nothing else is written. It is the form GraphAr has a slot for, and the mapping's
logical source unnests the list once, so the standard reader still reads one cell as one term at the
point where the term is made ([the mapping](/docs/format/reading/rdf#a-multi-valued-property)). The
form it replaced, a table of its own with a row per value, and the other forms not taken, are on
[what was discarded](/docs/design/discarded#the-graph-as-apache-graphar), with what brings each back.

## The graph does not say what it was derived from

A table's lineage — `derived_from`, PROV-O's `prov:wasDerivedFrom` — is not written. Nothing in
kanzo-ui or keasy reads it, and the graph is a function of its program and its sources, which a host
keeps. The executor's `Graph` still computes it from the MIR DAG
(`crates/fossil-df/src/plan.rs, derived_from`), so the first reader of it has the value to hand.
**What would reverse it.** A reader of lineage: then it is PROV-O when an RDF reader appears, or an
OpenLineage `RunEvent` if the reader is a Marquez or a DataHub, generated by `describe` and never
passed through; column-level lineage, the `ColumnLineageDatasetFacet`, is the next step and would need
the `ColRef`s behind each property. Both are [discarded for now](/docs/design/discarded#the-graph),
with what brings each back.

## What the reader's relations are named

`attachGraph`'s relations are spelled as GraphAr spells the facts: `graphar_vertex_types`,
`graphar_edge_types`, `graphar_properties`, `graphar_extra_info` and `graphar_chunks`, with
`ordinal` and `count` as the information files order and size them
([reading a graph without fossil](/docs/format/reading/without-fossil)). The seven-column triples
relation `rml::sql` makes of the mapping names a term's parts as SPARQL 1.1 Query Results JSON names
them (§3.2.2) — `type`, `value`, `datatype` and the language — under the `s_`, `p` and `o_`
prefixes: `s_type`, `s_value`, `p`, `o_type`, `o_value`, `o_datatype`, `o_lang`. Those are the names
an RDF reader already knows, and the values stay `I`, `B` and `L`; SPARQL's `uri` and `literal` would
rewrite every comparison a consumer makes for no fact it lacks.

**What would reverse it.** A consumer whose engine fixes other names for the same facts and cannot
alias a column — then that consumer's names are the argument. Brevity does not.

What the relations carry beyond these — the counts the writer takes of what it wrote — is
[the graph's own facts](/docs/design/facts).

## What a graph can carry, and where the format lives

Vertex and edge tables of values, and one graph: there are no quads and nowhere to put a graph
name, which is why `grammar.bnf` has no `in g`. And **a cell in a columnar file carries a value, not
a term with its trimmings**: a literal's language tag, and in RDF 1.2 its base direction, are gone at
the pivot into columns unless the layout carries them explicitly. Base direction exists precisely
because the first strong character of a string does **not** determine how it should be laid out, so a
value returned without it is one the host renders backwards with nothing in the cell to say so. The
tag travels as `langString`; the base direction is not written.

The format itself — the conventions and what a round trip preserves — is documented in
[/docs/format](/docs/format), for somebody implementing a reader and requiring no knowledge of the
language. **The language is one product and the graph is another, and the seam is the artifact.**
