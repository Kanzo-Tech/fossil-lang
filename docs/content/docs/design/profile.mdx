Kanzo's assistant and its Ask become one pattern, a *Task*: a small model in the browser fills a
small artefact under a JSON Schema, a deterministic oracle checks it, and a bounded loop repairs it or
asks the person. The pattern, its API and the decisions about the model are kanzo-ui's, on [Tasks in
the design of Kanzo UI](https://kanzo-tech.github.io/ui/docs/design/tasks); the assistant's screens
are keasy's. This page is the part that lives here: what fossil computes so that the model has less to
guess, and the program fossil writes from what the host decided, so that no model writes one.

## What the assistant guesses today

Keasy's wizard asks one call for a whole program. The model sees column types — all `introspect`
answers is a `DESCRIBE` — and nothing else: not which column is a key, not which column of one
source holds the values of another. So it invents the keys and the edges, and the checker reads the
result afterwards. Every one of those guesses is a fact of the data that a query could have
answered.

## Profile replaces introspect

**A profile is what a source is: its columns and types, its candidate keys, the inclusions between
its columns and another source's, and a few sample rows.** Unique column combinations are the keys;
inclusion dependencies are the edges. Both are read on a sample for the preview and checked whole
in the background, so on a large file they are *candidates* until the full check agrees, and a
verdict that changes reaches the person as an assumption to review, not as a silent edit.

**It is written once, sans-IO.** Introspect was two implementations — a crate for the language
server and a package over DuckDB-WASM — kept in agreement by
generating the reader and the type table into both from `catalogue.bnf` ([Three
hosts](/docs/design/three-hosts)). That works because a `DESCRIBE` has no logic to agree on. A profile
does: which pairs of columns to test, how to prune them by type, how to read the counts back. Two
copies of that would drift. So `fossil-profile` decides which queries to run and interprets their
answers, and runs nothing — the shape of `h11` and `quinn-proto`:

```rust
let mut plan = Profiler::new(&sources);
while let Some(query) = plan.next_query() { // DESCRIBE, counts, inclusions
    let rows = host.run(&query)?;           // native DuckDB or DuckDB-WASM
    plan.feed(query.id, &rows);
}
let profile = plan.finish();                // types, keys, inclusions, samples
```

The browser reaches it through
`fossil-wasm`'s `Profiler` and runs each query on the page's DuckDB-WASM: `runProfiler` in
`@fossil-lang/wasm` is the loop (`packages/wasm/src/profile.ts, runProfiler`), and `profileInputs`
beside it reads each input under its credential and hands the plan its name and its binding
(`packages/wasm/src/describe.ts, profileInputs`). A program's own sources are `program.describe()`:
its inputs, profiled, handed to the checker, and answered as the value a run takes. The sources a
host names before there is a program are `profile(sources)`, each a reference and the format the
host chose: the inputs a program at the workspace's root binding each under its `bindingName` would
read (`crates/fossil-hir/src/lineage.rs, inputs_named`), with no program text written to reach them.
A host that wrote `x := io.csv("…")` lines only to have them scanned back was asking the parser for
what the anchor and the connections answer directly.

*Held by* `crates/fossil-hir/src/lineage.rs`,
"a_named_source_is_the_input_a_program_at_the_root_binding_it_would_read". `fossil-df`'s tests run the same plan on the native
`duckdb` crate, so the code is shared and only the engine differs
([Three hosts](/docs/design/three-hosts)).

**It is inside the wasm gate, on purpose.** The engine stays with the host, and nothing that
depends on `fossil-profile` links one through it — its own tests and `fossil-df`'s take DuckDB on a
dev edge. So `fossil-profile` is a dependency of `fossil-wasm`, and the gate has watched it from
its first commit (`crates/xtask/src/main.rs, wasm_check`). A `native` feature carrying the engine
was the other shape, and cargo's feature unification is why it is not: one dependent enabling it
links DuckDB into every build of the crate, the wasm one included.

**What would reverse it:** a query only one host can run. Then that query is marked per host, and
the module is still one. A host that cannot afford the statistics gets a mode of Profile —
`Options::TYPES`, one `DESCRIBE` a source, which is what the editor asks for on every keystroke —
not a second package.

**A profile names its sources by binding** (owner decision, 15 October 2026). `Profile.sources`,
an inclusion's `ColumnRef.source` and a failure's `source` carry the name the program binds the source
to (`users` in `users := io.csv("@lake/users.csv")`): the name a prompt, a mapping and a diagnostic
write, and the one a host used to recover from a path with `bindingName` and a suffix for the
collisions. `ProfileSource` takes it as `binding`, and what it called `name` — what the host's DuckDB
reads — is `location`, so a source has one name. The descriptor inside a `SourceProfile` is still
keyed by the reference the program wrote, because that is what the compiler's cache is keyed by and
what survives a connection being repointed: two bindings of one file share a descriptor and are two
sources of the profile, each profiled under its own name. A profile of files before there is a program
has no bindings, so the host gives each the name `bindingName(file)` makes of it, and a collision is
the host's to disambiguate; a program cannot bind a name twice. The plan reads a binding once, so one
file bound twice is read twice.

*Held by* `crates/fossil-profile/tests/native.rs`,
"a_profile_says_what_the_files_are", and `crates/fossil-profile/src/lib.rs`,
"two_bindings_of_one_file_are_two_sources_under_their_own_names".

**What would reverse it:** a host that profiles by path and has no bindings at all, and a cost of
reading one file twice that is measured on a program that does it. Then the key is the name again and a
binding is the host's to attach.

## The program is written by fossil, from a model of the data

**A host describes what it decided a graph holds as data, in one type, and fossil writes the
program** (owner decision, 21 October 2026). The decisions are the host's: which sources are read,
which types there are and the source each is read from, which columns identify one, which column
fills each field, and which relations hold between them, read on the type's own source or across a
link file. That is a `Model` (`crates/fossil-ide/src/model.rs, Model`). Everything derived from
it is knowledge of the language and is fossil's: each IRI, each `@subject`, the bindings, a column
quoted when its header is not a name, the join of a link file, and the mappings in one canonical
layout (`crates/fossil-ide/src/model.rs, write`; `@fossil-lang/wasm`'s `write`). The same model
writes the same text.

The IRI scheme is the workspace's: a type's IRI is `<base>/vocab/<name>`, a field's
`<base>/vocab/<field>`, a thing's `<base>/id/<name in words>/` and the columns of its identity as
holes, and a field's type is the checker's own spelling of the primitive (`Option<Date>`,
`Seq<Ref<Institutions>>`), so a copy in a host could not drift from it. A relation's `many` is
`Seq<Ref<…>>` and wins over `optional`, as a sequence is already empty. A relation read across a link
file is one more mapping of the type it starts from, joined on the type's first identity column, and
it writes again what the type requires: its fields that are not optional and the relations it holds
exactly one of.

**What `write` is not is an oracle.** Its output is a program like any other, and the checker reads
it: a field whose primitive is not its column's is said at its span, as it would be in a program a
person wrote. And it is not the spec fossil discarded ([discarded](/docs/design/discarded), "A mapping
spec of our own"): that was a format a model filled in place of Fossil, an untyped layer in front of a
typed language. Here no model fills anything, the `Model` is what a host already decided, and the
output is Fossil, which the person edits in the editor.

*Held by* `crates/fossil-ide/tests/model.rs`,
"a_model_is_written_as_its_types_its_sources_and_a_mapping_per_type_and_link",
"a_subject_is_the_workspaces_prefix_the_types_words_and_the_identitys_holes",
"a_relation_is_a_ref_an_optional_ref_or_a_sequence", and `crates/fossil-df/tests/written.rs`,
"the_program_a_model_implies_checks_clean_and_runs".

**What it replaced:** `grammarFor`, the grammar of Fossil for a request's names, which held a
constrained decoder to the mapping productions so a model could not invent a name; and `vocabularyOf`
and `subjectOf`, the names and identities a host computed for that model. Once the mappings are
derived from the model, a model writes nothing a grammar would hold ([discarded](/docs/design/discarded),
"A grammar of Fossil per request").

**What would reverse it:** a program a host needs that a `Model` cannot describe — a mapping filtered
by a predicate, a value computed from two columns — that a model would write better than a person in
the editor. Then the model writes that mapping, and a grammar for it comes back with it.

## The model is inferred by fossil, from the profile

**What a profile implies about a graph is fossil's answer, and a host asks only what it cannot
settle** (owner decision, 21 October 2026). `infer` reads a profile into a `Model` and the
questions it took a default for (`crates/fossil-ide/src/model.rs, infer`; `@fossil-lang/wasm`'s
`infer`). This is where the references put it: an F# type provider and `DuckDB`'s `read_csv_auto`
infer inside the library and not in its callers ([prior art](/docs/design/prior-art#types-from-data)),
and the rule is W3C's Direct Mapping — a table with a key is a class, its key the subject, a column
holding another's key a reference — with the link-table rule D2RQ's mapping generator adds.

- **A type** is a source with a candidate key, named by its binding in `PascalCase` —
  `laureates` is `Laureates`, never singularised. It is identified by the key an inclusion lands on,
  as a relation fixes it, and otherwise by the one the person chooses among its candidates.
- **A relation** is an inclusion from a type's column to another's key, named by the column without a
  trailing `id` (`country_id` is `country`), or by the column itself when a field already holds that
  name; optional when the column has nulls.
- **A link file** is a source with no key whose two inclusions land on types' keys. It is a relation
  across it, `Seq<Ref<…>>`, or, chosen, a type of its own identified by the two ends it links.
- **A field** is every other column, named by its own words as the lexer spells an identifier
  (`crates/fossil-syntax/src/name.rs, identifier`). Two columns whose words make one name are a
  question, and the one chosen keeps it: a suffix is the scheme [discarded](/docs/design/discarded)
  rejects.
- A source that is none of these is left out: nothing identifies one of its rows.

**A question never blocks the model.** Each `Ambiguity` names what it asks — a key, a link file, a
shared name — its options and the option the model stands at: the host's choice by the question's
`id`, else the first. The host phrases the question to its person; fossil does not write prose for a
UI it does not own.

*Held by* `crates/fossil-ide/tests/model.rs`,
"a_key_is_asked_only_where_no_inclusion_lands_on_one",
"a_type_is_its_binding_in_pascal_case_and_a_relation_its_column_without_its_id",
"two_columns_whose_words_make_one_name_are_asked_and_never_suffixed",
"a_source_nothing_identifies_is_left_out_and_not_bound", and `crates/fossil-df/tests/written.rs`,
"the_program_a_profile_implies_checks_clean_and_runs_a_link_file_as_a_relation",
"the_program_a_profile_implies_checks_clean_and_runs_a_link_file_as_a_type".

**What it replaced:** keasy's structure, names, decisions and acceptance of a draft, which computed the
same model in TypeScript beside the profile it read, with a singulariser and numeric suffixes on a
collision.

**What would reverse it:** a host whose people answer the same question differently for the same
profile, so the default a model stands at is wrong more often than right. Then the question stays and
the default goes, and `infer` answers no model until it is answered.

## The graph before a run

**`program.mapping()` is the mapping of the program's types, with no run.** The pre-run shape of a
graph — the types, their keys, columns and labels — is `Mapping.model()` over this document, and no
host builds it by hand ([the graph as Apache GraphAr](/docs/design/graphar) has the function and what
differs from the run's). It is not `program.describe()`, which is a credential and a query per source;
the mapping reads no source and needs no `describe` first.

**What would reverse it:** a shape a program declares that the types cannot state without running it —
a type that exists only by what a source contains. Then that type is absent before the run and present
after, and the host says so.

## The DuckDB type table reaches TypeScript from the catalogue

**`cargo xtask catalogue` projects the `duckdb` table of `catalogue.bnf` to
`packages/wasm/src/catalogue.generated.ts` as `DUCKDB_TYPES`**, in file order, which is precedence. A
host that stands in for an engine — a test double answering a `DESCRIBE` — says a primitive in the
words the table does, and states no row of it; keasy's fixture kept its own `Primitive` to DuckDB-type
map beside the Rust table. Only the table is projected. What a `DESCRIBE` type *means* is matched by
`fossil-profile`, in the wasm module, from the same file, and a matcher in TypeScript would be a second
implementation of it.

*Held by* `crates/xtask/tests/catalogue_generated.rs`,
"the_duckdb_table_is_projected_to_typescript_in_file_order", and
"the_checked_in_files_match_the_catalogue".

**What would reverse it:** a TypeScript host that has to read a `DESCRIBE` itself and cannot ask the
module. Then the matcher is generated beside the table, from the same lines, as the Rust one is.

## Order

The profiler and the program a model implies are phase 2 of Kanzo Tasks, after the evaluation set
and Ask's resolver. Both are built: `fossil-profile` with its two hosts, introspect gone, and
`fossil_ide::model`: the `Model` a profile implies, and the program a `Model` implies with its
types [declared in the program](/docs/design/declared). On keasy's side the executor runs in a worker of
its own, and it has moved into the executor itself ([A run off the page](/docs/design/off-the-page)).

## The graph's profile is the same plan

A run profiles what it wrote with this plan, over the tables instead of the sources, and stores it in
each vertex chunk's footer for the readers of the graph — [the graph's own facts](/docs/design/facts) argues why
the output and not the sources, and what the plan gains for it: its queries as data so DataFusion can
run them too, the least, greatest and commonest values, and Parquet's names for the counts.
