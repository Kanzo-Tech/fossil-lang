description: "The facts a reader would otherwise guess reach it without a scan: the relations attachGraph makes of the information files, and the counts the writer takes of what it wrote — per column what Parquet's statistics and PostgreSQL's pg_stats carry: nulls, distinct values, the least and greatest value, the commonest values and their frequencies — stored in each vertex chunk's footer. Inclusions between tables were measured and dropped."
---

A graph is read by things that were not there when it was written — kanzo-ui's Ask, which turns a
question into SQL, and `@kanzo-tech/graph`, which draws it. Both need to know what each table and
column *is* before they read a row, and without the facts both guess: Ask would run `SUMMARIZE` on
every table at every attach and decide by a name regex and a fifty-value threshold whether a column
is an identifier; the graph would read an edge's label by splitting the table name
`Order_placedBy_Person` on `_`. Every one of those guesses has an exact answer in the information
files or in the rows the writer just wrote.

So this page does two things. **The information files expose what GraphAr says**, so a guess one
column away from its answer is not made. And **the writer counts what it wrote** — with the same plan
`fossil-profile` runs over a source for the assistant ([Profile](/docs/design/profile)) — and stores
the answer in each vertex chunk's footer, so a reader reads the counts instead of taking them.

## The relations carry every fact the information files hold

`attachGraph` (`@kanzo-tech/graphar-duckdb`) makes the information files into relations beside the
tables' views, and the reader needs nothing else:

```
graphar_vertex_types(type, count, ordinal)
graphar_edge_types(name, src_type, edge_type, dst_type, count, directed, ordinal)
graphar_properties(type, property, data_type, is_primary, is_nullable, ordinal, cardinality)
graphar_extra_info(key, value)
graphar_chunks(type, kind, path)
```

- **`edge_type`** is the relation's label, as GraphAr names it: the reader does not cut it out of
  the table name.
- **`is_primary`** says which property is the identity, the `subject`; **`cardinality`** says which
  columns are lists. A column whose values are IRIs is an identifier by what the shape declared, not by
  a regex over its name and a count of its values.
- **`graphar_chunks`** is the path of each chunk file as the engine names it, so the counts below are
  read with `parquet_metadata` and `parquet_kv_metadata` and no path arithmetic.
- **A label, an annotation and a datatype** beyond GraphAr's are the mapping's:
  [Its RDF meaning, as a mapping](/docs/format/reading/rdf) carries them as plain triples about the
  class and predicate IRIs, read by `Mapping.model()`.

The relations are a SQL projection of the information files, so they are one fact and not a second
document. **What would reverse it:** a fact of the information files that a reader needs and no
relation carries. The rule is that there is none, so the fix is the column, never a reader that
parses the YAML itself.

## The writer counts what it wrote

### The output, not the sources

The assistant profiles a program's **sources**, before there is a program, to propose one
([Profile](/docs/design/profile)). A reader of the graph asks about something else: the types and
fields the program made. «How many laureates have no birth date», «which prizes' `category` values
are there», «is `Laureate.name` an identifier» are questions about a column of a chunk of
`vertex/Laureate/`, which no source has — a join made it, a `parse.date` changed its type, a dedup
merged its rows. A source profile stored in the graph would describe columns the graph does not have,
under names the program renamed, and would leak the structure of sources the graph exists not to
expose (the graph names no source, for the same reason). So **the writer profiles the tables it
wrote**, and what it stores is about them.

**What would reverse it:** a reader of a graph that asks about a *source* — a lineage view that
shows how many rows of `people.csv` became `Person`s. Then the source profile the run was checked
against (`profiled`) is stored beside the graph's, and it is a second section, never a replacement.

### What it counts

The same plan as a source's, `crates/fossil-profile/src/lib.rs, Profiler`, run over the tables
about to be written instead of the sources, **whole** — `Options::sample` `0`, so every count is
exact over every row the graph holds — and stopping at the counts: a plan over tables tests no
inclusion. **What it keeps is what the references keep, under their names.** A column's statistics
already have a shape three formats agree on, and fossil takes it rather than a fourth:

| fact | where it goes | the reference that names it |
| --- | --- | --- |
| rows | `vertex_count`, `edge_count<k>` and the footer's `num_rows` | Iceberg's `record_count` on a data file; `pg_class.reltuples` |
| nulls | the column chunk's `Statistics.null_count` | Parquet `Statistics.null_count`, Iceberg `null_value_counts`; `pg_stats.null_frac` as a fraction |
| least and greatest value | the column chunk's `Statistics.min_value`, `max_value` | Parquet; Iceberg `lower_bounds`, `upper_bounds`. Absent for a column with no value |
| distinct values | `fossil:stats`, `distinct_count`, exact | Parquet `Statistics.distinct_count`, which the Arrow writer leaves empty; `pg_stats.n_distinct` |
| commonest values | `fossil:stats`, `most_common_vals`, `most_common_freqs` | `pg_stats`' two arrays, which Parquet and Iceberg have no field for: the ten most frequent non-null values that occur at least twice, most frequent first and ties by value, so the same graph writes the same list, and each one's share of the chunk's rows. Absent when no value repeats — a key has none |
| candidate keys | not stored | derived by the reader from the counts: a column of a keyable type with `null_count` 0 and `distinct_count` equal to the rows — `pg_stats.n_distinct = -1` with no nulls |

**Candidate keys are derived, and not stored.** The rule needs which types can be a key (not a
float, not a boolean), and it is five GraphAr types, `int32`, `int64`, `string`, `date`, `timestamp`,
that the reader already has in `graphar_properties.data_type`. **What would reverse it:** a reader
that derives keys under a different rule — a sampled count, a composite key — at which point the rule
is the reader's, as it already is.

**Every value is text, and it is the text the mapping gives it**: the natural lexical form of the
column's type, R2RML §10.2 ([Its RDF meaning, as a mapping](/docs/format/reading/rdf)). One spelling
of a value across the graph's relations, and the one a reader casts back with the column's
`data_type`. **A value longer than 64 bytes** is left out, never cut: `most_common_vals` is then
absent for a column with such a value among its ten commonest. A truncated value would be a value the
column does not hold, which a reader would filter by and match nothing; Parquet truncates its bounds
at 64 bytes and marks them inexact, so a reader that keeps only exact bounds never shows a cut value.

**Which columns.** The distinct count and the commonest values are taken on every property of every
vertex type; the nulls and the bounds are Parquet's, on every column of every chunk. A set column is
counted over its elements, since Parquet counts leaf values.

**What is not stored: the sample rows.** A source's profile keeps its first rows because the source
is somewhere a model cannot read. A graph's rows are a `SELECT … LIMIT 5` away on the view.

### In the footer, beside the field it measures

The statistics are in each vertex chunk's own footer, the one place a Parquet reader already looks,
and the document under `fossil:stats` is specified on
[Statistics](/docs/format/conventions/statistics). **They are not in a file beside the graph**,
because the information files and the footers are what a reader reads anyway, and a second file would
be a second read at every open for facts as small as the schema they describe. The size is bounded by
the columns, not the rows — at most ten values of at most 64 bytes per column. That is Delta Lake's
choice, per-file `stats` read with the log, and not Iceberg's, whose distinct-value sketches live in
Puffin files because a sketch is large.

The names are Parquet's where Parquet has the field — `Statistics` has `null_count`,
`distinct_count`, `min_value` and `max_value` — because the graph is Parquet, and the profiler's own
`nulls` and `distinct` were renamed to them, so a source's profile and a graph's say the same thing in
the same words. The commonest values are the one fact Parquet and Iceberg have no field for, and the
names are PostgreSQL's, whose planner is the reader that has kept them longest: `most_common_vals`
and `most_common_freqs`, two arrays in the same order, a frequency being the share of the chunk's
rows. The source profile of [Profile](/docs/design/profile) keeps its counts, because a sampled source
has no table row count to divide by.

**What would reverse it:** a graph whose counting the writer measurably cannot afford, which then
counts in the reader for that graph only; or a Parquet release with a table-level distinct count or
frequent values in the footer, which moves each fact into its field.

### Where it runs, and what it costs

**In the writer, after the layout is final and before the type's chunk is written**, on the batches it
already holds — the writer collects every batch to number the ids, so nothing is read back from
storage. A run that cannot profile what it wrote writes no graph document and so no graph: the
profile is part of the commit, and a graph never exists without its facts.

**The plan runs on DataFusion, which has no SQL here.** `fossil-df` builds DataFusion with
`default-features = false`, dropping its `sql` frontend from the wasm build, and the profiler's
queries are SQL strings DuckDB runs. So the plan's queries are **data** — an `Ask`, one per kind
(the counts of a table, the commonest values of a column) — and SQL is DuckDB's rendering of an
`Ask`, kept in `fossil-profile` for the two hosts that profile sources, while `fossil-df` renders the
same `Ask` as a DataFusion plan (`crates/fossil-df/src/facts.rs`). Which queries to run and what a
count means stay in one crate; only the rendering is per engine. The wasm gate does not move:
`fossil-profile` links no engine and is in the wasm closure already.

**Under the run's budget.** Every query reserves against the same 2 GiB pool as the run
([Three hosts](/docs/design/three-hosts#what-the-wasm-writer-holds-and-how-it-says-no)), so counts
that do not fit are `run/over-budget` like any operator, before anything is committed: **the run is
refused**, and no graph is written without its stats. The counts of a table are one aggregate over
it; the commonest values are one `GROUP BY` per column, and only for a column whose `distinct_count`
is below its non-null count, since a column with no repeat has none.

### Inclusions: measured, and dropped

The writer used to test inclusions too — every value of one column a value of another table's
candidate key or `subject`, the shape of an edge the program did not declare — and list them in
the manifest as `inclusions`, read as `fossil_inclusions`. They are gone from the writer, for two reasons, one measured and one about references.

**They were the cost.** Measured natively, release build, the run into memory, median of three
interleaved with the same program on the writer without facts, on a shared four-core host (load 10
to 13). *Write* is `fossil_df::write` whole; *facts* the part of it that counted; the SNB, CORDIS and
Nobel graphs are the keasy dev examples:

| graph | tables · rows written | run before | run with inclusions | write before → with inclusions | facts | of it, inclusions | manifest |
| --- | --- | --- | --- | --- | --- | --- | --- |
| shop, 60,000 · 180,000 | 3 · 395,854 | 0.98 s | 1.01 s | 57 → 221 ms | 166 ms | 4 asks, 148 ms | 2.6 → 6.5 KB |
| shop, 200,000 · 600,000 | 3 · 1,313,992 | 3.30 s | 3.85 s | 163 → 798 ms | 610 ms | 4 asks, 379 ms | 2.6 → 6.6 KB |
| Nobel laureates | 10 · 6,779 | 0.10 s | 0.21 s | 7 → 104 ms | 99 ms | 30 asks, 47 ms | 10.5 → 31.1 KB |
| CORDIS (Horizon subset) | 8 · 523,395 | 2.26 s | 3.58 s | 241 → 1,418 ms | 1,221 ms | 78 asks, 1,043 ms | 13.0 → 44.6 KB |
| LDBC SNB SF0.1 | 23 · 1,135,175 | 4.88 s | 10.80 s | 319 → 6,163 ms | 5,906 ms | 297 asks, 5,650 ms | 25.6 → 71.8 KB |

The counts and the commonest values were cheap — at most 290 ms on any of them — and **the
inclusions were 47 to 96 % of the facts**: on SNB they more than doubled the run. They grow with the
pairs the pruning keeps, not with the rows: SNB holds fewer rows per table than shop at 200,000 and its
inclusions cost fifteen times as much. **None of the five found one**: every reference of these
programs is an edge, which is declared, and the 413 anti-joins were all between columns that turned
out not to be contained. The peak did not move with any of it (51 to 291 MiB resident, the same with
and without facts), because the counts read the batches the writer already holds. Vermont was not
measured; it is not in this repository.

**Without them**, the same bench once more over the two graphs they cost most on, median of three,
on the same host when it was otherwise idle (load under 5) — so the run times are not comparable to
the table's, while the write and the counting inside it are what was asked of them. The CORDIS subset
is derived from the current CORDIS dump, the archived one being unreachable that day: 0.4 to 0.7 % more
rows per file.

| graph | write | of it, counting | run | manifest |
| --- | --- | --- | --- | --- |
| CORDIS (Horizon subset) | 384 ms | 179 ms | 3.63 s | 37.6 KB |
| LDBC SNB SF0.1 | 519 ms | 277 ms | 6.23 s | 63.1 KB |

The counting is what the counts and the commonest values cost before — about 180 and 250 ms — and the
write is a third of what it was on CORDIS and a twelfth on SNB. The peak is unchanged (263 and
289 MiB).

**The source profile keeps them.** Between a program's *sources*, before there is a program, an
inclusion is what keasy's assistant proposes an edge from: it offers an edge only where one was found
([Profile](/docs/design/profile)). That is the discovery the paragraph below names, run on purpose by
a caller that needs it, and it is a different question from what a written graph holds.

**No reference stores them.** Parquet's `Statistics`, Iceberg's column metrics and Puffin
sketches, Delta Lake's file stats and PostgreSQL's `pg_stats` all describe one column at a time; none
of them has a field for a dependency between two. Finding inclusion dependencies is a discovery
problem with its own literature and tools — Metanome's profilers, SPIDER and BINDER among them
([Prior art](/docs/design/prior-art)) — run on purpose over data someone is investigating, not a
statistic a format keeps beside every file. A graph carries what the references carry and is read
by tools that know those references; a field none of them has is a field no tool reads.

**What would bring them back:** a reader that needs them — a «join nobody declared» a person or a
model acts on — together with a reference that stores them, so the field has a name and a reader
outside fossil. Until both exist, a reader that wants one runs the anti-join on the attached views,
which is one query and costs only the asker. Recorded in [Discarded](/docs/design/discarded).

**What would reverse the rest:** if exact distinct counts push a graph that fits over the budget,
`distinct_count` becomes a sketch — Iceberg's Puffin `ndv` is the reference for that — and
the candidate keys the one exact count kept.

## What a reader stops guessing

| a reader's guess | the fact it reads instead |
| --- | --- |
| the edge label, split out of `Src_label_Dst` | `graphar_edge_types.edge_type` |
| «identifier», by a name regex and fifty distinct values | `graphar_properties.is_primary`, the term type and `distinct_count` against the rows |
| «numeric measure» for a year stored as `int32` | the datatype `xsd:gYear` in the mapping, read by `Mapping.model()` |
| `SUMMARIZE` over every table at attach | the footers, by `parquet_metadata` and `parquet_kv_metadata` over `graphar_chunks`, with no scan |
| the six commonest values, by a scan | `fossil:stats.most_common_vals`, `most_common_freqs` |
| a column's word, from its identifier | the annotation triples of `mapping.ttl` |

## What it touches

| Where | What changes |
| --- | --- |
| `fossil-profile` | `Ask` as the plan's queries, with `sql()` as DuckDB's rendering; `min_value`, `max_value` and `top_values` in the counts; `nulls` and `distinct` renamed to `null_count` and `distinct_count`; a source that is a table the host already holds, with no reader, counted and never tested for an inclusion |
| `fossil-df` | `fossil-profile` a dependency; `Ask` rendered on DataFusion; the counts run before each vertex chunk, under the pool; `fossil:stats` written in the chunk's footer |
| `@fossil-lang/types` | the renamed profile wire types, generated |
| `@fossil-lang/wasm` | `runProfiler` reads `query.sql` as before; the editor's profile carries the new counts |
| kanzo-ui | Ask's field statistics read the footers instead of `SUMMARIZE`; `@kanzo-tech/graph` reads GraphAr's relations |
