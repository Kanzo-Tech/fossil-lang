A fossil program produces a **corpus**: a graph written as columnar files with a manifest that names
them. Not a database to connect to, not a stream to consume, not an endpoint. Files.

A reader opens the manifest and reads the tables it names — from a local path, an object store, or a
plain web server. **There is no service in the path**, so no query language between reader and data
beyond the engine the reader already has, no process to keep alive, no writer version to match.

## Files, and the one that commits them

```
<dest>/
  fossil.json                           written last
  vertex/<Type>.parquet                 one per vertex type
  edge/<Src>_<label>_<Dst>.parquet      one per relation
```

`fossil.json` names every table, its path, its columns with their types, its row count, and — for a
vertex table that is drawn — the two columns it is drawn at. It is written **after** every Parquet
file, so its presence is the commit: a directory without it is a write that did not finish, and a
reader that finds it can trust every path it names. The shape is
`crates/fossil-sinks/src/manifest.rs, Manifest`, and [/docs/format](/docs/format) specifies it for a
reader who has none of this repository.

**Nothing is computed from a path, and no path is listed.** A reader composes no URL; it takes each
`path` as written, relative to the manifest. The constraint that forced the old arithmetic addressing
— **you cannot list a directory over HTTP** — is met by the manifest naming every file, which is the
whole of what a reader needs when there is one file per table.

**What would reverse it.** A table too large to be one file. Then a table is several parts and the
manifest names each; the rule — named, never listed — does not move.

## One graph, one id space

Every vertex of every type has a `dense_id`, and the ids run `0..V−1` across the **whole graph**, not
per type. An edge table is `src` and `dst` over those ids, so an edge is a pair of integers whichever
types it joins, and a viewer's buffer index **is** the id.

The id is the rank of a vertex in the Hilbert order of its position, over the union of every drawn
type. `crates/fossil-layout/src/layout/hilbert.rs, hilbert_codes` quantises with `floor`, which makes
the order the one DuckDB's `ST_Hilbert` computes, and
`crates/fossil-layout/src/layout/hilbert.rs, hilbert_ranks` turns codes into ranks. Vertices of a type
with no position take the last ids, ordered by type and then by subject. Every table is written
sorted by its key, so reading a vertex table in id order is reading it in curve order, and a filter
on a box prunes row groups on the footers' own statistics. [Position](/docs/design/position) is where
the coordinates come from.

**What would reverse it.** A graph whose types cannot share one layout — relations between types so
sparse that the joint placement pulls nothing together. That is measured against per-type planes on
the same corpus before anything is decided, and per-type planes are what it would bring back.

### A reader is handed the subject IRI, because an address is not something to key on

A lookup by identity is a `scan` filtered on `subject`, the IRI. The alternative is the `dense_id`,
and it is the cheap one. It is refused because **the spatial order is the id space**: redoing the
layout ranks every vertex by the Hilbert code of its new position and lets that rank be its id, so a
`dense_id` held anywhere outside the corpus names a *different vertex* after the next write. A
bookmark, a selection, a link from another system and a row in somebody else's database all key on
something, and an address is not something to key on.

The manifest says which column is which — `key` is `dense_id` and `identity` is `subject`, on every
vertex table — so a reader keys on the field rather than on a column name it was told.

What would reverse it is a corpus whose ids survive a re-layout — a stable id column written beside
the address. Nothing writes one, and adding one is a format change and not a reader change.

## The artifact is the API

The stance follows the table formats — Iceberg, Delta Lake, Lance — where a manifest plus a set of
files is the interface, *many* engines read the same table, and **none of them is the contract**. A
`fossil/1` corpus is plain Parquet: `read_parquet` on a path the manifest names is a whole reader,
and [reading one without fossil](/docs/format/reading/without-fossil) is the recipe.

**Two implementations before a format change, not after** — the Arrow rule. Parquet is the warning:
thirteen years of unwithdrawable files and a reference implementation that became normative without
anyone deciding it.

<Callout type="warn" title="One clock, running one way">
**If a corpus reaches a third party before the format is settled, the option is gone.** Nothing is
published, which is what made a cut like `fossil/1` cheap exactly once. Within `fossil/1` a field is
only ever added, optional and ignorable; changing what a fixed column or a byte means is `fossil/2`.
</Callout>

## Nothing is borrowed from GraphAr any more

The manifest was three YAML files named and keyed the way GraphAr names them, opening with
`version: gar/v1`, and this page carried nine measured divergences from GraphAr's specification and
the observation that GraphAr's own reader throws on the first property of every corpus fossil wrote —
`dense_id` is `uint32`, and its parser has no unsigned type. The borrowed names bought no reader and
promised a conformance the files did not have.

`fossil.json` replaces all three. Its vocabulary is SQL/PGQ's — vertex tables and edge tables, a
`key`, a `source` and a `destination` that each `references` a vertex table, a `label` per relation —
because that is the vocabulary of the engine a reader actually opens it with. Its version string is
`fossil/1`, one constant, `crates/fossil-sinks/src/manifest.rs, FOSSIL_FORMAT`, and a reader rejects
any other before it reads a byte of Parquet. The YAML manifest, the divergence table and the `gar/v1`
count are kept on
[the tiled corpus](/docs/design/later/corpus-tiles#what-is-borrowed-from-graphar-and-where-borrowing-stops).

**What would reverse it.** A second reader, not ours, that already speaks GraphAr and would open a
fossil corpus if the names matched. [What was discarded](/docs/design/discarded) carries the
conformance row with the same condition.

## The width of an address, and what actually runs out first

`dense_id` is declared `uint32`, which puts a hard ceiling of **4,294,967,295 vertices in one graph**
— every type together, since the id space is shared — and the question the number invites is whether
that ceiling is close.

**It is not close, and what is close is something else.** The layout pass assigns the numbering, and
it was measured: on a 14-core machine with 48 GiB it peaked at **2.09 GiB at two million vertices and
8.82 GiB at ten**, and the whole write at ten million took **404.4 s**. Linear over that range, 2³²
vertices is on the order of **3.7 TiB resident and two days of wall clock** — the pass exhausts a
machine roughly **430× before the column exhausts its range**, and the wasm host, with 4 GiB of linear
memory, long before that. The width is not what stops a corpus.

It is also 32-bit *by construction* rather than by choice of spelling.
`crates/fossil-layout/src/layout/community.rs, community_hierarchy` and
`crates/fossil-layout/src/layout/hilbert.rs, hilbert_ranks` are `u32` throughout. Widening the column
without widening the pass would declare a range nothing in the writer can number. And the ecosystem
is at the same place: no maintained community-detection crate exceeds 32-bit indices, which is one
of the reasons [adopting one is rejected](/docs/design/discarded#streaming-memory-and-scale).

The cost of the other choice is on a column every drawing read takes: at a million vertices
`dense_id` is **4.0 MB** on disk beside **4.0 MB** for `x` and **3.96 MB** for `y`, so `uint64`
spends the most-read bytes of the corpus on range nothing can reach.

### The gapless `0..V−1`, and the price of keeping it

The other half of the same commitment is gaplessness, and it is the convention a writer is most
tempted to trade. The temptation is concrete: the writer assigns ids after holding every batch, and
handing each partition a **preassigned range** removes that — at the price of holes wherever a
partition does not fill its range.

Both exits were priced on the ten-million corpus before any code was written, and neither is taken.

- **How many holes.** The split is a hash's, not the data's: fourteen partitions on `subject` come
  out within **0.526%** of each other. A quantum sized to the largest leaves **35,200 holes, 0.35% of
  V** — but that quantum is known only *after* the run. The one a writer can pick beforehand is
  source rows over partitions, and the dedup collapses 8.1 rows into one: **71,027,072 holes, 710% of
  V**.
- **What compacting them costs.** **9.6 s and 3.72 GiB**, against a whole write of 404.4 s and 20.72
  GiB — 2.4% of the wall clock standing alone, with output byte-identical to compacting the gapless
  numbering.
- **And the premise did not survive the measurement.** Holding the batches is not where the peak
  comes from: the sort is **13.72 GiB** and the aggregate beneath it **13.85**, and that term is the
  dedup, which no range scheme touches.

The two harnesses were `dense_id_ranges.rs` in `fossil-df`'s examples and `compaction_pass.rs` in
`fossil-layout`'s, at `ac1801d4`. **So the convention stays, and the reason it stays is the third
bullet rather than the first two.**

## Why write-once/read-many is not an implementation detail

[Identity is unique per type](/docs/design/identity) because a fossil program is compiled in one
piece with every mapping in front of it — a check unavailable to any system whose parts deploy
independently, which is why the one federation system that shipped an equivalent removed it. And
atomic renames, lock files, visibility protocols and transaction logs exist to protect a reader from
a half-written state; with no such reader they are cost without benefit. The one ordering the writer
keeps is the manifest last, and it is the only one a reader could observe.

## `sql` reaches the engine unparsed, and one option opens it

[The door](/docs/design/one-door) reads with `scan`, whose filter is a tree the door renders itself.
`sql` takes a **raw SQL string**, evaluated by the host's engine against the corpus's views; it is
not a parsed predicate language and nothing that reaches it is. It exists only on a corpus opened
with `sql: 'allowed'` — the default withholds it — so a host that hands a corpus to code it does not
trust decides once, at `open`, and the type says which it decided.

Two things it does not claim. It does not stop a host *granting* access — withholding SQL is a
policy, and a library cannot hold a policy for its consumers. And it is not a sanitiser: there is no
chokepoint to sanitise towards, because a corpus is files and a recipient holds them.

**What would reverse it.** A consumer whose question `scan` cannot express and that must not be
handed SQL. Then the question earns a member of the door, argued with its measurement.

## The camera has a renderer, and it is not fossil's

The door does not draw, which leaves one thing unstated: *something* has to put a million points on a
screen, and fossil does not ship it. What draws is `@kanzo-tech/graph`, a WebGL canvas over
cosmos.gl, and it is the only viewer. **The view owns the picture and every policy over it; fossil
owns the bytes and the manifest that names them.**

A `fossil/1` corpus is drawn whole: every vertex table with a `position`, and every edge table whose
two ends are drawn. At a million vertices and two million edges that read was measured in
DuckDB-WASM, one thread, a local file: the vertices' `dense_id`, `x`, `y` and `cluster_id` to **16 MB
of Arrow in 77–152 ms**, the edges' `src` and `dst` to **16 MB in 51–127 ms**. The tiled read it
replaced is on [the tiled corpus](/docs/design/later/corpus-tiles), and what brings it back is a
corpus that does not fit the tab, measured.

### A palette has a capacity, and a corpus does not know it

`cluster_id` is what the layout pass writes and what colours the picture, and the two scales are not
the same size. The bench corpus carries **128 communities**; the design system's categorical palette
publishes its capacity as `--chart-capacity`, which is **8**, and an ordinal at or past it resolves
to the muted token. Handed over unfolded, **937,496 of a million vertices came back one grey** — a
picture that is not wrong about anything and shows nothing. Folded into the capacity by remainder,
two communities can share a slot, which is what eight slots *means*; the fold is a function of the
community alone, so a colour survives a pan.

**The heading is the whole of it: a corpus does not know.** The manifest carries no domain for
`cluster_id`, and a reader that draws everything counts the distinct values it holds. What would add
one is a reader that needs the number before it reads — a view that sizes its palette before the
first batch — and then it is an optional field within `fossil/1`.

## Conformance reads the bytes with an engine nobody here wrote

The checker is `packages/corpus/guards/check.mjs`, and it needs `node` and the `duckdb` binary and
nothing else: no crate of this repository, no package, no build. It reads `fossil.json`, opens every
table with `read_parquet`, and asserts the conventions [/docs/format](/docs/format) states — ids
unique and gapless over the union of vertex tables, every `src` and `dst` in the table its endpoint
`references`, each table sorted by its key, each declared count equal to the rows. **An assertion
there can only be satisfied by agreeing with the bytes**, never by agreeing with another
implementation of the same arithmetic — the gap through which GraphAr's fourth implementation landed
green and wrong.

The three-reader round trip that preceded it — a JavaScript reader, a Rust planner at two widths, and
the published vectors — is on
[the tiled corpus](/docs/design/later/corpus-tiles#conformance-is-a-round-trip-and-what-it-rests-on-is-not-a-headcount).
It existed because the arithmetic a reader reproduced was the contract, and a `fossil/1` reader
reproduces none.

## What a corpus can carry, and where the format lives

RDF terms, quads and named graphs — a graph is not restricted to triples and the container is not
restricted to one graph. But **a cell in a columnar file carries a value, not a term with its
trimmings**: a literal's language tag, and in RDF 1.2 its base direction, are gone at the pivot into
columns unless the layout carries them explicitly. Base direction exists precisely because the first
strong character of a string does **not** determine how it should be laid out, so a value returned
without it is one the host renders backwards with nothing in the cell to say so.

The format itself — the conventions and the executable guards — is documented in `/docs/format` and
executed by `packages/corpus/guards/`, for somebody implementing a reader and requiring no knowledge
of the language. **The language is one product and the corpus is another, and the seam is the
artifact.**
