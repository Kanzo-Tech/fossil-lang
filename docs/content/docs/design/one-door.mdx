A consumer reads a corpus through one door, and the whole of it is five names:

```ts
const corpus = await open(url, { engine });
const { vertex_tables, edge_tables } = corpus.manifest;       // fossil.json, parsed once
const scan = corpus.scan({ table: 'Person', select: ['dense_id', 'x', 'y'] });
const batches = await scan.read(scan.plan());
await corpus.close();
```

`open` (`packages/corpus/src/open.ts, open`) fetches `fossil.json`, rejects a `format` that is not `fossil/1` before a byte of Parquet is
read, and creates one view per table in the host's engine. `manifest` is that document, parsed once.
`scan` reads any table — vertices or edges — with a filter, a projection and a limit. `sql` is the
escape hatch, present only on a corpus opened with `sql: 'allowed'`. `close` detaches. The contract is
[the corpus](/docs/design/corpus); the format underneath is [/docs/format](/docs/format).

**A consumer states what it wants, and how it is fetched is the door's business.** Whole, by range or
by tile is decided behind `scan`, never by the caller, which is why the door has no `tileMatrix`, no
`edges` and no addressing member: those were the camera's door over a tiled corpus, and
[a door for a camera](/docs/design/later/one-door-camera) keeps what it was and what it measured.

## `scan` plans tasks, and plans one

`scan(params)` returns a plan and a read — `plan()` then `read(tasks)` — and `plan()` answers exactly
one task, the whole table under the filter. The split is the seam and nothing more: it is where a
tiled read would go without a consumer changing a line, and it is kept for that one reason.

**What would reverse it.** A year with no reader that needed a second task — no corpus that failed
the in-browser thresholds on [the page that keeps the tiles](/docs/design/later/backend). Then the
split is ceremony, and `scan` answers batches directly.

## One door, and one layer behind it

One door is half of the rule. The other half is what stands behind it: **each thing the door does
is done once, by one layer.** A layer that parses what the layer below already parsed, or forwards a
call it could have made itself, is a second implementation with a longer path, and it is deleted.
The door stays minimal and hides everything underneath: a consumer states what it wants, and how it
is fetched — whole, by range, or by tile — is the door's business and never the consumer's.

**Reading a corpus broke this, measured 2026-09-30 on `main` `ac1801d4`.** One read crossed
four layers that each knew the manifest: the TS door scanned it line by line
(`ac1801d4:packages/corpus/src/manifest.ts`), the WASM crate resolved it again (`fossil-graph/src/plan.rs`,
`plan::resolve`, which `open(job)` ran twice), the Rust verb path loaded it once more on every call
(`fossil-graph-wasm/src/lib.rs`, `dispatch_graph` → `Manifest::load`), and the verb it served ended
as SQL that DuckDB could have been sent directly — `executeSql` loaded the manifest and never read it
(`fossil-graph/src/executor.rs`). keasy's discover view parsed the manifest six times before it
drew anything. The door above is the repair: `fossil.json` is parsed once, in TypeScript, and a
read is one statement to the host's engine.

Writing had the same shape: the native CLI and the browser were two hosts that wrote different
corpora, and no test compared them. The CLI is gone ([discarded](/docs/design/discarded)), and the
wasm executor is the one host that writes, in a browser and in Node.

The same pattern is expected elsewhere, so the rule obliges an audit rather than a fix to this one
case: for every capability, count the layers that implement it, and keep one.

**What would reverse it.** A layer that is the only place a capability can run — the WASM build is
the only way the browser can *write* — earns its place for that capability and no other. Reading is
not such a case: it is a small manifest and SQL, which the door can do without Rust.
