> **Deferred, not reversed.** A `fossil/1` corpus has no tile contract: it is read whole, through
> `open` and `scan`, and a scan is one task. The code existed at commit `ac1801d4` (main
> `e5b2113f`), and every path on this page is spelled against that commit. What brings it back: a
> `fossil/1` corpus that fails the in-browser thresholds — open over 1.5 s, first paint over 3 s,
> or heap over 1.5 GB at a million vertices over HTTP.

**fossil is the backend. The view is `@kanzo-tech/graph` and the rest of kanzo-ui, and there is one
path between them.** Anything that answers the same question a second way is deleted rather than
kept beside it — the playground went for being a second viewer, `@fossil-lang/draw` went with it, and
`fossil-mcp` went for being a second binding. What is left on this side is one reader,
`@fossil-lang/corpus`, and this page is the shape it has.

The shape is borrowed, and naming where it comes from is what makes it checkable rather than an
analogy. **Reading a corpus follows Apache Iceberg's read path**, Catalog → Table → Scan: a table is
loaded from its metadata, a scan is a filter plus a projection, planning turns the scan into tasks
pruned by statistics the writer published, and a task is read on its own. **Addressing follows the
OGC Two Dimensional Tile Matrix Set** (17-083r4) and OGC API – Tiles (20-057): a set of tile matrices,
coarsest first, and a tile named by its matrix and its position in it. Both are in
[prior art](/docs/design/prior-art#the-backend).

The view side has references of its own — deck.gl's `Tileset2D` for loading, Ark UI and TanStack for
the React surface — and they are kanzo-ui's to argue. What this page owns is where the seam is and
what crosses it.

## Three layers, and what each owns

| layer | what it owns | what it does not |
| --- | --- | --- |
| **writer** — `fossil run`, the layout pass | the bytes: payload tiles in Hilbert order, both adjacency orientations, the identity index, the cell pyramid and its quotients — and **the statistics of every tile it wrote** | any reader's question: which tiles a window needs, what a view draws |
| **manifest** — `graph.graph.yml` and one file per type | what a reader cannot recover without reading every footer: counts, the declared base of the pyramid, the tile matrix, and the per-tile statistics | anything derivable from what it already says |
| **reader** — `@fossil-lang/corpus` | planning (which tiles a scan needs, from the manifest alone) and reading (a batch per tile, through the host's engine) | policy: caching, cancelling what went stale, drawing a parent while a child loads, prefetching — all of it is the view's |

The line under the reader is the one that matters. **A reader that caches is a second view.** The
reader's answers are pure functions of an address, a filter and a projection, which is what lets a
view cache them without asking; the moment the reader holds a cache of its own there are two
residency policies over one set of tiles, and the camera page measured what the first one cost to
build at the wrong seam ([the camera](/docs/design/later/camera)).

**What would reverse it.** A second view — anything other than kanzo-ui reading a corpus at
interactive rates — that would otherwise have to rebuild the same cache. Then the cache is shared
infrastructure, and it would belong in a package between the two, still not in the reader.

## The contract

This is everything that crosses. `Engine` and `Host` are `@fossil-lang/types`' own
(`ac1801d4:packages/types/src/engine.ts, Engine`, `ac1801d4:packages/types/src/host.ts, Host`), and `SchemaResult` and
the SQL pair are the verbs' generated shapes, unchanged.

`Filter` is a tree, and it is Iceberg's expression vocabulary spelled as data:

```ts
type Literal = number | bigint | string | boolean;
type Filter =
  | { column: string; op: '=' | '!=' | '<' | '<=' | '>' | '>='; value: Literal }
  | { column: string; op: 'in' | 'not in'; values: readonly Literal[] }
  | { column: string; op: 'is null' | 'not null' }
  | { and: readonly Filter[] }
  | { or: readonly Filter[] }
  | { not: Filter };
```

`Box` is `{ x, y, w, h }`, and as a tile's `bbox` or a set's `extent` it is bounds, closed on both
edges; a window a view culls with is its own, and a `Filter` states one half-open. A `bbox` and an `extent` are
`null` for a type with no `x` and `y`, and `coordinates` is `null` where the document declares no
coordinate system; the contract had all three total, and a type without geometry still has tiles.
`CorpusTypes`, `CorpusRelation` and the two errors are the ones
`ac1801d4:packages/corpus/src/index.ts` already exported, with one addition: each vertex type carries its
manifest's `channels:` block. The page said the reader parsed it and did not surface it; nothing on
the reader's side parsed it at all, so `fossil_graph::plan` reads it now
(`ac1801d4:crates/fossil-graph/src/plan/declared.rs, channels_of`) with the cell tree and the coordinate
system beside it. `Channel`, `Direction`, `Gap` and `GapReason` are the ones
`ac1801d4:packages/corpus/src/address.ts` exports — `src` reads the source-aligned half of a relation and `dst`
the target-aligned one — and they are the only names of the addressing on the barrel.

What each member answers, in one line each:

- **`open`** — Iceberg's `StaticTable.from_metadata` for a URL, and the REST catalog's vended
  credential for a job. Two call shapes that differ only in where the bytes come from, and **both take
  the `Engine`**: the `query` callback that stood beside it is folded into the engine a host already
  has.
- **`tileMatrix(type)`** — the OGC `TileMatrixSet` for one vertex type: its extent, and one matrix
  per `z`, coarsest first, each listing **every tile with its row count and its box**. Synchronous,
  because it is the manifest bought at `open`, and total: `dense_id` is gapless and so is a rung's
  cell id, so no tile of any matrix is empty, and a view picks its zoom — the finest whose visible
  tiles' rows fit its budget — without a request.
- **`scan(params)`** — Iceberg's `Table.scan`: a type, a filter and a projection, **bound when it is
  built** — a column no matrix carries fails here, not on a read. No zoom and no box: a scan is
  built once per filter, not once per camera move.
- **`scan.plan()`** — Iceberg's `plan_files`: the tasks the scan needs **at every zoom**, pruned by
  the manifest's per-tile statistics and each carrying its residual. Synchronous for the same reason
  as `tileMatrix`. A filter naming a column cells do not carry has no task below `Z`.
- **`scan.read(addresses)`** — a columnar batch per address, in the order given, cancelled by one
  signal. It takes any address in the matrix, not only a planned one: a view builds `{ type, z, tile }`
  from what it sees, and the far end of an edge is the tile its `dense_id` shifts to. At `z = Z` a
  batch holds at most `tileRows` rows — 4,096 — so a finest tile can always be drawn as vertices.
  **How it addresses tiles**: DuckDB's Parquet reader reads no row group by number, so a statement
  names the tiles' file and ONE conjunctive range on the column their rows are a range of —
  `dense_id` at `Z`, `cell_id` below — which the engine prunes against every row group's statistics
  in the footer. Consecutive tiles of one zoom are one range, so **a run is one statement**, split
  back into a batch per tile on that column; tiles that are not consecutive are separate statements,
  never a disjunction. Under `rowgroups` the range is the run's row groups and no others; under
  `files` the files are the tiles. [The ruling](#a-read-does-not-cost-the-corpus) is below.
- **`edges({ from, direction })`** — an answer per tile of `from`, each the relations incident to it
  out of the half aligned on
  `direction`, **and the ones it declined, with fossil's `GapReason`**: `not-declared` for an
  orientation the corpus does not publish, `other-space` for a relation whose far end is another
  type, which is read only when `relation` names it. At `z = Z` a batch is the adjacency's two
  columns, and a tile the tile manifest lists no entry for is answered empty without a request;
  below it, the rung's quotient — `src_cell`, `dst_cell` and a `weight` — where the writer published
  one. **The quotient is undirected**, and the page said source-aligned: one row per cell pair, keyed
  and tiled on the pair's LOWER cell (`ac1801d4:crates/fossil-layout/src/layout/cells.rs, pair_edges`), so
  `src` reads the pairs whose lower cell is in the tile, `dst` is declined, and the pairs whose upper
  cell is in the tile are in the tiles below it. Mass is conserved either way, which is the
  obligation cells states; what the orientation costs is the view's, which draws a rung's lines from
  the tiles it holds and the ones below them.
- **`schema`, `relations`, `executeSql`** — unchanged: the verbs' introspection, what a SQL host registers, and the escape hatch behind `sql: 'allowed'`.

**Nothing else crosses.** The addressing a corpus is opened with — `CorpusAddressing` and its
family — and `QueryFn` are internal, and the engine is the one capability; a consumer that needs a
URL has outgrown a surface whose claim is that a corpus is a URL.

**What would reverse it.** A view question that cannot be answered by composing these members
without reading a byte twice. The test is kanzo-ui's showcase: if the graph code there cannot come
down to a provider over `scan` and `edges`, something is missing here, and it is added as a member
rather than as a second path.

### What a row carries at each zoom

At `z = Z` a row is a vertex: the payload's columns, of which `select` chooses, and its tile is
`denseId` over `tileRows`. `select` does not reach below `Z`: a cell row carries every cell column
whatever it names, because they are not a projection of the payload's and there is nothing of them to
choose.

Below `Z` a row is a cell, and its columns are the writer's, not a projection of the payload's
(`ac1801d4:crates/fossil-sinks/src/generated.rs, CELL_COLUMNS`): `cell_id`; `x` and `y`, **the centroid of
its members** — a mean weighted by membership, declared `derived` by `cell-member-centroid`; `count`,
how many vertices it holds; `internal`, the weight of the edges absorbed inside it; and `mode` and
`purity`, the majority value of **one** categorical and the share of the members holding it. Which
categorical is the tree's `mode_channel`, resolved against the type's `channels:`, and a channel's
`domain` is its value count over a writer's ordinal `0..domain` — which is the whole of what a
legend can be drawn from. So a view colouring by that channel colours a cell by `mode`; a view
colouring by any other column has no summary to colour with, and a view sizing by anything has
`count` and nothing else. `tileMatrix(type).mode` is that channel, resolved, so a view reads the
column to colour by off the set it already holds. **A cell summarises one channel and its membership,
and not the row.**

**What would reverse it.** A second channel the writer summarises. Then `mode` stops being one column
with one referent, and a cell row grows a pair per channel, each naming its own.

## What is taken from Iceberg, and where fossil departs

| Iceberg | fossil | taken or departed, and why |
| --- | --- | --- |
| `Catalog.load_table`, `StaticTable.from_metadata(metadata_location)` | `open(url, { engine })`, `open(job, { engine, host })` | **Taken.** A corpus has no catalog service, so the URL case is the static table; the job case reuses what [storage access](/docs/design/prior-art#storage-access) already took from the REST catalog — a vended credential scoped to one prefix. |
| `Table.schema()` | `corpus.types` | **Taken**, read off the bytes at `open` for the reason `ac1801d4:packages/corpus/src/open.ts, open` gives: the manifest declares three properties against seven columns on disk. |
| `Table.scan(row_filter, selected_fields, case_sensitive, snapshot_id, options, limit)` | `corpus.scan({ type, filter, select })` | **Departs twice.** No `snapshot_id`: a corpus is written once and never appended to, so there is one snapshot and nothing to name. **No `limit`**: a task is a tile, and a tile holds at most `tileRows` rows by construction, so every read is bounded by its address rather than by a clause. No zoom and no box either, though a camera always has both: a scan is planned once over every zoom, and which of its tasks a camera sees is the view's cull against the boxes `tileMatrix` publishes. |
| `EqualTo`, `In`, `IsNull`, `And`, `Or`, `Not`; `UnboundPredicate.bind(schema)`, `rewrite_not` | `Filter`, bound in `scan()` | **Taken**, including the timing: an unknown column is an error at bind, before anything is planned, and a `not` is pushed to the leaves as `rewrite_not` does. Spelled as JSON rather than classes so it crosses a worker boundary as it is. `StartsWith` and `IsNaN` are left out until something asks, and NaN is Iceberg's: not a literal, and matched by no comparison — the rendered SQL says `NOT isnan(x)` beside `x > v`, because DuckDB orders NaN above every number. Nulls are SQL's. |
| `plan_files()` → `FileScanTask { file, delete_files, residual }`; iceberg-rust adds `start`, `length`, `record_count` | `plan()` → `ScanTask { z, tile, rows, bbox, residual }` | **Departs on the unit.** A task is a **tile**, which under `container: rowgroups` is one row group — iceberg-rust's `start`/`length` split, not PyIceberg's whole file. No delete files: nothing is ever deleted from a corpus. The byte range stays inside the reader; a view keys on the address. |
| `_InclusiveMetricsEvaluator` over `lower_bounds`, `upper_bounds`, `null_value_counts` — *rows might match* | the planner over the tile manifest | **Taken as the pruning rule**: a tile is dropped only when its statistics prove no row can match, and a tile with no statistics for a column is kept. |
| `StrictMetricsEvaluator` — *rows must match*, which PyIceberg's planner does not use | `ScanTask.residual` | **Taken further than Iceberg takes it.** A tile whose bounds satisfy the filter outright carries a `null` residual and is read with no predicate beyond the range that selects it — except for a comparison on a float, which never settles: the manifest counts no NaN, because Parquet's footer does not, and Iceberg's `nan_value_counts` is the statistic that would let it. |
| `ManifestEvaluator` over the manifest list's partition summaries | the zoom | **Departs.** A corpus has no partitions; the only coarse cut is `z`, every `z` is planned, and the view picks among them. |
| `to_arrow()`, `to_arrow_batch_reader()` over the whole scan | `scan.read(addresses)`, a batch per task | **Departs.** There is no whole-scan read, because the unit a view caches and cancels is the task, and a batch comes back per task whatever was read together. iceberg-rust's reader streams per task too; fossil reads a run of consecutive tasks in one statement, because the statement is what costs a round trip and a footer. |

**The filter is data, not a SQL fragment**, and it is the filter language that was refused for
`read`'s `where` while `read` existed. The refusal does not transfer, because what it weighed is
different here. `where` was a query language beside `execute_sql`, buying read-time policy the
corpus has no chokepoint for. `Filter` buys **planning**: the planner evaluates it against statistics
before a byte is read, and a string cannot be evaluated without being parsed — which is the second
language again, spelled worse. It is rendered to SQL in one place, for one engine, and it carries no
`execute_sql` authority, so a view the hatch is closed to can hold one.

**What would reverse it.** Iceberg's shape stops fitting the day a corpus changes after it is
written — appends, deletes, a second snapshot. Then `snapshot_id` and delete files come back, and
with them Iceberg's own answer rather than an invention of ours. Short of that, a whole-scan read
comes back if a second consumer that is not a view — a batch job — needs one, and it would be a loop
over `plan()` in that consumer, not a member here.

## What is taken from OGC tile matrices, and where fossil departs

| 17-083r4 / 20-057 | fossil | taken or departed, and why |
| --- | --- | --- |
| `TileMatrixSet { id, crs, boundingBox, tileMatrices }` | `TileMatrixSet { type, coordinates, extent, tileMatrices }` | **Taken.** One set per vertex type. `coordinates` names the type's declared coordinate system ([where x and y come from](/docs/design/position)) where OGC names a CRS. `extent` is informative, exactly as the standard says `boundingBox` is: tiles are located by their own statistics, never by it. |
| `TileMatrix { id, scaleDenominator, cellSize, tileWidth, tileHeight, matrixWidth, matrixHeight }` | `TileMatrix { z, count, shift, tileRows, tiles }` | **Departs on the axis.** The matrix is one-dimensional: `tileRows` is `tileWidth` with `tileHeight` fixed at one, `tiles` is `matrixWidth` with `matrixHeight` at one, and `shift` plays `cellSize` — how many `dense_id`s one row at this `z` stands for, as a power of two. |
| tile address `(tileMatrix, tileRow, tileCol)`, `tileMatrix` a string id | `(type, z, tile)` | **Departs**, for the axis's reason. `z` is a number because it is compared and subtracted. |
| Annex I: tile indices from a bbox by arithmetic over `pointOfOrigin` and `cellSize` | every tile's box, published in the manifest and listed by `tileMatrix` | **Departs, and this is the one that is forced.** `dense_id` is a vertex's **rank** in the Hilbert order of its position, not its Hilbert code, and where a rank falls on the plane depends on how the positions are distributed — which no field of any matrix can carry. So the arithmetic that locates a tile runs on the rank axis, and which tiles a rectangle touches is read off the tiles' own boxes. |
| `tileMatrixSetLimits`: per matrix, the tile rows and columns that exist | a box and a row count per tile, in the manifest | **Taken and widened.** The standard publishes the range so a client does not compute it; a rank axis needs the box of every tile for the same reason. |
| WebMercatorQuad: matrix `z` is `2^z × 2^z`, four children per tile | the parent of `(z, t)` is `(z − 1, t >> (shift(z−1) − shift(z)))` | **Taken.** Between two rungs the difference is two bits — four children per tile, the quad tree's own branching. From the rows to the first rung it is the declared base, four bits at sixteen vertices per cell. |
| an out-of-range tile is a 404 or a 400 | `read` of an address outside `tiles` throws `CorpusReadError` | **Taken.** |

**What would reverse it.** A corpus whose positions sit on a grid a writer fixes in advance — a
raster, or a `geographic` plane quantised to a declared square — would make the rank and the code the
same number, and the Annex I arithmetic would then work unchanged. The published boxes would become
derivable, and a document carries a fact exactly when a reader cannot recover it, so they would go.

## The cell pyramid is the tile matrix

**The zoom levels are the pyramid that is already on disk**, and the arithmetic is the arithmetic
[cells](/docs/design/later/cells) decided, restated as matrices rather than rungs.

For a vertex type of `V` rows, a tile of `C` rows — `ac1801d4:crates/fossil-sinks/src/manifest.rs,
TILE_SHIFT` is 12, so 4,096 — and a declared base of `b = 2^B` vertices per cell
(`ac1801d4:crates/fossil-sinks/src/manifest.rs, DEFAULT_VERTICES_PER_CELL`, sixteen):

- **Rung `k` is matrix `z = R − k`**, where `R` is the rung holding a single cell, and the payload is
  **`z = Z = R`**. So `z = 0` is the root, one cell, and `z = Z` is every row — the standard's order,
  coarsest first.
- A row at rung `k` stands for `2^shift` ids, **`shift = B + 2(k − 1)`**
  (`ac1801d4:crates/fossil-sinks/src/manifest.rs, CellTree`), and a cell id is `dense_id >> shift`. At `z = Z`
  the shift is zero and a row is a vertex.
- Matrix `z` holds **`count = ceil(V / 2^shift)`** rows in **`tiles = ceil(count / C)`** tiles,
  because a rung is tiled at the type's own `chunk_size` and declares none of its own
  (`ac1801d4:crates/fossil-layout/src/layout/cells.rs, Pyramid`).
- **Tile `t` of matrix `z` is the contiguous `dense_id` range `[t·C·2^shift, (t+1)·C·2^shift)`.**
  Every tile at every zoom is an interval of one axis, which is what lets a single conjunctive range
  select it and lets its parent be a shift.

Three corpora, every figure derived from those four lines rather than measured:

| | com-DBLP, 317,080 | the bench corpus, 1,000,000 | 10,000,000 |
| --- | --- | --- | --- |
| `Z` | 9 | 9 | 11 |
| tiles at `z = Z` | 78 | 245 | 2,442 |
| rung 1 (`z = Z − 1`), cells · tiles | 19,818 · 5 | 62,500 · 16 | 625,000 · 153 |
| rung 2, cells · tiles | 4,955 · 2 | 15,625 · 4 | 156,250 · 39 |
| rung 3, cells · tiles | 1,239 · 1 | 3,907 · 1 | 39,063 · 10 |
| every tile at every `z` | 92 | 272 | 2,654 |

The last row is what the tile manifest holds, one entry per tile, and it is why publishing it is
cheap: at ten million vertices it is 2,654 entries, against the 4,892 footer reads an open costs
without it.

What is kept from [cells](/docs/design/later/cells) unchanged: the base is declared and never derived;
the partition is quaternary, so a cell carries no `parent` column; a rung is summarised from the
payload, never folded from the rung below; the quotient is one undirected row per cell pair, tiled on
the pair's lower cell's tile (`ac1801d4:crates/fossil-layout/src/layout/cells.rs, write_quotient`); and a cell
is not an entity, so no lookup by identity returns one.

**What would reverse it.** A base that is not a power of four. Then a rung's shift stops being an
integer number of bits and the parent stops being a shift — which is why
`ac1801d4:crates/fossil-sinks/src/manifest.rs, CellTree` refuses one — and the tile matrix would need a
`scaleDenominator` in earnest.

## The sample goes: below `Z` there are only cells

**Every `z < Z` is a rung, and the level files are retired**: `vertex/<Type>/l{k}/`, the relation
levels beside the adjacency, the plan that chose them and the two functions of the layout pass that
wrote them. A manifest declares its payload and its adjacencies, all at `scale: 1`, and
`ac1801d4:crates/fossil-layout/tests/layout_renumber.rs` lists everything the pass writes under a type.

This reverses a row of [what was discarded](/docs/design/discarded), and the row said what would do
it: *a reader that addresses a cell — or, failing that, those three readers going away.* Both
happened.

- **The three readers are gone.** A crossfilter mask indexed by `dense_id` and a residency pass that
  deduplicated answers taken at two levels were the playground and `@fossil-lang/draw`, deleted on
  2026-09-29. The third was `pinned`, which existed only on `frame`, and `frame` went with it.
- **A cell is addressable.** A cell id is `dense_id >> shift`, and `(type, z, tile)` names the tile
  holding it by the same arithmetic that names a payload tile. A view that pins a vertex holds its
  `dense_id`, and at any `z` the cell containing it is one shift away — the pin draws as its cell,
  with no second read.

**The edge argument is not answered by bytes, and it is paid.** An edge level was the only artefact
whose rows carried both endpoints' coordinates, so a coarse view could draw real edges off one file.
Below `Z` the lines are now the rung's quotient where the writer published one, and nothing where it
did not; a coarse view draws the field and not the relation, which is the conclusion
[cells](/docs/design/later/cells#no-coarse-quotient-is-drawable-and-the-partition-is-not-the-reason) had
already reached about every rung but the finest. What is bought is one multiscale structure instead of
two, and the bytes of the one that went: on com-DBLP the level pyramid is **83.1%** of
payload-plus-adjacency against the cell pyramid's **8.1%**.

**What would reverse it.** A view that needs a real row at a coarse zoom — something that clicks,
masks or brushes by `dense_id` where the rows at `Z` under the cell are too many to read. It is not
enough that a view wants to *identify* what is under a cell: the rows are one shift away, at `Z`,
and a view can read the tiles under one cell without reading the rectangle.

## The ten measured costs, and which ones the backend closes

These were measured on 2026-09-29 in kanzo-ui's reader over this package. Six are the backend's to
close, two are the view's, and two are closed by the shape of the contract rather than by any one
mechanism.

| # | the cost | closed by | whose |
| --- | --- | --- | --- |
| 1 | under `rowgroups` each slice read the whole vertex file and the whole `by_source` file | a task is one row group, selected by one conjunctive `dense_id` range | backend |
| 2 | an anchor CTE's `NOT (bbox)` scanned every vertex outside the window | no anchors: a far end is read by its tile's address | contract |
| 3 | the edge join was O(E) per slice, with no range predicate on `src_dense` | `edges({ from })` reads the aligned adjacency's rows for one tile's id range | backend |
| 4 | the same CTEs were computed twice per slice, once for points and once for links | points and edges are separate reads of separate tiles, each cacheable on its own | contract |
| 5 | `count(*) OVER ()` materialised the whole match before sampling | counts are the manifest's; nothing samples, because coarse is a lower `z` | backend |
| 6 | no tile cache: every pan re-asked the whole rectangle | answers are pure functions of an address, so the view caches by `(type, z, tile)` | view |
| 7 | superseded queries were not cancelled | `AbortSignal` on `read` and `edges`, handed to the engine | backend |
| 8 | opening cost a footer read over every payload file — 4,892 requests, 40 MB at ten million | the writer publishes every tile's statistics in the manifest | backend |
| 9 | every slice re-uploaded every GPU buffer and rendered twice | per-tile batches a renderer can append rather than replace | view |
| 10 | no `by_target` read: an edge whose source is off-screen was never drawn | `edges({ direction: 'dst' })` reads the target-aligned adjacency | backend |

### What the backend's half measures at a million vertices

Measured on 2026-09-29 over a corpus the layout pass wrote — `ac1801d4:crates/fossil-layout/examples/enrich_memory`'s
fixture, 1,000,000 vertices at mean degree 14 (6,993,608 edges), 4,096 rows a tile, pyramid base 16,
`rowgroups` — for a window of 1% of the extent, a tenth of it on each axis at its centre. The finest
zoom whose planned tiles fit 65,536 rows is `Z` itself: the box filter plans **8 of 245** payload
tiles, 32,768 rows, of which 9,265 are in the window, exactly the vertices `rows` returned. Bytes and
requests are every statement replayed through the `duckdb` CLI's `httpfs` against a local HTTP origin
that counts what it serves; times are medians of seven through DuckDB-WASM 1.32 over local files in
Node, Mac16,8.

| read | files | requests | bytes | time, WASM | time, native over HTTP |
| --- | --- | --- | --- | --- | --- |
| `plan()` | — | 0 | 0 | 0.8 ms | — |
| `scan` + 8 `read`s, 4 columns | 1 | 37 | 0.54 MB | 121 ms | 84 ms |
| `scan` + 8 `read`s, every column | 1 | 25 | 4.55 MB | — | 75 ms |
| `edges`, both halves of the 8 tiles | 2 | 51 | 2.36 MB | 126 ms | 131 ms |
| `rows` over the same box, as it was | 3 | 493 | 37.55 MB | 172 ms | 102 ms |

Cost #1 and #3 are the difference, and they are the adjacency: `rows` read its edges with an `IN`
over the window's ids and no range on the aligned column, so the engine read 17.5 MB of the 33 MB
`by_source` and 16.5 MB of `by_target` in 525 requests, where `edges` reads one row group of each per
tile. What the tiles do not buy is the vertex side at `Z`: the same 4.55 MB either way, in 25
requests over 8 statements against `rows`' 10 in one — each statement read the footer again and
could not coalesce ranges across tiles, which [a read does not cost the corpus](#a-read-does-not-cost-the-corpus)
closes — and the reads are sequential because a view keeps one in flight. The edge count
is the other half of the trade — the tiles' edges are every edge of the 8 tiles, 458,204, against the
91,652 incident to the window's vertices — and it is the view's to cull, per tile, once, and cache.

### Pruning is the manifest's, at tile granularity

A statement selects its tiles with **one conjunctive range** on the aligned column — `dense_id` for
a vertex tile, `src_dense` or `dst_dense` for an adjacency — and never a disjunction of them. That is
the one shape the engine is measured to prune row groups on. The identity lookup `node` (deleted after
`8326b8f`) measured DuckDB pruning a conjunctive range and declining a disjunction over a string
column, and `ac1801d4:crates/fossil-graph/src/lib.rs` records 179 `BETWEEN … OR …` ranges evaluated per row
rather than skipped — which is why a run of consecutive tiles is one read and two runs are two reads,
and not one read with an `OR`.

What the planner prunes with is the tile manifest: a lower and an upper bound for every ordered
column of every tile. `cluster_id` is the one worth naming — communities are placed together, so a
filter on it prunes tiles a camera would otherwise read. The box is in the same manifest and prunes
nothing here: which tiles a camera sees is the view's cull, against the boxes `tileMatrix` lists.

**What would reverse it.** An engine that prunes a disjunction of ranges, measured: then every tile a
window needs becomes one read and the per-run form costs round trips for nothing.

### The writer publishes what the reader used to read from footers

The reader used to read every tile's footer while the corpus opened, and did it there on purpose: a
level that arrived as a promise would be a request between the camera moving and an address being
computable. The rule survives and the cost does not. **The writer already has every number the footer
sweep recovered**, so it writes them once, beside the bytes, and `open` reads one file per type
instead of one footer per tile — `ac1801d4:packages/corpus/src/tile-manifest.ts, published` — and no footer at
all since the sweep's last readers, `rows` and `frame`, went.

It is a manifest in Iceberg's sense, and it is published: one JSON file per vertex type, named by the
type's `tile_manifest:` and written beside its tiles, listing every tile of every zoom — the payload
and each rung — with Iceberg's `record_count`, `null_value_counts`, `lower_bounds` and
`upper_bounds` (`ac1801d4:crates/fossil-sinks/src/tiles.rs, TileManifest`). The writer reads the numbers off
the footer each container closes rather than computing them twice, which is how Iceberg's own writers
fill one; bounds are published for every numeric column and for no string, and a tile's box is its
coordinate columns' bounds rather than a field of its own. The format is
[the tile manifest](/docs/design/later/addressing#the-tile-manifest-is-the-footers-published-once).

The edge sets are in it too, since `edges` landed: at the payload's `z` an entry per adjacency orientation cut
on the type's tiles, and below it each rung's quotient, numbered by the aligned tile because an edge
set's row-group ordinals skip where a tile of sources has no edges. `edges` is their first reader, and
an absent entry is a tile it answers without a request. **The byte range did not land, and the
section said it would**: DuckDB reads no row group by offset — a tile is one conjunctive range the
engine prunes against the footer it reads anyway — so an offset would be a field with no reader.
What would bring it is a host that issues its own `Range` request for a row group.

**What would reverse it.** A writer other than fossil's. The statistics are then a claim the reader
has to check rather than trust, and the check exists: `ac1801d4:packages/corpus/guards`' `tile-manifest` holds
the file against the footers read back from disk, tile for tile and bound for bound, and
`ac1801d4:crates/fossil-cli/tests/conformance.rs` holds a corpus `fossil run` wrote — payload and every rung —
against `parquet_metadata` the same way.

### Cancellation is a signal the engine honours

`read` and `edges` take an `AbortSignal` and hand it to the host's engine; a view that moved past its
tiles aborts them. One signal covers a call, so a view that wants to cancel one run and keep another
makes two calls. **The reader does not decide what is stale** — that is the view's cache — it only
makes a stale read stoppable.

**The signal has to reach the running query, not the queue.** A DuckDB-WASM connection runs one
statement at a time, so a view keeps one read in flight rather than deck.gl's six, and an abort that
only dropped queued work would leave the one read that matters — the running, stale one — to finish.
So `Engine.query` takes the signal and the host's engine interrupts the statement it is running —
[the ruling](#four-rulings-the-contract-rests-on) below, beside the Arrow-shaped answer.

**What would reverse it.** Reads short enough that cancelling costs more than finishing. A tile is
4,096 rows, so this is plausible, and it is one measurement: the wall time of a single-tile read
against the latency of a cancel on the host's engine.

## Four rulings the contract rests on

**A filter on a payload column has no task below `Z`.** A cell's `count`, `mode` and `purity`
summarise every member, so a view that filters the rows — a crossfilter brush — has no precomputed
answer at a coarse zoom, and `plan()` gives it none: the view gets rows or nothing. Recomputing the
rung from the rows at `Z` would read every row under the camera and make a coarse read cost what a
fine one does, which is the property the tile matrix exists to prevent.

**What would reverse it.** A view that needs the filtered field at a zoom where the rows do not fit —
a crossfilter brush over a corpus of ten million is the likely first — and a writer willing to
summarise per filter value, which is a second pyramid per channel rather than a reader-side fallback.

**Rows and cells cross only while loading.** A cell tile is drawn until the row tiles under it
arrive, and then it goes: the two are never on screen together at rest. That is the one crossing
[cells](/docs/design/later/cells) admits, and it is the same condition stated there. The backend's part is
that both are addressable in one matrix and a parent is a shift of its child; when to swap is the
view's.

**What would reverse it.** A reader measured to be lost at the swap — a click or hover that lands on
a cell and resolves to a row, or the reverse, while the two are both drawn — which would mean the
loading window is long enough to be interacted with, and the parent has to stop answering input
before it stops being drawn.

**Below `Z`, edges come only from the quotient.** The level files are retired, relation levels
included, so a coarse zoom draws the rung's quotient where the writer published one and no lines
where it did not. The argument is [above](#the-sample-goes-below-z-there-are-only-cells); this is
the ruling.

**What would reverse it.** A coarse view whose lines are measured to be what its reader needs and
which no quotient can draw — real edges between real vertices at a far zoom — which is the
self-drawing edge level coming back as a third artefact beside the cells, not as a second pyramid of
rows.

**`Engine.query` takes an `AbortSignal` and returns Arrow-shaped data.** The signal reaches the
running statement, and the answer is a table a `Batch` reads, so no reader turns columns into objects
and back. It is `ac1801d4:packages/types/src/engine.ts, Engine` now, with `Table` and `Column` beside it —
the part of apache-arrow's `Table` fossil reads — and every host in this repository moved with it.
DuckDB-WASM interrupts through the pending-query API: `AsyncDuckDBConnection.send` then
`cancelSent()`, and the blocking bindings' `startPendingQuery`, `pollPendingQuery` and
`cancelPendingQuery` underneath, which is what `ac1801d4:packages/corpus/tests/engine.ts` drives. Measured
there, a statement over twenty billion rows aborted at 50 ms rejects at about 200 ms — one polling
interval — and the connection answers the next statement. Hosts outside it — kanzo-ui's `engine()`,
keasy — moved with kanzo-ui's move onto the tile members.

**What would reverse it.** A host engine that can neither interrupt a statement nor answer in
columns. Then the reader converts at the boundary and drops a stale answer instead, and both costs
are measured rather than assumed.

## Where the tile manifest lives

**One file per vertex type, named from the type's YAML** — Iceberg's manifest-list-to-manifest shape,
`tile_manifest: tile-manifest.json` — and not inline in the YAML. It was decided by building both
behind a switch, measuring them, and deleting the loser.

Measured on 2026-09-29 over corpora the layout pass wrote (`ac1801d4:crates/fossil-layout/examples/enrich_memory`'s
fixture at mean degree 14, pyramid base 16, seven payload columns of which four are numeric), with the
manifest served over local HTTP and parsed the way the reader parses it: the YAML by
`fossil-graph-wasm`'s `Corpus`, the file by `JSON.parse`. Medians of 31 opens and of 31 verb calls,
Mac16,8, Node 23.

| | 1,000,000 | 3,000,000 | 10,000,000 |
| --- | --- | --- | --- |
| tiles at every zoom | 272 | 801 | 2,654 |
| inline: the vertex YAML | 130 kB | 358 kB | 1,156 kB |
| file: the vertex YAML · the tile manifest | 13 kB · 83 kB | 14 kB · 244 kB | 15 kB · 808 kB |
| open, inline — fetch and parse | 8.3 ms | 16.9 ms | 46.0 ms |
| open, file — fetch and parse both, **plus one round trip** | 5.4 ms | 5.9 ms | 14.2 ms |
| every `schema` or `execute_sql` call, inline | 4.6 ms | 12.9 ms | 56.7 ms |
| every `schema` or `execute_sql` call, file | 0.38 ms | 0.43 ms | 0.44 ms |

Two costs decide it and they point the same way above a million vertices.

- **Open.** The file costs one more serial request than inline — the path is in the YAML, so the
  manifest cannot be fetched beside it — and inline costs a YAML parse that grows with the tile count.
  At ten million the parse is 31.8 ms more than the file's, so the file opens faster over any link
  whose round trip is under about 32 ms, and the break-even rises with the corpus: it was 2.9 ms at a
  million and 11 ms at three. Gzipped the two transfers are within 7 kB of each other at ten million
  (75 kB against 69 kB), so bandwidth does not move it.
- **Every verb after it.** `fossil-graph-wasm`'s `dispatch_graph` loads the manifest set on every
  call, so an inline tile manifest is parsed again for every `schema` and every `execute_sql`:
  56.7 ms a call at ten million, against 0.44 ms. That cost is paid for the life of the corpus, and
  the file's round trip is paid once.

And a third that is not a timing: `DuckDB` reads JSON, so the guard that holds the file against the
footers is one SQL join in the `guards/` directory a stranger copies, where an inline block would need
a second YAML reader past `guards/manifest.mjs`'s one level of nesting.

**What would reverse it.** A reader that parses the manifest set once rather than per verb, together
with corpora whose tile count keeps the parse gap below one round trip on the links they are read
over — at ten million that gap is 32 ms, and a corpus read across an ocean has a longer trip than
that. Then one request fewer is worth more than the parse, and the entries move into the YAML under
the same four names.

## The id is a Hilbert rank

**`dense_id` is a vertex's rank in the Hilbert order of its quantised position, and the tile manifest
keeps one box per tile.** Ruled on 2026-09-30, on the investigation kanzo-ui's graph view asked for.
The curve is Wikipedia's `xy2d` at `n = 2^16` over the same binary32 quantisation the Z-curve used,
published with vectors on [addressing](/docs/design/later/addressing#the-arithmetic) and in
`corpus.bnf`'s gloss, and written by `ac1801d4:crates/fossil-layout/src/layout/hilbert.rs, hilbert2`. Nothing
reads both orders: every corpus is written again, and one written before the ruling fails
`hilbert-order`.

**The finding, as the view reported it.** A window holding about 5,000 vertices still drew cells:
the payload tiles whose boxes it intersected held more rows than the view's 20,000, so the finest
zoom that fit was a rung. And one payload tile cost about 230 ms, as three sequential statements —
`scan.read` and both halves of `edges`. The second half is [the next ruling](#a-read-does-not-cost-the-corpus).

### What a payload tile's box claims, measured

Measured on 2026-09-29 and again after the ruling by `ac1801d4:crates/fossil-layout/examples/tile_compactness.rs`
over three corpora of 1,000,000 vertices: the bench corpus kanzo-ui's view was built against, and
`enrich_memory`'s fixture at mean degree 14 through the real layout pass, in each order.
*Compactness* is a tile's box over the area its rows would cover on a uniformly filled extent — one
is a square of exactly its own rows. Windows are 400 squares centred on random vertices; *tiles
holding* counts the tiles that have a vertex inside the window, which is the best any box of any
shape can do with the same tiles.

| | kanzo-ui's bench, Z-curve | `enrich_memory`, Z-curve | `enrich_memory`, **Hilbert** |
| --- | --- | --- | --- |
| compactness p50 · p90 · max | 2.03 · 4.82 · 23.1 | 1.89 · 5.67 · 17.9 | **1.41 · 1.76 · 1.9** |
| ~5,000-vertex window: tiles hit p50 · p90 | 7 · 10 — 28,672 · 40,960 rows | 7 · 10 — 28,672 · 40,960 rows | **5 · 7 — 20,480 · 28,672 rows** |
| … tiles holding a window vertex p50 · p90 | 5 · 7 | 5 · 7 | 4 · 6 |
| 1% of the extent (~9,500 vertices): tiles hit p50 · p90 | 10 · 13 | 10 · 13 | **7 · 9** |
| … tiles holding a window vertex p50 · p90 | 8 · 10 | 8 · 10 | 7 · 9 |
| the `spatial-tiles` guard's mean box share | — | 1.13% | 0.57% |

The archive corpus is 1,543 vertices, one tile, and has nothing to measure; com-DBLP was not rebuilt.

**The boxes were not wide in the sense the report meant.** The median tile was twice its own area,
not the extent, and the `spatial-tiles` guard's bound of one half is two orders of magnitude away.
But a window opened 1.4× the tiles that hold its vertices at the median and at p90, and that was the
geometry's share of the cost.

### Where it came from

**`dense_id` was already a pure curve rank**, and the community-major order is not a second sort
underneath it. On all three corpora the written order is exactly the order of the recomputed codes —
the `hilbert-order` guard's rule — and the groups come out contiguous because
`ac1801d4:crates/fossil-layout/src/layout/place.rs, cluster_layout` gives each one an aligned block of the
quaternary, and an aligned block is one interval of codes on either curve. So there was no community
order to trade away for a spatial one: they are the same order by construction.

**It was not outliers.** Trimming each tile's box to its 1st–99th percentile moved compactness from
1.89 to 1.84 at the median and from 5.67 to 4.6 at p90; the phyllotaxis discs are compact, and no
tile is inflated by a few members placed far away.

**It was the Z-curve.** A run of 4,096 ranks that crosses a quad boundary at depth *d* leaves one
quad at its far corner and enters the next at its near one — the Z's diagonal — so its box is the
hull of both. Of 245 tiles, one straddled the root split, six a depth-1 boundary and 24 a depth-2
one; all five tiles above 10× were among the first seven. The same jump is the residue
[position](/docs/design/position) named — *the Z-curve makes long jumps at the boundaries of the
large quads* — seen from the tile's side instead of the cell's.

**And the rest is the tile, not its box.** A window of *N* vertices over a uniformly filled plane
touches about (√*N*/64 + 1)² tiles of 4,096 however they are drawn: for 5,000 that is 4.4 tiles,
18,000 rows. The *tiles holding* row says the same from the data — four or five at the median — so
**no box, however tight, puts every 5,000-vertex window under a 20,000-row budget at this tile
size**. That half of the finding is the view's: a budget of 20,000 rows is four tiles, and a budget
in rows has to be stated against the tile granularity.

What the geometry's half did to that budget was larger than the medians suggest, because a view
falls back to a rung whenever a window lands badly. The share of 300 windows, centred on random
vertices of `enrich_memory`'s fixture, whose intersected tiles exceed 20,000 rows — the last line
`tile_compactness` prints:

| window | ~385 vertices | ~855 | ~1,500 | ~2,350 | ~3,400 | ~5,000 |
| --- | --- | --- | --- | --- | --- | --- |
| Z-curve | 26% | 44% | 56% | 72% | 85% | 91% |
| **Hilbert** | **0%** | **2%** | **7%** | **18%** | **38%** | **58%** |

Under the Z-curve a window of a few hundred vertices drew cells one time in four, because it only
had to touch one tile that straddled a large quad.

### The options, measured

Every row over `enrich_memory`'s fixture, the ~5,000-vertex window, p50 · p90. The sub-box and
quadtree rows were simulated over the corpus the Z-curve wrote; the Hilbert row is the pass itself.
The ones not taken are on [what was discarded](/docs/design/discarded), each with what would bring
it back.

| option | tiles hit | rows read | what cells keep | what it costs |
| --- | --- | --- | --- | --- |
| the Z-curve's rank, 4,096 rows | 7 · 10 | 28,672 · 40,960 | — | — |
| up to four boxes per tile, cut at the tile's largest Z jumps | 5 · 7 | 20,480 · 28,672 | unchanged, and so is the rung-1 cell area spread of 5,030× | `TileInfo.bbox` becomes a list, four boxes per tile in the manifest and its guard, and the view culls against a union |
| sixteen equal sub-boxes per tile | 6 · 9 | 24,576 · 36,864 | unchanged | the same, sixteen boxes |
| tiles cut on quad boundaries — quadtree leaves of at most 4,096 | 4 · 7 | 14,742 · 22,022 | **breaks** `tile = dense_id >> 12`: 364 tiles of 3,656 rows at the median, so a tile stops being arithmetic and cells stop nesting in tiles | the addressing becomes a table |
| **the Hilbert rank, 4,096 rows** — taken | **5 · 7** | **20,480 · 28,672** | every `cluster_id` one run (995 of 995); the share of cells spanning two clusters identical at every rung; rung-1 cell area spread **5,030× → 428×**, rung 3 **571× → 21×**, rung 6 **11× → 3×** | the order the format publishes, its vectors and guards, and every conformance corpus regenerated |
| 1,024-row tiles, Z-curve · Hilbert | 15 · 19 and 11 · 14 | 15,360 · 19,456 and 11,264 · 14,336 | cells nest in tiles to 4⁵ | four times the statements, at a per-statement cost measured below to grow with the corpus |

**Hilbert is the only row that is a change to the order rather than to what is published about it.**
Every aligned `2^k` square is one interval of `4^k` Hilbert indices exactly as it is of Z-curve codes,
so the whole quaternary argument survives: a group's block is still one run, a cell is still
`dense_id >> shift`, and a tile is still `[t·4,096, (t+1)·4,096)`. What changes is the one thing the
Z-curve got wrong — an interval that is *not* an aligned square is edge-connected on a Hilbert curve,
so its hull is never far from its area. It closes the geometry's share: tiles hit is tiles holding
plus one at the median and at p90, and equal to it at 1% of the extent. And it buys the cells more
than the tiles: the jump residue [position](/docs/design/position) could only name is gone, and a
coarse rung is within 3× of uniform area.

The sub-box row matches it on this window and is the Iceberg-shaped answer — tighten the statistics
so pruning works. It is not taken because it publishes a second geometry to describe a first one
that is worse than it needs to be: it widens the contract, quadruples the boxes a guard has to hold,
and leaves every rung's cells as uneven as they are.

**What it cost, paid in one change.** The writer's two functions —
`ac1801d4:crates/fossil-layout/src/layout/hilbert.rs, hilbert_codes` codes with `hilbert2`, and
`ac1801d4:crates/fossil-layout/src/layout/place.rs, cluster_layout` walks its frontier along the same curve,
taking a block's corner from its alignment because Hilbert enters a block at whichever corner its
orientation puts first (reading the first cell put 24,570 ids inside foreign groups, and
`ac1801d4:crates/fossil-layout/tests/cells.rs, a_cluster_is_one_run_of_dense_id` caught it). The format: the
rule on [addressing](/docs/design/later/addressing#the-order-that-makes-an-interval-mean-something),
`corpus.bnf`'s gloss, and `vectors.json`'s `hilbert2` table where `morton2` was — written by
`ac1801d4:crates/fossil-layout/examples/hilbert_vectors.rs` from the writer's own curve and held against it by
a Rust test, because a curve is exactly the arithmetic Iceberg publishes vectors for and PMTiles left
every port to re-derive ([prior art](/docs/design/prior-art#the-corpus-and-how-a-format-ships)).
`guards/arithmetic.mjs` carries the function and `guards.mjs` sixteen unrolled steps of SQL for the
`hilbert-order` guard. `ac1801d4:packages/corpus/conformance/corpus` was regenerated from its recipe and every
test corpus is written through the pass. kanzo-ui changes no view code — it culls against the boxes
it is handed, and they are tighter — and rebuilds its bench corpora; its row budget is its own call,
which the floor above bounds.

**What would reverse it.** A reader that computes which ids a rectangle holds from the codes
themselves rather than from published boxes — BIGMIN/LITMAX over a Z-curve is a few bit operations,
and its Hilbert equivalent is a state machine a port would have to get right. No reader here does
that since [the anchor was discarded](/docs/design/discarded); a corpus whose positions sit on a
writer-fixed grid, the reversal named under the OGC table above, would be the one that asks. Or a
measured corpus on which Hilbert tiles are not tighter than the Z-curve's, which would mean the gain
here is this placement's rather than the curve's.

That anchor's own row named the condition that would bring it back — *a read where the 13% is the
difference between fitting a budget and not* — and this was that read: at a 5,000-vertex window the
over-read was 1.4×, and it was the difference. It does not come back, because the curve closes the
gap the anchor would have closed, with no second index.

## A read does not cost the corpus

**`scan.read` and `edges` take a list of addresses and answer one batch per address, and a run of
consecutive tiles of one zoom is read as one statement with one conjunctive range, split back into
batches on the aligned column.** And **a host's engine caches Parquet metadata** —
`SET parquet_metadata_cache = true`, once — which `ac1801d4:packages/types/src/engine.ts, Engine` now says a
host should, beside the interrupt it already requires. Ruled on 2026-09-30.

### Three statements a tile, and what they actually cost

The same nine tiles a ~5,000-vertex window at the centre of kanzo-ui's bench corpus opened under the
Z-curve, with both halves of their edges: 591,937 rows. *A* was the contract as it stood — three
statements a tile. *B* folds a tile's three into one `UNION ALL BY NAME`; *C* one statement per part
across the nine; *D* one statement for the window; *E* one statement per part with each run of
consecutive tiles read as one conjunctive range. DuckDB-WASM 1.32 in Node over local files, medians
of seven; native DuckDB 1.5 over HTTP against a local origin that counts, medians of five, and again
with 10 ms added to every response.

| shape | statements | WASM | WASM, metadata cached | HTTP: requests · MB · ms | HTTP, metadata cached | HTTP at 10 ms · cached |
| --- | --- | --- | --- | --- | --- | --- |
| A — three a tile | 27 | 194 ms | 88 ms | 108 + 27 HEAD · 6.17 · 259 | 54 · 2.45 · 106 | 1,711 · 689 ms |
| B — one a tile | 9 | 217 ms | 112 ms | 108 + 27 · 6.17 · 254 | 54 · 2.45 · 116 | 1,732 · 698 ms |
| C — one a part | 3 | 200 ms | 96 ms | 108 + 3 · 6.17 · 209 | 54 · 2.45 · 106 | 1,478 · 688 ms |
| D — one | 1 | 216 ms | 114 ms | 108 + 3 · 6.17 · 222 | 54 · 2.45 · 111 | 1,560 · 692 ms |
| E — one a part, runs coalesced | 3 | **109 ms** | **52 ms** | 84 + 3 · 4.52 · 118 | 54 · 2.45 · **60** | 811 · **384 ms** |

**Merging statements buys nothing.** B, C and D read exactly the requests and bytes A does, and are
no faster: every `read_parquet` branch plans its own scan and reads its own footer, one statement or
many. The 230 ms the view measured was round trips — at 10 ms a request, A is 190 ms a tile — and
two things make them, neither of which is the statement count.

**The footer is read again by every statement, and it grows with the corpus.** Without the metadata
cache, 3.7 of A's 6.17 MB are footers: the payload's is 176 kB at a million vertices and **2.24 MB
at ten million**, because the container is one file with a row group per tile and the footer lists
every one. Cached, it is still planned against: natively a vertex statement costs 1.3 ms at a
million and **14.7 ms at ten million** with the metadata already in memory, 26.3 ms without — against
0.66 ms for the same statement over a file of 64 row groups. At ten million the same nine tiles cost
**2,960 ms** in WASM as A, 1,754 ms cached, and 958 ms cached and coalesced. A tile read is O(*V*),
and that is the container's, not the curve's.

### What the two rulings do together, measured

After both, over `enrich_memory`'s fixture at a million vertices in each order, `rowgroups`: a square
at the centre of the extent holding about 5,000 vertices (5,019 under the Z-curve, 5,027 under
Hilbert), the exact statements the reader issues run through DuckDB-WASM 1.32 in Node over local
files, medians of seven after a warm-up. *Runs* is how the window's tiles fall along the id axis;
over 300 random ~5,000-vertex windows the Z-curve's tiles fall in 3 runs at the median and 5 at p90,
Hilbert's in 2 and 3, so the two rulings compound.

| shape | Z-curve (7 tiles, 5 runs): statements | ms, uncached → cached | Hilbert (6 tiles, 3 runs): statements | ms, uncached → cached |
| --- | --- | --- | --- | --- |
| vertices, a statement a tile | 7 | 84.1 → 25.9 | 6 | 78.7 → 22.9 |
| vertices, a statement a run | 5 | 59.0 → 18.6 | 3 | 37.5 → 11.7 |
| edges, both halves, a statement a tile | 14 | 78.5 → 42.0 | 12 | 68.8 → 38.7 |
| edges, both halves, a statement a run | 10 | 60.2 → 31.6 | 6 | 35.3 → 20.1 |
| **the window, a statement a tile** | 21 | 162.1 → 70.0 | 18 | 141.9 → 60.2 |
| **the window, a statement a run** | 15 | 115.8 → 52.0 | 9 | 71.6 → **33.4** |

The cache is 2.3× on its own; runs are another 1.35× under the Z-curve and 1.8× under Hilbert,
because the curve puts the same window in fewer of them. The window the view reported at 230 ms a
tile, read the way it is read now, is **33.4 ms for all six** — 4.9× below the same window under the
Z-curve, uncached, a statement a tile. `edges` takes addresses for the same reason `read` does: its
half of the window halved, 38.7 → 20.1 ms.

### One signature, and why it is not a `readRun`

`read(addresses)` replaces `read(address)` rather than standing beside it, and one tile is a list of
one. A `readRun` next to `read` would be two ways to read a tile, and it would put the run in the
view's hands — a view would have to know which of its tiles are consecutive, which is arithmetic
over the matrix and the reader's. The answer stays **a batch per address**, so the unit a view
caches and cancels is still `(type, z, tile)`, and nothing about the seam in
[three layers](#three-layers-and-what-each-owns) moves: how tiles are grouped into statements is a
fact about the engine, and it stays under the reader.

Inside the reader: addresses are grouped by zoom — by edge set, for `edges` — and sorted, and each
maximal run of consecutive tiles is one statement. A tile whose statistics exclude it answers empty
with no request and breaks the run; a run whose tiles carry different residuals is read under the
scan's whole filter, which selects the same rows on each. The aligned column is selected whether or
not the scan named it, the answer is cut at `key / span`, and a column the scan did not select is
dropped from each batch. `ac1801d4:packages/corpus/tests/scan.test.ts` holds a run as one statement with one
range and no `OR`, every batch of a run against the same tile read alone, and an abort mid-run.

**What would reverse it.** A host engine that shares footers across statements without being told
to, which makes the cache a no-op; a DuckDB that prunes a disjunction of ranges, which makes a whole
window one statement and a run an unnecessary grouping; or a view that has to cancel one run of a
call and keep another often enough that one signal per call is the wrong grain.

### What neither ruling touches: the container

**The container stops being one file per type** is the only lever that makes a tile read O(1)
rather than O(*V*). The one-file ruling was measured on whole-window reads, 5.6 range requests
against 22.3 at five million, and whole-window reads no longer exist; a file per `z − 3` tile, 64
row groups, is the obvious candidate. **Not ruled**: it wants its own end-to-end measurement over
HTTP, opens and all, before it is argued.
