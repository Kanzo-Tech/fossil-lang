Two things are missing between a shape and a reader, and they are the same thing at two levels. A
reader that draws a graph has no word for a type or a field but the program's identifier — `birthDate`
where a person reading Spanish wants *fecha de nacimiento*. And a value that *is* a word in a language —
a laureate's name as it is written in Polish — has no place for its language at all: the catalogue had
`core.lang(value, tag)`, and it went because the tag type-checked and was dropped.

Both are solved problems in RDF, and this page takes the solutions as they are. **A label is a ShEx
annotation, a predicate and an RDF object** — `// rdfs:label "birth date"@en` in ShExC. **A string in
a language is an `rdf:langString`**, a lexical form and a BCP 47 tag. Nothing here is built; the
grammar is written, ahead of the parser as [the grammar](/docs/book/grammar) always is —
`grammar.bnf, DeclAttrs`, `grammar.bnf, AnnotationAttr` and `grammar.bnf, LANG_STRING` — and this
page is why it is shaped as it is and what it costs.

## What an annotation is

ShEx 2.1 defines it, §5.9 *Annotations*:

> Annotations provide a format-independent way to provide additional information about elements in a
> schema. They appear in lists in Shape, OneOf, EachOf and TripleConstraint's annotations.
>
> `Annotation { predicate:IRIREF object:objectValue }`

and §5.9.1: «Annotations do not affect whether a node conforms to some shape. Because they are part of
the structure of the schema, they can be parsed in one ShEx format and emitted in that format or
another.» ShExC writes one after a triple constraint or after a shape's closing brace, production
[58] `annotation ::= "//" predicate (iri | literal)`.

SHACL has the same idea under another name, the *non-validating* properties of §2.3.2: «properties
that are ignored by SHACL processors … They MAY be used for purposes such as form building or
predictable printing of RDF files.» §2.3.2.1 gives the two a label needs:

> Property shapes may have one or more values for `sh:name` to provide human-readable labels for the
> property in the target where it appears. If present, tools SHOULD prefer those locally specified
> labels over globally specified labels at the `rdf:Property` itself. … Both `sh:name` and
> `sh:description` may have multiple values, but should only have one value per language tag.

So the shape of the thing is decided twice over, and it is a pair: a predicate IRI, and an object that
is an IRI or a literal, the literal possibly language-tagged. There is no `label` field anywhere in
either standard; a label is the pair whose predicate is a labelling one.

**What would reverse it:** a reader that needs from a label something a predicate and an object cannot
say — a label that varies by the *mapping* rather than the type, say. Then the annotation grows a
qualifier, and it is still an annotation.

## Writing one in Fossil

```
@iri("https://schema.org/Person")
@annotation("http://www.w3.org/2000/01/rdf-schema#label", "Nobel laureate"@en)
type Laureate
    @iri("https://schema.org/name")
    name: Seq<LangString>

    @iri("https://schema.org/birthDate")
    @annotation("http://www.w3.org/2000/01/rdf-schema#label", "birth date"@en)
    @annotation("http://www.w3.org/2000/01/rdf-schema#label", "fecha de nacimiento"@es)
    birthDate: Date
```

**`@annotation(predicate, object)`** is ShExC's `// predicate object` in this language's attribute
form: the attribute namespace is where a declaration's metadata already lives (`@iri`), and the
argument pair is ShExJ's `{ predicate, object }` in order. It goes where `@iri` goes — above a type,
before a field — and any number of times; `@iri` stays exactly one. **The name is `@annotation`**,
ShEx's own noun for the thing (§5.9), beside the two nouns the language already has, `@iri` and
`@subject`; a verb, `@annotate`, would be the one attribute named for what the writer does rather than
for what the declaration carries.

**Attributes stack.** A field with one attribute keeps it on its own line (`@iri(…) name: String`, as
[Types declared in the program](/docs/design/declared) shows); a field with several writes them on the
lines above it, F#'s attribute on its own line — the same F# form the field's line already cites — and a
blank line between fields is the lexical layer's, which never touches the indentation. That is the
only change to the body, and it is `grammar.bnf, DeclAttrs`. The body stays indented: braces and
commas are [discarded](/docs/design/discarded) for a declaration with the reason
[Types declared in the program](/docs/design/declared) gives, and nothing here reopens it.

**The predicate is a whole IRI, in a string.** Fossil has no `PrefixDecl`, and every other IRI a program
writes is whole for the reason the declared-types page gives: a name nobody wrote never becomes an IRI.
`"rdfs:label"` would not even fail on its own — it is a well-formed absolute IRI whose scheme is
`rdfs` — so the checker refuses a predicate whose scheme is a prefix of the W3C's
[RDFa Core Initial Context](https://www.w3.org/2011/rdfa-context/rdfa-1.1), naming the IRI it
abbreviates, and the same check holds `@iri`. **There are no prefixes**, and that is decided:
expanding through that context would be a rule about strings that look like something else, and the
context maps `schema:` to `http://schema.org/` while every program here writes `https://schema.org/`,
so the expansion would mint a different IRI from the one the program means
([discarded](/docs/design/discarded)).

**The object is a literal.** A plain string is `xsd:string`, and `"…"@en` is a language-tagged one,
the `LANG_STRING` token: Turtle's, SPARQL's (production [145] `LANGTAG`) and ShExC's spelling, with the
`@` touching the quote, as a Rust literal's suffix is part of the literal. Neither carries a hole: an
attribute's argument is a constant, JLS §9.7.1's rule and the reason `@subject` left the attribute
form. The tag is checked well-formed by BCP 47 §2.2.9 at compile time. An IRI object and a typed
literal are not spelled ([discarded](/docs/design/discarded)).

**What would reverse it:** programs where the annotation lines are most of the text — then a
`PrefixDecl`, explicit and in the program, comes back for annotations' predicates, as `@base` would
for `@iri`; never an implicit context.

## Reading one from a shape document

**ShEx.** `shex_ast` parses annotations on a shape and on a triple constraint into its AST
(`Shape::annotations`, `TripleExpr::TripleConstraint { annotations, … }`), and `fossil_hir::shex`
walks that AST already (`crates/fossil-hir/src/shex.rs, ShapeBinding`) and drops them. Reading them
is carrying them: a shape's onto the type, a triple constraint's onto the property or the relation it
lowers to. `EachOf` and `OneOf` annotations are not carried, because a group is not a type, a field or a
relation — and `OneOf` is refused anyway. One finding constrains the
[declared-types direction](/docs/design/declared): `shex_ast` 0.3.1's conversion from the AST to its
compiled `SchemaIR` drops every annotation (`cnv_annotations` in `ast2ir.rs` is a `TODO` that returns
an empty list), so a decoder written as a `TryFrom` over `SchemaIR` loses them until rudof fills that
in. The reading stays on the AST.

**SHACL.** `crates/fossil-hir/src/shacl.rs, decode_shacl` reads a shape's triples into the same pair:
on a property shape, `sh:name` and `sh:description`, SHACL's own two, as `rdfs:label` and `rdfs:comment`; on any shape, every triple whose
predicate is outside SHACL's namespace and is not `rdf:type` — `rdfs:label`, `rdfs:comment`,
`skos:prefLabel` — because §2.3.2 says a processor ignores them and ShEx admits any predicate.

**`sh:name` is read as `rdfs:label`.** A field's label has one predicate in the corpus whichever
document it came from: a ShEx shape writes `// rdfs:label "…"`, a program writes
`@annotation("…rdf-schema#label", …)`, and a SHACL property shape's `sh:name` becomes the same
annotation, its object — language tag and all — unchanged. So a reader asks for one predicate and
never carries a preference list between two words for one thing, and the three sources of a label
meet in the decoder, once, rather than in every reader. On a property shape that writes both, both are
kept, `sh:name`'s first: SHACL §2.3.2.1 says a tool SHOULD prefer the locally specified label, and
first is the one a reader that takes one per language takes. **`sh:description` is read as
`rdfs:comment`** by the same argument, ISSUE-112's twin: one predicate for a description whichever
document wrote it, `sh:description`'s first where a shape writes both.

The cost is the distinction the Shapes WG drew. Its
[ISSUE-112](https://www.w3.org/2014/data-shapes/track/issues/112), raised 2015-11-05, was that SHACL's
draft let a property constraint carry an `rdfs:label` «to provide a human-readable label for the
property in the scope where it appears», while RDFS says `R rdfs:label L` «states that L is a human
readable label for R» — for the *shape*, not the property in a context — and the group closed it by
inventing `sh:name`. Inside a corpus that distinction has nothing to hold on to: an annotation there is
already scoped to the column it sits on, never stated about the predicate IRI (it makes no triple, as
below), so `rdfs:label` on a column *is* the local name ISSUE-112 wanted, and the shape it would have
labelled is not in the corpus at all. The counter-argument is recorded with what brings it back on
[what was discarded](/docs/design/discarded).

**What would reverse it:** a consumer that reads the corpus's annotations back *as a shapes graph* —
a SHACL engine, or [the ShEx round trip](#back-out-as-shex) carried to SHACL — where the annotation is
again about a shape and `rdfs:label` again means the shape's label. Then the predicate is kept as the
document wrote it, and the normalisation moves into the reader that wants one word.

## In the corpus

`fossil.json` gains `annotations` on a vertex table (the type's), an edge table (the relation's, from
the `Ref` field that declares it), and a column's `properties` entry (the field's) — and so on a
property table's value column, which already carries the field's `iri`. Each entry is ShExJ's
Annotation, with one word changed:

```jsonc
"annotations": [
  { "predicate": "http://www.w3.org/2000/01/rdf-schema#label",
    "object": { "value": "fecha de nacimiento", "language": "es" } }
]
```

`object` is ShExJ's `objectValue`: an IRI is a bare string, a literal is `ObjectLiteral`,
`{ value, language?, datatype? }`. ShExJ calls the datatype IRI `type`; `fossil.json` calls it
`datatype`, the word a column already uses for the same IRI, so one document has one word for one
thing and `type` keeps meaning the column's storage type. A program's annotations only ever produce
the two literal forms; a document's may carry the others, and they pass through.

**What would reverse it:** a consumer that reads `annotations` as ShExJ unchanged — then the word is
ShExJ's and the column's `datatype` is the one that moves.

**It is `fossil/1`, changed in place.** The field is optional and absent when there is nothing to say,
and the reader that reads it ships in the same release as the writer that writes it — the rule
[the corpus](/docs/design/corpus#one-format-changed-in-place) now states for every change to the
format, this one and the language column below alike.

**Annotations are not triples.** `triples` is the corpus's data as RDF; an annotation is about the
schema. Writing `schema:birthDate rdfs:label "fecha de nacimiento"@es` would state a *global* label of
the predicate from a *local* one, which is ISSUE-112 again in the other direction.
`@fossil-lang/corpus` attaches them as a relation of their own beside `fossil_tables` and
`fossil_columns`: `fossil_annotations(table_name, column_name, predicate, o_type, o_value, o_datatype,
o_lang)`, `column_name` null for the table's own, the object in the four columns `triples` already
spells a term in.

**What would reverse it:** a consumer that needs the schema as RDF — a SHACL engine reading the shapes
graph back from the corpus. Then it is a second relation of triples about the shapes, never mixed into
the data's.

## Back out as ShEx

Fossil writes no ShEx today. When a declared type is converted onto rudof's types — the
[declared-types direction](/docs/design/declared) — an annotation is `shex_ast`'s `Annotation`, and
`shex_ast`'s compact printer already prints one as `//` after its triple constraint or its shape
(`ShExCompactPrinter::pp_annotation`). The round trip is then `@annotation` → `fossil.json`'s
annotation → `// predicate object`, with one key renamed on the way, a literal's `datatype` back to
ShExJ's `type`.

## Language-tagged strings in the data

### The type is `LangString`

ShEx and SHACL both write the type as a datatype, `rdf:langString`: ShEx 2.1's own example is
`ex:IssueShape { rdfs:label rdf:langString }`, with the note that «in RDF 1.1, language-tagged strings
have the datatype `rdf:langString`»; SHACL writes `sh:datatype rdf:langString` and constrains the tags
with `sh:languageIn`, §4.4.4, «a list of basic language ranges as per [BCP47]». So the primitive is
named for that datatype's local name, as `AnyUri` and `GYear` are for theirs: **`LangString`**, the
tenth primitive of `crates/fossil-graph-schema/src/lib.rs, Primitive`, written as `rdf:langString`.
`Option`, `Seq` and a bare `LangString` mean what they mean for any primitive; a multilingual name is
`Seq<LangString>`.

Read from a document: a ShEx `rdf:langString` datatype, or a value set of languages (`[@en @es]`,
`[@en~]`), is `LangString`; a SHACL `sh:datatype rdf:langString` is too, and `sh:languageIn` becomes
the property's `languages`, a list of basic language ranges in the neutral vocabulary
(`crates/fossil-graph-schema/src/shapes.rs, PropertyConstraint`). ShEx's language stems and SHACL's
list are one thing: both match by RFC 4647's basic filtering. Today a ShEx `rdf:langString` reads as
`String`, so a program that maps a plain string into one stops checking — the
[property-mismatch](/docs/errors/type/property-mismatch) it should always have been.

### The mapping: a literal, and `str.lang`

R2RML gives a constant tag, §7.5:

> A term map with a term type of `rr:Literal` MAY have a specified language tag. It is represented by
> the `rr:language` property on a term map. If present, its value MUST be a valid language tag.
>
> `[] rr:objectMap [ rr:column "DNAME"; rr:language "en-us" ].`

RML adds a tag read per row, §6.5: «A language map is represented by the `rml:languageMap` property on a
term map. If present, its value must be a term map. The value generated by the language map is used as
a language tag on the created term.»

In Fossil both are **one catalogue row, `str.lang(text: String, tag: String) -> LangString`**, reached
as a member call: `PrizeRow.motivation.lang("en")` is `rr:language`, and
`NameRow.name.lang(NameRow.lang)` is `rml:languageMap`. A tag is an ordinary argument, so it is a
constant or a column with no second form, and the verb is a row and not a rule. The name is SPARQL's:
`STRLANG(lexicalForm, langTag)` (SPARQL 1.1 §17.4.2.11) constructs exactly this term, and in Fossil the
`str.` namespace already is the `STR`. It replaces `core.lang`, which lowered to its first argument
because there was nowhere to put the second.

**A constant is the literal.** `"Nobel laureate"@en` in an expression is a constant `LangString`, the
same token an annotation's object is. `"Nobel laureate".lang("en")` would be a second spelling of it,
and is refused naming the literal — the rule [`needless-quotes`](/docs/errors/syntax/needless-quotes)
already applies to a quoted member. An interpolated string takes no tag; its tag is the call's.

**What would reverse it:** a tag that cannot be a `String` expression — RML's precedence, where a
language map that yields no valid tag falls back to `rr:language`. Then `lang` grows a named
fallback argument; it does not become a second function.

### The corpus: a language column

**A `LangString` property is always a property table**, whatever its cardinality, of three columns:
`src`, the value under the property's name, and **`lang`**, with a new role, `language`, in
`corpus.bnf`:

```
col lang = in property ; type string ; role language .
```

on the property tables of `LangString` properties only. The value column carries `term_type`
`rr:Literal` and `datatype` `rdf:langString`, the shape's verbatim. A property table is where the tag
has a fixed column name: on a vertex table it would need a name minted from the property's, which is
the compiler naming something nobody wrote. And one value per language is the ordinary case, not the
exception — SHACL §2.3.2.1 says `sh:name` «should only have one value per language tag» — so a
language-tagged property is multi-valued in practice even when each language has one.

**It is `fossil/1`, and the reader changes with the writer.** A reader that did not know `lang`
would read the value column, see `datatype` `rdf:langString` and write a literal with no tag — which
RDF 1.1 Concepts §3.3 forbids («if and only if the datatype IRI is `rdf:langString`, a non-empty
language tag»). That is not answered by a second format string and a reader that branches on it. It is
answered by the reader that knows `lang` — `@fossil-lang/corpus`'s `triples` and the guards — shipping
in the same release as the writer that writes it, which is the only way a corpus reaches a reader
today; [the corpus](/docs/design/corpus#one-format-changed-in-place) argues the rule and says what
would bring a second version back. A corpus with no `LangString` property is byte for byte what it
was.

### The RDF view

`triples` emits a `LangString` value as `o_type` `L`, `o_value` the lexical form, `o_datatype`
`rdf:langString` and `o_lang` the row's `lang` — where `o_lang` was always `''` because a corpus stated
none ([Its RDF meaning, as triples](/docs/format/reading/rdf)). In N-Triples that is
`"Maria Skłodowska-Curie"@pl`. The tag is written as the data gave it: RFC 5646 §2.1.1 makes tags
case-insensitive and RDF 1.1 lets a syntax lower-case them, so a reader compares with `lower()`.

### What the checker and the writer refuse

| What | Where | Code (proposed) |
| --- | --- | --- |
| A constant tag that is not well-formed BCP 47 (RFC 5646 §2.2.9) — `"x"@english-language` | checker, with `oxilangtag`, already in the lock through `oxrdf` | `syntax/invalid-language-tag` |
| A constant tag outside the shape's `sh:languageIn` or ShEx language set | checker | `type/language-not-allowed` |
| A `LangString` field assigned a `String`, or `str.lang` given a non-string | checker | [`type/property-mismatch`](/docs/errors/type/property-mismatch), `type/argument-mismatch` |
| `"x".lang("en")` | checker | `type/needless-lang` |
| A per-row tag that is not well-formed, or outside the shape's languages | the writer, as it writes the property table | `write/invalid-language-tag`, `write/language-not-allowed` |

A per-row tag is data, so only the run sees it. It refuses the run rather than following RML's
fallback (no valid tag, no language): the fallback writes an untagged string into a column whose
datatype is `rdf:langString`, and a corpus's `declared-term` guard holds every value to its declared
term. SHACL's `sh:uniqueLang` is not read: nothing in the writer de-duplicates by language, and a
second value in one language is the data's to fix. **What would reverse it:** a host that needs the
corpus written anyway, with the bad rows counted — the way a dropped edge is counted in a run's
answer, never in `fossil.json`.

## The Nobel example, end to end

**The program.** Three CSV files: `laureate.csv` (`id`, `birth_date`), `laureate_name.csv`
(`laureate`, `lang`, `name` — `6,en,Marie Curie`, `6,pl,Maria Skłodowska-Curie`,
`26,en,Albert Einstein`) and `prize.csv` (`id`, `laureate`, `category`, `motivation`).

```
@iri("https://schema.org/Person")
@annotation("http://www.w3.org/2000/01/rdf-schema#label", "Nobel laureate"@en)
@annotation("http://www.w3.org/2000/01/rdf-schema#label", "galardonado con el Nobel"@es)
type Laureate
    @iri("https://schema.org/name")
    name: Seq<LangString>

    @iri("https://schema.org/birthDate")
    @annotation("http://www.w3.org/2000/01/rdf-schema#label", "birth date"@en)
    @annotation("http://www.w3.org/2000/01/rdf-schema#label", "fecha de nacimiento"@es)
    birthDate: Date

    @iri("https://nobel.example/vocab/awarded")
    @annotation("http://www.w3.org/2000/01/rdf-schema#label", "awarded"@en)
    awarded: Seq<Ref<Prize>>

@iri("https://nobel.example/vocab/Prize")
type Prize
    @iri("https://nobel.example/vocab/category")  category: String
    @iri("https://nobel.example/vocab/motivation")  motivation: Option<LangString>

LaureateRow := io.csv("data/laureate.csv")
NameRow     := io.csv("data/laureate_name.csv")
PrizeRow    := io.csv("data/prize.csv")

Laureates : Laureate from LaureateRow.join(NameRow, on = LaureateRow.id == NameRow.laureate)
    @subject  = "https://nobel.example/laureate/{LaureateRow.id}"
    name      = NameRow.name.lang(NameRow.lang)
    birthDate = parse.date(LaureateRow.birth_date, "%Y-%m-%d")

Awards : Laureate from LaureateRow.join(PrizeRow, on = LaureateRow.id == PrizeRow.laureate)
    @subject  = "https://nobel.example/laureate/{LaureateRow.id}"
    birthDate = parse.date(LaureateRow.birth_date, "%Y-%m-%d")
    awarded   = Prize(PrizeRow.id)

Prizes : Prize from PrizeRow
    @subject   = "https://nobel.example/prize/{PrizeRow.id}"
    category   = PrizeRow.category
    motivation = PrizeRow.motivation.lang("en")
```

**`fossil.json`**, abridged to what changes:

```jsonc
{
  "format": "fossil/1",
  "vertex_tables": [{
    "name": "Laureate",
    "iri": "https://schema.org/Person",
    "annotations": [
      { "predicate": "http://www.w3.org/2000/01/rdf-schema#label", "object": { "value": "Nobel laureate", "language": "en" } },
      { "predicate": "http://www.w3.org/2000/01/rdf-schema#label", "object": { "value": "galardonado con el Nobel", "language": "es" } }
    ],
    "properties": [
      { "name": "dense_id", "type": "uint32", "role": "address" },
      { "name": "subject", "type": "string", "role": "identity" },
      { "name": "birthDate", "type": "date", "iri": "https://schema.org/birthDate",
        "annotations": [
          { "predicate": "http://www.w3.org/2000/01/rdf-schema#label", "object": { "value": "birth date", "language": "en" } },
          { "predicate": "http://www.w3.org/2000/01/rdf-schema#label", "object": { "value": "fecha de nacimiento", "language": "es" } }
        ] }
    ]
  }],
  "edge_tables": [{
    "name": "Laureate_awarded_Prize", "label": "awarded", "iri": "https://nobel.example/vocab/awarded",
    "annotations": [
      { "predicate": "http://www.w3.org/2000/01/rdf-schema#label", "object": { "value": "awarded", "language": "en" } }
    ]
  }],
  "property_tables": [{
    "name": "Laureate_name",
    "path": "property/Laureate_name.parquet",
    "source": { "key": "src", "references": "Laureate" },
    "properties": [
      { "name": "src", "type": "uint32", "role": "endpoint" },
      { "name": "name", "type": "string", "iri": "https://schema.org/name",
        "term_type": "http://www.w3.org/ns/r2rml#Literal",
        "datatype": "http://www.w3.org/1999/02/22-rdf-syntax-ns#langString" },
      { "name": "lang", "type": "string", "role": "language" }
    ]
  }, {
    "name": "Prize_motivation", "path": "property/Prize_motivation.parquet", "…": "the same three columns"
  }]
}
```

**The Parquet.** `vertex/Laureate.parquet` is `dense_id, subject, birthDate`, as before.
`property/Laureate_name.parquet` is `src, name, lang`: `(0, 'Marie Curie', 'en')`,
`(0, 'Maria Skłodowska-Curie', 'pl')`, `(1, 'Albert Einstein', 'en')`.

**The RDF.** `triples` holds, among the rest:

```
<https://nobel.example/laureate/6> <https://schema.org/name> "Marie Curie"@en .
<https://nobel.example/laureate/6> <https://schema.org/name> "Maria Skłodowska-Curie"@pl .
<https://nobel.example/laureate/6> <https://schema.org/birthDate> "1867-11-07"^^<http://www.w3.org/2001/XMLSchema#date> .
```

and no triple for an annotation.

**What Ask shows.** A reader asks the catalog for the header of `birthDate` in the person's language
and falls back to the field's name. There is one predicate to ask for, whether the label came from the
program, a ShEx annotation or a SHACL `sh:name`:

```sql
SELECT coalesce(
  (SELECT o_value FROM "nobel".fossil_annotations
    WHERE table_name = 'Laureate' AND column_name = 'birthDate'
      AND predicate = 'http://www.w3.org/2000/01/rdf-schema#label'
      AND lower(o_lang) = 'es'
    LIMIT 1),
  'birthDate')
```

So a Spanish reader sees the column *fecha de nacimiento*, the type *galardonado con el Nobel*, and
for Marie Curie the name whose `lang` matches, *Maria Skłodowska-Curie* under `pl` and *Marie Curie*
under `en`, from `property/Laureate_name.parquet` filtered on `lang`.

## What it touches

| Where | What changes |
| --- | --- |
| `fossil-syntax` | `LANG_STRING` in the lexer, the `@` read as the literal's suffix when it touches the quote; `DeclAttrs` — several attributes, stacked or inline — and `@annotation` in the parser; a CST node for each |
| `fossil-graph-schema` | `Primitive::LangString` and `rdf:langString` in its XSD table both ways; `annotations` on `Shape` and `PropertyConstraint`, and `languages` on `PropertyConstraint`; the wire types `@fossil-lang/types` generates from them |
| `fossil-hir` | `shex.rs` carries a shape's and a triple constraint's annotations, `rdf:langString` and language value sets; `shacl.rs` reads `sh:name` as an `rdfs:label` annotation and `sh:description` as an `rdfs:comment` one, carries the non-SHACL predicates, `sh:datatype rdf:langString` and `sh:languageIn`; `declared.rs` lowers `@annotation`; the checker types `LangString`, checks a constant tag with `oxilangtag` (a direct dependency then, through `cargo deny` and the wasm gate), refuses a CURIE predicate and `"x".lang("en")`; `fossil-ide` shows a field's annotations on hover |

| `fossil-df` | the writer's third property column and its per-row tag check; `annotations` on `VertexTable`, `EdgeTable` and `Property` in `manifest.rs`; `fossil.schema.json` and `corpus.bnf`'s `language` role regenerated |
| `@fossil-lang/corpus` | `fossil_annotations`; `triples` fills `o_lang` and `rdf:langString`; the guards learn the `language` role and `rdf:langString` in `declared-term` — all in the release whose writer writes them, and `FOSSIL_FORMAT` stays `fossil/1` |

## The migration

**fossil, 0.3.0-alpha.32**, with the other three designs of this batch. Everything in the table above, in one release: the grammar, the checker,
the decoders, the writer's `annotations` and language column, and the reader and guards that read
them. `fossil/1` is still the format string, and a corpus with no annotation and no `LangString`
property is unchanged.

**keasy.** Nothing breaks: no program it holds writes `@annotation`, and a corpus it attaches with
no annotations has an empty `fossil_annotations`. What it gains is a column header in the person's
language — Ask's and the graph's — from `fossil_annotations`, once kanzo-ui reads it, and a
multilingual name filtered on `lang`. A program that used `core.lang` already failed to check, since
the row went with [the review of the catalogue](/docs/design/declared).
