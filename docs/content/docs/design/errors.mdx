The request, in the owner's words: *una forma de mostrar mensajes de error, que venga de Rust, y que
gestionemos en JavaScript bien, como lo haría un sistema en producción.* One way to show an error,
coming from Rust, handled properly in JavaScript, the way a production system would.

"Properly" has a test that can be run on the tree: **can a host decide what to do about a failure
without reading its prose?** Today it almost never can.

## What crosses into JavaScript today

Counted on `main` at `8d6114a3`, sites this repository owns, pass-through of a host's or an engine's
own errors excluded:

| Where it is raised | Sites | Distinguishable without the message |
| --- | --- | --- |
| `fossil-df-wasm` — the executor's run, its arguments, its descriptor, its storage | 36 | 1 — `OverBudget`, by `name` |
| `fossil-storage-wasm` and `@fossil-lang/storage` | 10 | 0 |
| `fossil-wasm` — the workspace behind `@fossil-lang/wasm` | 5 | 0 |
| `@fossil-lang/executor` | 1 | 0 |
| `@fossil-lang/introspect` (reaches a host only through `onWarn`) | 1 | 0 |
| `@fossil-lang/corpus` — `CorpusManifestError`, `CorpusReadError`, one `TypeError` | 17 | 17, by class — and then by message |
| **Total** | **71** | **18** |

**53 of 71 are a string and nothing else.** The 18 that are not are barely better: the two corpus
classes say *which package* refused, not *what* — `CorpusReadError` covers an unknown table, an
unknown column, a bad limit, an inverted box and a NaN, and the only way to tell them apart is the
message. The one real discriminant was `run_error` in
`crates/fossil-df-wasm/src/lib.rs` at `8d6114a3`, which named an over-budget run `OverBudget` — and
`runJob` (`8d6114a3:packages/executor/src/run-job.ts, runJob`) then reduced it to `error: string` in its
`CompletePayload`, so a host never saw the name. The `Refusal` behind it
(`crates/fossil-df/src/memory.rs, Refusal`) carries the consumer, the bytes requested, the bytes held
and the budget as four fields; all four reach JavaScript inside a sentence.

What else is lost on the way, each one a place where structure existed and was flattened:

- `RunError` (in `crates/fossil-df/src/executor.rs` at `8d6114a3`) is `OverBudget(Refusal)` or
  `Failed(String)`, with a `From<String>`. Sixteen distinct failures — a destination no store covers,
  a source that would not route, a DataFusion error, every variant of `WriteError` and `LayoutError` —
  enter `Failed` through `format!` or `.to_string()`.
- `StorageError` (`crates/fossil-storage/src/credential.rs, StorageError`) is a seven-variant enum
  with typed fields, and was `.to_string()`'d at every boundary it crossed (it converts to a `Failure` now).
- A host's own typed rejection from `credentials` is reduced to its `message` before it is wrapped.
- `attach` builds `did not read: ${cause.message}` and drops the `cause`.
- A program that does not compile fails at `run` as `execute_graph: Error during planning: the
  mapping did not compile; see the reported diagnostics` — and the executor exposes no diagnostics.

**Compile diagnostics are the better half, and still have no identity.** `Diagnostic`
(`crates/fossil-base/src/diagnostic.rs, Diagnostic`) is structured — severity, span and frame, labels,
`help`, `suggestion_source`, `did_you_mean` — and reaches JavaScript as data, not as a throw: `check()`
answers `CheckRow[]` (`crates/fossil-wasm/src/lib.rs, CheckRow`). But a `CheckRow` at `8d6114a3` was
`{ uri, range, severity, message, related }`: `help` was appended to `message` as a `\nhelp:` line,
`did_you_mean` and `suggestion_source` were dropped, and there was no code.
The `Diagnostic` that `packages/types/src/diagnostic.ts` declared had `code?` and `source?`, and nothing
filled them.
Measured over the emitters: **about 126 distinct message templates, every one `Severity::Error`**,
five that set labels, one that sets `suggestion_source`, one that sets the structured `did_you_mean` —
and seven more that offer a *did you mean* only inside the message text.

**The consumers show what that costs.** keasy's web app has about 38 places that catch or show an
error. It parses no message — which is to its credit — and so it cannot branch on any fossil error at
all: every one is rendered as raw `.message` (in an `Alert`, a `<pre>`, a toolbar span), logged to the
console, or swallowed. The executor's failure reaches its UI as a stored string in a `<pre>`. The one
place keasy *does* branch well is its own server's errors: an `ErrorBody { error, message }` whose
`error` is a closed, namespaced enum (`auth/session_required`, `rbac/no_membership`), and a copy table
in `web/src/lib/errors.ts` keyed by that code. That is the design below, already working one layer up.

And **26 tests assert on message text** — eighteen in the TypeScript packages (sixteen on a thrown error, two on a
diagnostic), eight in Rust — which is
the tree's own evidence that the message is being used as an identifier because nothing else is one.

## The references, and what each one decides

| Reference | What it contributes | What is not taken |
| --- | --- | --- |
| rustc's error codes, `rustc --explain`, and the error index ([rustc-dev-guide, *Error codes*](https://rustc-dev-guide.rust-lang.org/diagnostics/error-codes.html); [the index](https://doc.rust-lang.org/error_codes/error-index.html)) | A code per kind of mistake, a long explanation per code kept beside the compiler, a tidy check that every code has one, and **a retired code is never reused** | The opaque `E0308` spelling — see [the format](#a-code-is-areakind) |
| miette's `Diagnostic` trait ([docs.rs](https://docs.rs/miette/latest/miette/trait.Diagnostic.html)) | The field set: `code`, `severity`, `help`, `url`, `labels`, `related`, `diagnostic_source` — which is already what fossil's tests render with | Implementing it on every type; one type implements it |
| thiserror ([docs.rs](https://docs.rs/thiserror/latest/thiserror/)) | `#[error("…")]` as the one place a message is written, `#[source]` for the chain | `#[error(transparent)]` across a boundary — that is how `WriteError` loses its variant today |
| RFC 9457, Problem Details ([rfc-editor.org](https://www.rfc-editor.org/rfc/rfc9457)) | `type` as *the* identifier (§3.1.1), a `title` that **does not change between occurrences** (§3.1.3), a `detail` that **consumers should not parse** (§3.1.4), and typed extension members (§3.2) | `status` (there is no HTTP here) and, for now, `instance` |
| ES2022 `Error` `cause` ([ECMA-262, InstallErrorCause](https://tc39.es/ecma262/#sec-installerrorcause)) | The chain, in the language's own spelling | A custom `inner`/`reason` field |
| TypeScript discriminated unions ([handbook](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#discriminated-unions)) | `code` as the discriminant, so `if (e.code === 'run/over-budget')` narrows `e.data` to its fields | — |
| LSP `Diagnostic.code` and `codeDescription` ([3.17](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#diagnostic)) | `code: string` plus `codeDescription.href`, so an editor links the squiggle to its page | Integer codes |

They agree more than they differ, and where they agree the design takes the common part: **an
identifier that is stable, a short title that is fixed per identifier, a detail for a person that is
not parsed, typed data beside it, a link to a long explanation, and a chain of causes.**

## A code is `area/kind`

A code is two lowercase kebab-case words joined by a slash: `run/over-budget`, `type/property-mismatch`,
`corpus/not-json`. The area names **where the mistake is**, not which crate noticed it — the same
mistake found by `check` and again by `run` has one code, which is the point of sharing a namespace.

The grammar is a predicate on both sides: `is_code` in `fossil_graph_schema`, and `isCode` exported
from `@fossil-lang/types`, which a host's registry tests its own codes with rather than keeping a
third copy of the rule.

It is `area/kind` rather than `E0308` because a code is read by people before it is looked up: a
host author writing `case 'storage/outside-prefix':` needs no index to review the line. It is a slash
because the code is also the route of its page, and because keasy's server already spells its own
codes that way.

**Stability.** A code, once it is in a tagged release, **never changes meaning and is never reused**.
Its title, its detail and its help may be reworded in any release; its `data` may gain optional fields.
Removing a field from `data`, or splitting one code into two, is a breaking change, stated in the
consumer's words in the release notes — the same rule a renamed export is held to.

**Retiring a code** is deleting its variant and its page, and saying so in the release notes — see
[the decisions](#the-decisions-and-what-would-reverse-each).

**What this reverses.** [Tooling for machines](/docs/design/tooling-for-machines#a-diagnostic-is-an-api)
ends *a diagnostic is an API* with a corollary: *their text is an interface; rewording an error message
is a change to something a consumer parses.* That was true because the text was the only identifier. With
a code and typed data, **the text stops being an interface**: a host that reads `message` for anything
but showing it is outside the contract, and rewording is free. That page says so now, in these
words.

**What would reverse it.** A consumer that needs to branch at a granularity finer than a code — the
same code meaning two things it must treat differently. The answer is a new code, never a message
pattern; and if that happens repeatedly inside one area, the area is cut wrong.

## Rust: one type, and `Diagnostic` carries it

**The catalogue is one enum, `Problem`, in `fossil-graph-schema`.** That crate is the leaf where
shared vocabulary already goes — `Span` moved down into it for the same reason — it depends on
`serde` and nothing else, and every crate that raises an error can reach it (`fossil-storage` gains
that one edge; today it depends on no fossil crate). A sketch, not a signature:

```rust
#[derive(Debug, Clone, thiserror::Error, Serialize, JsonSchema)]
#[serde(tag = "code", content = "data")]
pub enum Problem {
    #[serde(rename = "run/over-budget")]
    #[error("the run needs more memory than the executor's {budget} budget: {consumer} asked for {requested} with {reserved} already held. Nothing was written.")]
    OverBudget { consumer: String, requested: u64, reserved: u64, budget: u64 },

    #[serde(rename = "type/property-mismatch")]
    #[error("`{property}` expects {expected}, and this is {actual}")]
    PropertyMismatch { property: String, expected: String, actual: String },
    // … one variant per code
}

impl Problem {
    pub fn code(&self) -> &'static str;   // the serde tag, read back
    pub fn title(&self) -> &'static str;  // fixed per code — RFC 9457 §3.1.3
}
```

Three properties fall out of making the code the **serde tag of the data enum**, and they are the
argument for this shape over a `code: &'static str` field beside a free `message`:

- **The code and the data cannot disagree.** A variant *is* its code; there is no second list.
- **The message is rendered from the data**, by the one `#[error]` on the variant. It cannot say
  something the data does not carry, and a consumer that wants the column name reads `data.column`.
- **The JSON Schema is derived**, so the TypeScript union is generated rather than restated (below).

**`Diagnostic` keeps its spans and swaps `message: String` for `problem: Problem`.** It stays the salsa
accumulator, keeps `severity`, `span`, `frame`, `labels`, `help`, `suggestion_source` and `did_you_mean`
— everything positional, which a run failure has none of. `message` becomes `problem.to_string()`. That
is the one-layer rule applied: there is one type that says *what went wrong* (`Problem`) and one that
says *where in a program* (`Diagnostic`), and a compile diagnostic is the second holding the first. A
parallel `RunDiagnostic` with its own code field is the thing this avoids.

**`RunError` is deleted.** A failure that is not about a position is a `Failure`:

```rust
pub struct Failure {
    pub problem: Problem,
    pub help: Option<String>,
    pub related: Vec<Diagnostic>,                        // run/does-not-compile carries the program's
    pub cause: Option<Box<dyn std::error::Error + Send + Sync>>,
}
```

`Failure` implements `std::error::Error` with `source()` returning `cause`, and `miette::Diagnostic`
with `code`, `help`, `url` and `related` — so the native renderer the acceptance fixtures are blessed
through prints the code without a second path. `From<String>` goes, and with it the route by which
sixteen failures became one: a site that has no code yet does not compile.

**`help` is per occurrence, `title` is per code.** `help` stays where it is — on the `Diagnostic` or
`Failure` — because the best help names things only this occurrence knows (`` `Purchase.amount` is
Float ``). The title is a constant of the variant.

**A foreign error is a cause, never a code.** DataFusion, `object_store`, DuckDB and a host's own
rejection have their own vocabularies, and fossil does not classify them. The layer that meets one
wraps it in the fossil failure it *means* — `engine/failed`, `storage/unreachable`,
`storage/host-refused` — and keeps the original as `cause`, whole. That is what `attach` and `JsHost` did
wrong at `8d6114a3`: they kept the text and dropped the object. Both keep the cause now — and a
host's own `area/kind` code on it, [as a foreign one](#a-hosts-code-kept-on-a-foreign-cause).

**What would reverse it.** A catalogue large enough that one enum in one file is the bottleneck of
every change — at which point the catalogue becomes a data file with a generator, as
`catalogue.bnf` already is for the standard library.

## The boundary: one shape, and a real `Error`

Everything that leaves fossil for JavaScript — thrown or returned — is one shape:

```ts
interface ProblemBase {
  code: Code;                 // 'run/over-budget' — the identifier (RFC 9457 `type`)
  title: string;              // fixed per code (RFC 9457 `title`)
  detail: string;             // for a person; never parsed (RFC 9457 `detail`)
  severity: 'error' | 'warning' | 'info';
  help?: string;
  related?: Related[];        // miette `related`; run/does-not-compile's diagnostics
  cause?: Problem | Foreign;  // ES2022 `cause`, serialized
}
interface Foreign { name: string; detail: string; code?: string; data?: object }  // a cause fossil did not raise
interface Related { code; data; title; detail; severity; help?; span? }  // a problem, file-absolute
type Problem = { [C in Code]: ProblemBase & { code: C; data: ProblemData[C] } }[Code];
```

A compile diagnostic is the same problem plus where. `CheckRow` carries `code`, `title`, `data`
(typed by `code`, as `Problem`'s is) and `help` beside where — `uri`, `range`, the labels as `related`
— and the two structured repairs, `didYouMean` (a range and a replacement) and `suggestion` (fossil
source). It keeps the LSP's spelling of the rest, because it is the LSP diagnostic `lsp_diagnostic`
renders plus a `uri`: `message` is the detail, `severity` the LSP integer. The LSP diagnostic carries
`code`, `codeDescription.href` pointing at the code's page, and the rest — `title`, `data`, `help`,
`didYouMean`, `suggestion` — as its `data`, the field LSP leaves to the server.

**It has no `type` URL on the wire, and that is the one departure from RFC 9457.** The published site
lives under a prefix a deployment chooses, so a URL baked into every error would be wrong for someone.
The code is the identifier, and `helpUrl(code, base?)` in TypeScript builds the link. **What would
reverse it:** the site gets a stable canonical origin, at which point `type` is added and is exactly
that function's answer.

**What is thrown is a real `Error`, built in one place per side.** In Rust, one function turns a
`Failure` into a `js_sys::Error` whose `name` is `FossilError`, whose `message` is `detail`, and which
carries `code`, `data`, `problem` (the whole serialized object) and `cause` — a cause that is a
`Failure` becomes a nested `FossilError`, a foreign one an `Error` of its own name. The three wasm
crates call that function and nothing else; `run_error`, `busy_error`, `js_err` and every
`JsError::new(&e.to_string())` go. In TypeScript, `new FossilError(problem)` builds the identical
object for the codes the TypeScript packages raise themselves — the corpus's are all of that kind,
because [reading is TypeScript](/docs/design/one-door).

**Compile diagnostics are still returned, not thrown.** A program with errors is an answer to `check`,
not a failure of it. The one place a diagnostic becomes a throw is a run over a program that does not
compile: `run/does-not-compile`, whose `related` carries the diagnostics the executor currently
withholds.

**What would reverse it.** A host that cannot receive an `Error` subclass across its own boundary — a
worker's `postMessage` strips the prototype. `problem` is there for exactly that: it is plain data,
and `FossilError.from(problem)` rebuilds the error on the far side. If every host ended up passing
`problem` rather than the error, the class is ceremony and goes.

## TypeScript: `FossilError`, generated data, one guard

```ts
class FossilError<C extends Code = Code> extends Error {
  readonly name = 'FossilError';
  readonly code: C;
  readonly data: ProblemData[C];
  readonly problem: Problem & { code: C };
}
// the guard, `isFossilError`, has this type:
type IsFossilError = {
  (e: unknown): e is FossilError;
  <C extends Code>(e: unknown, code: C): e is FossilError<C>;
};
```

**The guard is structural, not `instanceof`.** Two copies of a package in one bundle, or an error built
in wasm against one built in TypeScript, are different classes; `name === 'FossilError'` plus a `code`
that is a member of the generated `CODES` set is not. `CorpusManifestError` and `CorpusReadError` are
deleted — a consumer that caught one catches `isFossilError(e)` and reads `code`.

**`message` is `detail`, in English, for a person.** It is what a log line and an unhandled rejection
show, which is why it stays the real message rather than the code. It is not an identifier and nothing
in the contract reads it.

**`ProblemData` is generated from Rust.** `Problem`'s derived JSON Schema is written to
`crates/fossil-graph-schema/problem.schema.json`, and from it `crates/xtask/tests/wire.rs` writes
`problem.gen.ts` into `@fossil-lang/types` — `Code`, `CODES`, `ProblemData`, each
code's title, and `DETAILS`: each variant's `#[error]`, carried in the schema as `x-detail` and translated
wherever it is a format string over fields, so `FossilError.of(code, data)` renders the detail Rust would
and takes none of its own — and the test fails when the checked-in file is stale. Five details raised in
TypeScript had already drifted from Rust's when this was added. Every other shape that crosses to
TypeScript is generated the same way, the manifest's included. **What would reverse it:** the generator costing more to keep than the union does to write —
a schema dialect it cannot read, say.

`FossilError` lives in `@fossil-lang/types`, which gains its first runtime export; every package that
raises already depends on it.

## A page per code, and a test that holds them together

Every code has a page in an `errors/` section of this site, under the code as its route — the error
index. A page has the title as its heading, what the mistake is, why fossil refuses it, and how to
repair it, and **where one exists it transcludes the failing program and its blessed rendering** with
`<Program>`, the way this site already shows every program. The six directories under
`docs/programs/errors/` are the first six of those pages, compiled in CI and named by their codes:
`identity/conflicting`, `name/unknown-field`, `pipeline/join-one-side`,
`shape/missing-required-property`, `shape/name-collision` and `type/property-mismatch`.

`content.test.ts` gains one suite: every code in `problem.schema.json` has a page, every page under
`errors/` names a live code, and a page's heading is the code's title. A retired code has neither a
variant nor a page, so it is in neither set. This is rustc's tidy check, stated in this repository's
terms.

**What would reverse it.** Pages written as stubs to satisfy the test. If a quarter of them are a
title and one sentence a year after they exist, the requirement is wrong and becomes *every code
reachable from a fixture has a page*.

**`internal/bug` — 1 code** for everything that is fossil's fault and not the caller's: the
`internal compiler error` sites, a serializer that failed on a value fossil built, a Reflect `set` on a

`WebAssembly.RuntimeError` — it is not a value that can be built at the moment it happens.

**99 codes**, 98 of them a mistake someone other than fossil can repair.

**Retired, with no program that reached them.** `write/unknown-type` and `layout/dangling-endpoint`
were released in `v0.3.0-alpha.18` and are gone: the executor builds the schema it writes
from the types it has, and joins each relation to the vertices it names before the layout pass sees
it, so neither could fire. `pipeline/source-as-stage`, `name/ambiguous-member` and
`syntax/missing-value` never shipped and were deleted outright: the parser reports a property with no
value itself, a stage resolves only against relation verbs, and no member is spelled on two
receivers. Each of their arms reports `internal/bug` now. `syntax/retired-spelling`, released through
`v0.3.0-alpha.26`, went with the parser's refusals of forms the grammar no longer has: such a form is
now an ordinary `syntax/expected-token` or `syntax/unexpected-token`.

## The screen: kanzo-ui's `Diagnostic`, and the product decides the words

**No new component.** kanzo-ui already has the part, on its root barrel: the `Diagnostic` family —
*"a machine's complaint, shown: a severity, a message, and the positions it points at"* — with
`DiagnosticTitle`, `DiagnosticDescription`, `DiagnosticSeverity`, `DiagnosticSource` (monospace, *an
identifier somebody has to type back into a tool*), `DiagnosticFrame` (a path, a line, a column, a
label, jumpable), `DiagnosticActions`, and a collapsible `DiagnosticContent`. Every field of a problem
has a slot:

| `Problem` | `Diagnostic` part |
| --- | --- |
| `severity` | `variant` on the root, `DiagnosticSeverity` |
| `title` | `DiagnosticTitle` |
| `detail`, `help` | `DiagnosticDescription` — two of them, until a second call site asks `help` for a look of its own |
| `code` and its page | `DiagnosticSource`, `asChild` onto a link to `helpUrl(code)` |
| `range`, `labels` | `DiagnosticFrame`, `secondary` for a label in another document |
| `cause`, `related` | a nested `DiagnosticList` in `DiagnosticContent` |
| a retry | a `Button` in `DiagnosticActions` |

Alert, toast, `FieldError` and Empty were each checked and each is the wrong host: an Alert has no code,
no frame and no collapse, a toast is transient and takes an options object, a field error belongs to
one control, and Empty is a zero state. kanzo-ui's own rule settles the rest — *the library displays,
products produce*: it gains no `FossilError` type and no fossil dependency, and
fossil ships no UI of its own.

**So the mapping is keasy's, and it is one component.** keasy writes one `Problem` view that renders a
`Problem` into `Diagnostic` parts, and it replaces every place in the inventory that shows `.message`
today: the corpus `Alert`, the SQL panel, the run's `<pre>`, the studio's findings card, the ask panel's
`Failure`.

**keasy's rule, which is the rule for any host:**

1. **Branch on `code`**, with `isFossilError(e, 'run/over-budget')`, and read `data` for the numbers.
2. **Override copy only where the audience differs.** keasy's `registry` in `web/src/lib/errors.ts`
   is already keyed by code; fossil's codes join it. A code with no entry renders fossil's `title` and
   `detail` unchanged, which is the default and should stay the common case.
3. **Never parse `message`.** Not to classify, not to extract a name. If a host needs a value that is
   only in the message, that is a missing field in `data`, and the fix is in fossil.
4. **Never swallow.** The five console-only or silent paths in the inventory — the wasm workspace
   failing to load, `refs`, the relations publish, `describeDataSpace`, `rules-panel`'s unhandled
   rejection — show a problem like any other.

The run's failure changes shape end to end: `CompletePayload.error: string` becomes
`problem: Problem`, keasy's server stores it as JSON rather than `Option<String>`, and the job page
renders it rather than a `<pre>`.

**What would reverse it.** A second product rendering fossil problems — the playground, say — that
wants the same mapping. Then the mapping is a real candidate for a shared home, and the
question is which package may depend on both.

## The migration, in steps that each merge green

Each step is one branch, one merge, and leaves every gate green; each names what a consumer must edit.

1. **Accept the page.** The callout goes, and [tooling for machines](/docs/design/tooling-for-machines)
   loses its corollary. *Breaking:* nothing.
2. **`Problem` and `Failure` in Rust, the boundary unchanged.** The enum, `title()`, the schema file
   and its bless test; `RunError`, `From<String>` and the `Result<_, String>` routes in `fossil-df`
   and `fossil-storage` become `Failure`. The wasm crates still `.to_string()`. *Gate:* `cargo test`,
   the schema test. *Breaking:* nothing outside Rust.
3. **The boundary.** The one Rust-to-JS function in all three wasm crates; `problem.gen.ts`,
   `FossilError` and `isFossilError` in `@fossil-lang/types`; the corpus and storage packages raise
   `FossilError`; `runJob` completes with `problem`. The 16 TypeScript tests that match message text
   assert `code` and `data` instead. *Breaking:* `name === 'OverBudget'` becomes
   `code === 'run/over-budget'`; `CorpusManifestError` and `CorpusReadError` are gone;
   `CompletePayload.error` is `problem`.
4. **The error index.** Pages for the run, storage, corpus and API codes, the six fixture pages
   renamed, and the codes-to-pages suite. *Gate:* the docs build.
5. **Compile diagnostics.** `Diagnostic.problem`; `CheckRow` and the LSP `Diagnostic` gain `code`,
   `title`, `data`, `help`, `didYouMean`, `suggestion`; the six blessed `diagnostic.txt` are re-blessed
   with the code; the eight Rust tests and two TypeScript tests that match message text assert the variant; the remaining
   compile pages. *Breaking:* `CheckRow.message` no longer carries a `\nhelp:` line — `help` is its own
   field.
6. **keasy**, on its own branch after 3 and again after 5: the `Problem` view, the registry, the stored
   run problem, the five silent paths. *Gate:* keasy's own.

Steps 2 and 3 are the ones a consumer feels; 4 and 5 can interleave. Nothing waits on the compile
pages being complete — a code without a page fails step 4's suite, which is why the pages for a batch
land with that batch.

## The decisions, and what would reverse each

The owner accepted this page on 2026-10-01 and settled the four questions it had left open.

1. **A retired code keeps nothing**: no page and no list. rustc keeps a tombstone page per retired code
   so an old log still resolves, and a list that stops reuse; fossil deletes rather than keeps, because
   at `0.x` there are no old logs worth resolving and the release notes record what went. *What would
   reverse it:* a consumer holding logs across a release boundary that cannot resolve a retired code
   from its release notes, or a code reused with a second meaning — then the tombstone and the list
   are worth their lines.
2. **keasy's server speaks the same shape** — `code`, `title`, `detail`, `data` — as its own keasy
   change after step 3, so a keasy screen renders a server refusal and a fossil failure with one view.
   Its `dependents` field becomes `data`. *What would reverse it:* a server refusal that needs a field
   the shape cannot carry as `data`, which would say the shape is fossil's and not general.
3. **The catalogue ships at the grain derived above.** The codes-to-pages suite is the pressure: a
   code whose page cannot say something different from its neighbour's is merged into it when the
   pages are written, not before. Four were merged when step 5 gave every compile emitter its code,
   none of them released: `document/not-found` into `document/not-registered`
   (a document nothing registered under its key is one mistake, at `check` or at `run`),
   `document/not-named` into `provider/bare-document-path` (a document named by a bare path, with no
   provider to read it),
   `pipeline/join-foreign-binding` into `name/row-not-in-scope` (a join naming a row that is not one
   of its two sides is a row out of scope), and `unsupported/literal` into `unsupported/expression`
   (a literal the compiler cannot lower is an expression it cannot lower). *What would reverse it:*
   the pages for an area coming out as near-copies — then the area is cut too fine, and the merge is
   the edit.
4. **`FossilError` lives in `@fossil-lang/types`**, its first runtime export; every raising package
   already depends on it, and a package of its own would be a second place to look. *What would
   reverse it:* `types` growing runtime code that is not about the contract, at which point it is no
   longer a types package and the split is by what the code is for.

## A host's code, kept on a foreign cause

**A host that refused a `Host` call in its own vocabulary lost that vocabulary on fossil's wire**,
until `v0.3.0-alpha.21`; everything below about the loss describes `main` at `aa6c334a`.
keasy's server answers a credentials request with `job/not-found` or `store/silent`; its client
throws an `ApiError` carrying that `code`, `title` and `data`; fossil wraps it as
`storage/host-refused` with the rejection as cause — and the cause was a `Foreign`, which was
`{ name, detail }` and nothing else. The code survived only as long as the live object did, and the
live object does not survive the paths that matter:

- **In Rust it never exists.** `js::foreign` (`crates/fossil-graph-schema/src/js.rs`) read the
  rejection's `name` and `message` and dropped the object, because a `JsValue` is not `Send` and cannot
  ride a `Failure`'s cause. That is the path `JsHost` takes for every document a run reads
  (`storageRead`), so `document/unread > storage/host-refused` reaches `runJob` as plain data whose
  innermost cause is `{ name: "ApiError" }`.
- **On the wire it was never written.** `Failure`'s `Serialize` wrote a foreign cause as
  `name` and `detail`; `toWire` in `packages/types/src/error.ts` did the same on the TypeScript side.
- **From the wire it was never rebuilt.** `js::from_wire` and `causeOf` rebuilt a foreign cause as an
  `Error` with a name and a message. keasy stores a failed run's problem as JSON (`jobs.problem`), so
  what its job page shows is this rebuilt chain, not the thrown one.

Five functions, one omission. **keasy's e2e suite caught it on its first run**: scenarios 01 and 02
(`e2e/tests/discover.spec.ts`, `job/not-found`, `job/not-completed`) and 03 and 04
(`e2e/tests/stack.spec.ts`, `store/silent`, `store/refused`) each showed `storage/host-refused` over
an uncoded `ApiError`. keasy closed them with three workarounds, each in a commit that says why,
and each goes once keasy is on `alpha.21`:

1. `3c3a19d` — `toProblem` reads the cause off the live `FossilError`'s `cause` rather than its
   `problem` (`web/src/lib/errors.ts, fossilProblem`), which fixes 01 and 02, where the wrap happens
   in TypeScript and the object is still there; and the runner stops letting `runJob` report
   `failed`, reporting it itself from the thrown error
   (`web/src/app/(main)/(chrome)/(member)/jobs/[id]/_parts/use-browser-job-runner.ts`).
2. `05f485a` — that was not enough for 03 and 04, where the wrap happens in Rust: `ApiError.name`
   is set to the code (`api/src/client.ts`), and `ProblemView` shows a foreign cause whose name
   matches the grammar as the code it is (`web/src/components/problem-view.tsx`).

The second is a hidden convention between two repositories that neither one's types state, and
it is exactly what [the boundary](#the-boundary-one-shape-and-a-real-error) exists to prevent:
an identifier smuggled through a field meant for something else.

### The decision

The owner accepted this section on 2026-10-02.

**`Foreign` gains two optional fields, `code` and `data`, read from the thrown value.** A rejection
that carries a string `code` of the [`area/kind`](#a-code-is-areakind) shape keeps it, and its
`data` with it when `data` is a JSON object. RFC 9457's `type` is an identifier of the producer's
vocabulary, not of one registry (§3.1.1), so a cause may name its own vocabulary's code. It stays a
`Foreign`: it never joins fossil's catalogue, `CODES` never lists it, `isFossilError` never matches
it, and fossil never branches on it. [A foreign error is a cause, never a code](#rust-one-type-and-diagnostic-carries-it)
still holds, read as *never a fossil code*: fossil carries the host's code, it does not classify by it.

A code outside the grammar — Node's `ECONNREFUSED`, a `DOMException`'s number — is not read. The
grammar is what makes a string a key a host's registry can hold; anything else is still in `detail`.

**The wire's discriminant moves from `code` to `name`.** `js::from_wire` treated a cause with a
string `code` as a nested problem, and `isProblem` treated plain data with a catalogued `code` as
one. A coded foreign cause breaks the first outright and the second on any collision with a fossil
code. A problem has no `name` on the wire and a foreign cause always has one, so `name` decides: a
cause with a `name` is foreign, whatever its `code` says.

### The type change

```rust
type Object = serde_json::Map<String, serde_json::Value>;

pub struct Foreign {
    name: String,
    detail: String,
    coded: Option<Box<Coded>>,  // { code: the producer's own `area/kind`, data: Option<Object> }
    source: Option<Box<dyn Error + Send + Sync>>,
}
impl Foreign {
    pub fn coded(self, code: impl Into<String>, data: Option<Object>) -> Self; // keeps no code off the grammar
    pub fn code(&self) -> Option<&str>;
    pub fn data(&self) -> Option<&Object>;
}
```

`data` is a JSON object by type, not by a check at each reader. The pair is boxed because most
foreign errors carry no code, and every `Result` holding a `Foreign` — `StorageError`'s
`HostRefused` among them — pays for an unboxed field's width. `serde_json` stops being optional in
`fossil-graph-schema` — it is the only honest type for data fossil does not know the shape of, and every wasm crate already links it through the `js` feature.
`js::foreign` reads `code` and `data` off any object, an `Error` or not, through `Reflect` and
`JSON.stringify`; a `data` that will not stringify is dropped and the code kept. `Failure`'s
`Serialize` writes them when present. `js::from_wire` sets them as own properties on the rebuilt
`Error`, so `err.cause.code` reads the same on a live chain and a rebuilt one.

```ts
export interface Foreign {
  name: string;
  detail: string;
  /** The producer's own code, `area/kind`. Never one of fossil's: `isFossilError` does not match it. */
  code?: string;
  /** What that code carries. */
  data?: Record<string, unknown>;
}
```

`toWire` reads `code` and `data` as `js::foreign` does; `causeOf` puts them back; `isProblem`
refuses a value with a `name`. Every change is additive: a problem stored before it has no foreign
`code` and reads as it did.

### The alternatives, and why each is rejected

- **Keep the workaround.** It works, and it is a contract written nowhere: fossil's types say
  `name` is *the error's own name*, keasy's `ApiError` says it is a code, and the next host that
  does not know the trick loses its code silently. It also costs keasy two code paths for one chain
  — the live one and the stored one — which is what `3c3a19d` had to split.
- **A host-supplied `Problem` as cause.** Let a rejection be a `Problem` and nest it as one. A
  `Problem` is typed by fossil's catalogue — `code: Code`, `data: ProblemData[C]` — and a host's code
  is not in it; widening `Code` to `string` throws away the narrowing the generated union exists
  for, and `isFossilError` could no longer mean *fossil raised this*. The host's cause is foreign
  by definition; it needs a code, not membership.
- **Keep a JavaScript reference.** Hold the thrown object on the cause. It cannot cross the Rust
  half — a `JsValue` is not `Send`, which is why `js::foreign` copies today — and it would not
  survive `jobs.problem` or a `postMessage` anyway. The stored problem is what a job page renders;
  only data reaches it.

### The migration

1. **fossil.** The two `Foreign`s, the five functions, the discriminant. Tests: in `problem.rs`, a
   coded `Foreign` serializes `{ name, detail, code, data }`, and one off the grammar keeps no code;
   in `packages/types/tests/error.test.ts`, `toWire` keeps `code` and `data`, `FossilError.from`
   rebuilds them on the cause, a foreign cause whose code is a catalogued one is neither a problem
   nor a `FossilError`; in `packages/storage/tests/objects.test.ts`, a host whose `credentials`
   rejects with an error coded `job/not-found` yields `storage/host-refused` whose wire cause has
   that code — the Rust path, end to end; in `34e5fd51:packages/executor/tests/run-job.test.ts`, the same
   rejection survives into the `failed` report's `document/unread` chain. Released as
   `v0.3.0-alpha.21`. *Breaking:* nothing.
2. **keasy**, on `alpha.21`: `ApiError.name` goes back to `"ApiError"` (`api/src/client.ts`);
   `ProblemView`'s `CODED` name test goes and a foreign cause shows its `code`
   (`web/src/components/problem-view.tsx`); `fossilProblem` goes and `toProblem` returns
   `err.problem` (`web/src/lib/errors.ts`); `runJob` reports `failed` again through `Job.complete`
   (`use-browser-job-runner.ts`); the name-is-code test in `web/src/lib/errors.test.ts` becomes one
   that a stored problem's foreign cause carries `job/not-found`. *Gate:* scenarios 01–04 green
   against the stored chain, not the live one.

### What would reverse it

A host whose own vocabulary is not `area/kind` and that needs its code kept anyway — then the
grammar check is the wrong filter, and `code` becomes any string with the host's registry deciding
what it keys. Or fossil starting to *act* on a foreign code — retrying on `store/silent`, say —
which would mean the host's vocabulary had become part of fossil's contract, and the answer is a
fossil code for that case, not a branch on someone else's.
