**fossil is the backend. The view is `@kanzo-tech/graph` and the rest of kanzo-ui, and there is one
path between them.** Anything that answers the same question a second way is deleted rather than
kept beside it — the playground went for being a second viewer, `@fossil-lang/draw` went with it, and
`fossil-mcp` went for being a second binding. What is left on this side is one reader,
`@fossil-lang/corpus`, and this page is the shape it is going to have.

The shape is borrowed, and naming where it comes from is what makes it checkable rather than an
analogy. **Reading a corpus follows Apache Iceberg's read path**, Catalog → Table → Scan: a table is
loaded from its metadata, a scan is a filter plus a projection, planning turns the scan into tasks
pruned by statistics the writer published, and a task is read on its own. **Addressing follows the
OGC Two Dimensional Tile Matrix Set** (17-083r4) and OGC API – Tiles (20-057): a set of tile matrices,
coarsest first, and a tile named by its matrix and its position in it. Both are in
[prior art](/docs/design/prior-art#the-backend).

The view side has references of its own — deck.gl's `Tileset2D` for loading, Ark UI and TanStack for
the React surface — and they are kanzo-ui's to argue. What this page owns is where the seam is and
what crosses it.

## Three layers, and what each owns

| layer | what it owns | what it does not |
| --- | --- | --- |
| **writer** — `fossil run`, the layout pass | the bytes: payload tiles in Morton order, both adjacency orientations, the identity index, the cell pyramid and its quotients — and **the statistics of every tile it wrote** | any reader's question: which tiles a window needs, what a view draws |
| **manifest** — `graph.graph.yml` and one file per type | what a reader cannot recover without reading every footer: counts, the declared base of the pyramid, the tile matrix, and the per-tile statistics | anything derivable from what it already says |
| **reader** — `@fossil-lang/corpus` | planning (which tiles a scan needs, from the manifest alone) and reading (one tile, through the host's engine) | policy: caching, cancelling what went stale, drawing a parent while a child loads, prefetching — all of it is the view's |

The line under the reader is the one that matters. **A reader that caches is a second view.** The
reader's answers are pure functions of an address, a filter and a projection, which is what lets a
view cache them without asking; the moment the reader holds a cache of its own there are two
residency policies over one set of tiles, and the camera page measured what the first one cost to
build at the wrong seam ([the camera](/docs/design/camera)).

**What would reverse it.** A second view — anything other than kanzo-ui reading a corpus at
interactive rates — that would otherwise have to rebuild the same cache. Then the cache is shared
infrastructure, and it would belong in a package between the two, still not in the reader.

## The contract

This is everything that crosses. The types are the ones the reader will export; `Engine` and `Host`
are `@fossil-lang/types`' own (`packages/types/src/engine.ts, Engine`,
`packages/types/src/host.ts, Host`), and `SchemaResult` and the SQL pair are the verbs' generated
shapes, unchanged.

`Filter` is a tree, and it is Iceberg's expression vocabulary spelled as data:

```ts
type Literal = number | bigint | string | boolean;
type Filter =
  | { column: string; op: '=' | '!=' | '<' | '<=' | '>' | '>='; value: Literal }
  | { column: string; op: 'in' | 'not in'; values: readonly Literal[] }
  | { column: string; op: 'is null' | 'not null' }
  | { and: readonly Filter[] }
  | { or: readonly Filter[] }
  | { not: Filter };
```

`Box` keeps today's half-open rectangle, `x <= v.x < x + w` and the same in `y`. `CorpusTypes`,
`CorpusRelation`, `PlacedVertex` and the two errors are the ones `packages/corpus/src/index.ts`
already exports, with one addition: each vertex type carries its manifest's `channels:` block, which
the reader parses and does not surface today. `Direction`, `Gap` and `GapReason` are the ones
`packages/corpus/src/address.ts` exports — `src` reads the source-aligned half of a relation and
`dst` the target-aligned one.

What each member answers, in one line each:

- **`open`** — Iceberg's `StaticTable.from_metadata` for a URL, and the REST catalog's vended
  credential for a job. Two call shapes that differ only in where the bytes come from, and **both take
  the `Engine`**: the `query` callback that stood beside it is folded into the engine a host already
  has.
- **`tileMatrix(type)`** — the OGC `TileMatrixSet` for one vertex type: its extent, and one matrix
  per `z`, coarsest first, each listing **every tile with its row count and its box**. Synchronous,
  because it is the manifest bought at `open`, and total: `dense_id` is gapless and so is a rung's
  cell id, so no tile of any matrix is empty, and a view picks its zoom — the finest whose visible
  tiles' rows fit its budget — without a request.
- **`scan(params)`** — Iceberg's `Table.scan`: a type, a filter and a projection, **bound when it is
  built** — a column no matrix carries fails here, not on a read. No zoom and no box: a scan is
  built once per filter, not once per camera move.
- **`scan.plan()`** — Iceberg's `plan_files`: the tasks the scan needs **at every zoom**, pruned by
  the manifest's per-tile statistics and each carrying its residual. Synchronous for the same reason
  as `tileMatrix`. A filter naming a column cells do not carry has no task below `Z`.
- **`scan.read(address)`** — one tile, as a columnar batch, cancelled by its signal. It takes any
  address in the matrix, not only a planned one: a view builds `{ type, z, tile }` from what it sees,
  and the far end of an edge is the tile its `dense_id` shifts to. At `z = Z` a batch holds at most
  `tileRows` rows — 4,096 — so a finest tile can always be drawn as vertices.
- **`edges({ from, direction })`** — the relations incident to one tile out of the half aligned on
  `direction`, **and the ones it declined, with fossil's `GapReason`**: `not-declared` for an
  orientation the corpus does not publish, `other-space` for a relation whose far end is another
  type, which is read only when `relation` names it. At `z = Z` a batch is the adjacency's two
  columns; below it, the rung's quotient — `src_cell`, `dst_cell` and a `weight` — where the writer
  published one, source-aligned only.
- **`node`, `schema`, `relations`, `executeSql`** — unchanged: identity through the index, the
  verbs' introspection, what a SQL host registers, and the escape hatch behind `sql: 'allowed'`.

**Nothing else crosses.** `corpus.addressing`, the `CorpusAddressing` family, `QueryFn`,
`Answer` and every `Frame*` type leave the barrel; a consumer that needs a URL has outgrown a
surface whose claim is that a corpus is a URL.

**What would reverse it.** A view question that cannot be answered by composing these members
without reading a byte twice. The test is kanzo-ui's showcase: if the graph code there cannot come
down to a provider over `scan` and `edges`, something is missing here, and it is added as a member
rather than as a second path.

### What a row carries at each zoom

At `z = Z` a row is a vertex: the payload's columns, of which `select` chooses. `node` answers one by
identity with its `x` and `y`, so a pinned or searched vertex is placed without a scan, and its tile
is `denseId` over `tileRows`.

Below `Z` a row is a cell, and its columns are the writer's, not a projection of the payload's
(`crates/fossil-sinks/src/generated.rs, CELL_COLUMNS`): `cell_id`; `x` and `y`, **the centroid of
its members** — a mean weighted by membership, declared `derived` by `cell-member-centroid`; `count`,
how many vertices it holds; `internal`, the weight of the edges absorbed inside it; and `mode` and
`purity`, the majority value of **one** categorical and the share of the members holding it. Which
categorical is the tree's `mode_channel`, resolved against the type's `channels:`, and a channel's
`domain` is its value count over a writer's ordinal `0..domain` — which is the whole of what a
legend can be drawn from. So a view colouring by that channel colours a cell by `mode`; a view
colouring by any other column has no summary to colour with, and a view sizing by anything has
`count` and nothing else. **A cell summarises one channel and its membership, and not the row.**

**What would reverse it.** A second channel the writer summarises. Then `mode` stops being one column
with one referent, and a cell row grows a pair per channel, each naming its own.

## What is taken from Iceberg, and where fossil departs

| Iceberg | fossil | taken or departed, and why |
| --- | --- | --- |
| `Catalog.load_table`, `StaticTable.from_metadata(metadata_location)` | `open(url, { engine })`, `open(job, { engine, host })` | **Taken.** A corpus has no catalog service, so the URL case is the static table; the job case reuses what [storage access](/docs/design/prior-art#storage-access) already took from the REST catalog — a vended credential scoped to one prefix. |
| `Table.schema()` | `corpus.types` | **Taken**, read off the bytes at `open` for the reason `packages/corpus/src/open.ts, open` gives: the manifest declares three properties against seven columns on disk. |
| `Table.scan(row_filter, selected_fields, case_sensitive, snapshot_id, options, limit)` | `corpus.scan({ type, filter, select })` | **Departs twice.** No `snapshot_id`: a corpus is written once and never appended to, so there is one snapshot and nothing to name. **No `limit`**: a task is a tile, and a tile holds at most `tileRows` rows by construction, so every read is bounded by its address rather than by a clause. No zoom and no box either, though a camera always has both: a scan is planned once over every zoom, and which of its tasks a camera sees is the view's cull against the boxes `tileMatrix` publishes. |
| `EqualTo`, `In`, `IsNull`, `And`, `Or`, `Not`; `UnboundPredicate.bind(schema)` | `Filter`, bound in `scan()` | **Taken**, including the timing: an unknown column is an error at bind, before anything is planned. Spelled as JSON rather than classes so it crosses a worker boundary as it is. `StartsWith` and `IsNaN` are left out until something asks. |
| `plan_files()` → `FileScanTask { file, delete_files, residual }`; iceberg-rust adds `start`, `length`, `record_count` | `plan()` → `ScanTask { z, tile, rows, bbox, residual }` | **Departs on the unit.** A task is a **tile**, which under `container: rowgroups` is one row group — iceberg-rust's `start`/`length` split, not PyIceberg's whole file. No delete files: nothing is ever deleted from a corpus. The byte range stays inside the reader; a view keys on the address. |
| `_InclusiveMetricsEvaluator` over `lower_bounds`, `upper_bounds`, `null_value_counts` — *rows might match* | the planner over the tile manifest | **Taken as the pruning rule**: a tile is dropped only when its statistics prove no row can match, and a tile with no statistics for a column is kept. |
| `StrictMetricsEvaluator` — *rows must match*, which PyIceberg's planner does not use | `ScanTask.residual` | **Taken further than Iceberg takes it.** A tile whose bounds satisfy the filter outright carries a `null` residual and is read with no predicate beyond the range that selects it. |
| `ManifestEvaluator` over the manifest list's partition summaries | the zoom | **Departs.** A corpus has no partitions; the only coarse cut is `z`, every `z` is planned, and the view picks among them. |
| `to_arrow()`, `to_arrow_batch_reader()` over the whole scan | `scan.read(task)` per task | **Departs.** There is no whole-scan read, because the unit a view caches and cancels is the task. iceberg-rust's reader streams per task too; fossil makes that the only form. |

**The filter is data, not a SQL fragment**, and it is the filter language that was refused for
`read`'s `where` while `read` existed. The refusal does not transfer, because what it weighed is
different here. `where` was a query language beside `execute_sql`, buying read-time policy the
corpus has no chokepoint for. `Filter` buys **planning**: the planner evaluates it against statistics
before a byte is read, and a string cannot be evaluated without being parsed — which is the second
language again, spelled worse. It is rendered to SQL in one place, for one engine, and it carries no
`execute_sql` authority, so a view the hatch is closed to can hold one.

**What would reverse it.** Iceberg's shape stops fitting the day a corpus changes after it is
written — appends, deletes, a second snapshot. Then `snapshot_id` and delete files come back, and
with them Iceberg's own answer rather than an invention of ours. Short of that, a whole-scan read
comes back if a second consumer that is not a view — a batch job — needs one, and it would be a loop
over `plan()` in that consumer, not a member here.

## What is taken from OGC tile matrices, and where fossil departs

| 17-083r4 / 20-057 | fossil | taken or departed, and why |
| --- | --- | --- |
| `TileMatrixSet { id, crs, boundingBox, tileMatrices }` | `TileMatrixSet { type, coordinates, extent, tileMatrices }` | **Taken.** One set per vertex type. `coordinates` names the type's declared coordinate system ([where x and y come from](/docs/design/position)) where OGC names a CRS. `extent` is informative, exactly as the standard says `boundingBox` is: tiles are located by their own statistics, never by it. |
| `TileMatrix { id, scaleDenominator, cellSize, tileWidth, tileHeight, matrixWidth, matrixHeight }` | `TileMatrix { z, count, shift, tileRows, tiles }` | **Departs on the axis.** The matrix is one-dimensional: `tileRows` is `tileWidth` with `tileHeight` fixed at one, `tiles` is `matrixWidth` with `matrixHeight` at one, and `shift` plays `cellSize` — how many `dense_id`s one row at this `z` stands for, as a power of two. |
| tile address `(tileMatrix, tileRow, tileCol)`, `tileMatrix` a string id | `(type, z, tile)` | **Departs**, for the axis's reason. `z` is a number because it is compared and subtracted. |
| Annex I: tile indices from a bbox by arithmetic over `pointOfOrigin` and `cellSize` | every tile's box, published in the manifest and listed by `tileMatrix` | **Departs, and this is the one that is forced.** `dense_id` is a vertex's **rank** in the Morton order of its position, not its Morton code, and where a rank falls on the plane depends on how the positions are distributed — which no field of any matrix can carry. So the arithmetic that locates a tile runs on the rank axis, and which tiles a rectangle touches is read off the tiles' own boxes. |
| `tileMatrixSetLimits`: per matrix, the tile rows and columns that exist | a box and a row count per tile, in the manifest | **Taken and widened.** The standard publishes the range so a client does not compute it; a rank axis needs the box of every tile for the same reason. |
| WebMercatorQuad: matrix `z` is `2^z × 2^z`, four children per tile | the parent of `(z, t)` is `(z − 1, t >> (shift(z−1) − shift(z)))` | **Taken.** Between two rungs the difference is two bits — four children per tile, the quad tree's own branching. From the rows to the first rung it is the declared base, four bits at sixteen vertices per cell. |
| an out-of-range tile is a 404 or a 400 | `read` of an address outside `tiles` throws `CorpusReadError` | **Taken.** |

**What would reverse it.** A corpus whose positions sit on a grid a writer fixes in advance — a
raster, or a `geographic` plane quantised to a declared square — would make the rank and the code the
same number, and the Annex I arithmetic would then work unchanged. The published boxes would become
derivable, and a document carries a fact exactly when a reader cannot recover it, so they would go.

## The cell pyramid is the tile matrix

**The zoom levels are the pyramid that is already on disk**, and the arithmetic is the arithmetic
[cells](/docs/design/cells) decided, restated as matrices rather than rungs.

For a vertex type of `V` rows, a tile of `C` rows — `crates/fossil-sinks/src/manifest.rs,
TILE_SHIFT` is 12, so 4,096 — and a declared base of `b = 2^B` vertices per cell
(`crates/fossil-sinks/src/manifest.rs, DEFAULT_VERTICES_PER_CELL`, sixteen):

- **Rung `k` is matrix `z = R − k`**, where `R` is the rung holding a single cell, and the payload is
  **`z = Z = R`**. So `z = 0` is the root, one cell, and `z = Z` is every row — the standard's order,
  coarsest first.
- A row at rung `k` stands for `2^shift` ids, **`shift = B + 2(k − 1)`**
  (`crates/fossil-sinks/src/manifest.rs, CellTree`), and a cell id is `dense_id >> shift`. At `z = Z`
  the shift is zero and a row is a vertex.
- Matrix `z` holds **`count = ceil(V / 2^shift)`** rows in **`tiles = ceil(count / C)`** tiles,
  because a rung is tiled at the type's own `chunk_size` and declares none of its own
  (`crates/fossil-layout/src/layout/cells.rs, Pyramid`).
- **Tile `t` of matrix `z` is the contiguous `dense_id` range `[t·C·2^shift, (t+1)·C·2^shift)`.**
  Every tile at every zoom is an interval of one axis, which is what lets a single conjunctive range
  select it and lets its parent be a shift.

Three corpora, every figure derived from those four lines rather than measured:

| | com-DBLP, 317,080 | the bench corpus, 1,000,000 | 10,000,000 |
| --- | --- | --- | --- |
| `Z` | 9 | 9 | 11 |
| tiles at `z = Z` | 78 | 245 | 2,442 |
| rung 1 (`z = Z − 1`), cells · tiles | 19,818 · 5 | 62,500 · 16 | 625,000 · 153 |
| rung 2, cells · tiles | 4,955 · 2 | 15,625 · 4 | 156,250 · 39 |
| rung 3, cells · tiles | 1,239 · 1 | 3,907 · 1 | 39,063 · 10 |
| every tile at every `z` | 92 | 272 | 2,654 |

The last row is what the tile manifest holds, one entry per tile, and it is why publishing it is
cheap: at ten million vertices it is 2,654 entries, against the 4,892 footer reads an open costs
without it.

What is kept from [cells](/docs/design/cells) unchanged: the base is declared and never derived;
the partition is quaternary, so a cell carries no `parent` column; a rung is summarised from the
payload, never folded from the rung below; the quotient is source-aligned and tiled on its source
cell's tile (`crates/fossil-layout/src/layout/cells.rs, write_quotient`); and a cell is not an entity,
so `node` never returns one.

**What would reverse it.** A base that is not a power of four. Then a rung's shift stops being an
integer number of bits and the parent stops being a shift — which is why
`crates/fossil-sinks/src/manifest.rs, CellTree` refuses one — and the tile matrix would need a
`scaleDenominator` in earnest.

## The sample goes: below `Z` there are only cells

**Every `z < Z` is a rung, and the level files are retired**: `vertex/<Type>/l{k}/`, the relation
levels beside the adjacency, `crates/fossil-sinks/src/manifest.rs, VertexLevels`,
`crates/fossil-layout/src/layout/pass.rs, write_levels` and
`crates/fossil-layout/src/layout/pass.rs, write_edge_levels`.

This reverses a row of [what was discarded](/docs/design/discarded), and the row said what would do
it: *a reader that addresses a cell — or, failing that, those three readers going away.* Both
happened.

- **The three readers are gone.** A crossfilter mask indexed by `dense_id` and a residency pass that
  deduplicated answers taken at two levels were the playground and `@fossil-lang/draw`, deleted on
  2026-09-29. The third was `pinned`, which exists only on `frame`, and `frame` is retired below.
- **A cell is addressable.** A cell id is `dense_id >> shift`, and `(type, z, tile)` names the tile
  holding it by the same arithmetic that names a payload tile. A view that pins a vertex holds its
  `dense_id`, and at any `z` the cell containing it is one shift away — the pin draws as its cell,
  with no second read.

**The edge argument is not answered by bytes, and it is paid.** An edge level was the only artefact
whose rows carried both endpoints' coordinates, so a coarse view could draw real edges off one file.
Below `Z` the lines are now the rung's quotient where the writer published one, and nothing where it
did not; a coarse view draws the field and not the relation, which is the conclusion
[cells](/docs/design/cells#no-coarse-quotient-is-drawable-and-the-partition-is-not-the-reason) had
already reached about every rung but the finest. What is bought is one multiscale structure instead of
two, and the bytes of the one that goes: on com-DBLP the level pyramid is **83.1%** of
payload-plus-adjacency against the cell pyramid's **8.1%**.

**What would reverse it.** A view that needs a real row at a coarse zoom — something that clicks,
masks or brushes by `dense_id` where the rows at `Z` under the cell are too many to read. It is not
enough that a view wants to *identify* what is under a cell: the rows are one shift away, at `Z`,
and a view can read the tiles under one cell without reading the rectangle.

## The ten measured costs, and which ones the backend closes

These were measured on 2026-09-29 in kanzo-ui's reader over this package. Six are the backend's to
close, two are the view's, and two are closed by the shape of the contract rather than by any one
mechanism.

| # | the cost | closed by | whose |
| --- | --- | --- | --- |
| 1 | under `rowgroups` each slice read the whole vertex file and the whole `by_source` file | a task is one row group, selected by one conjunctive `dense_id` range | backend |
| 2 | an anchor CTE's `NOT (bbox)` scanned every vertex outside the window | no anchors: a far end is read by its tile's address | contract |
| 3 | the edge join was O(E) per slice, with no range predicate on `src_dense` | `edges({ from })` reads the aligned adjacency's rows for one tile's id range | backend |
| 4 | the same CTEs were computed twice per slice, once for points and once for links | points and edges are separate reads of separate tiles, each cacheable on its own | contract |
| 5 | `count(*) OVER ()` materialised the whole match before sampling | counts are the manifest's; nothing samples, because coarse is a lower `z` | backend |
| 6 | no tile cache: every pan re-asked the whole rectangle | answers are pure functions of an address, so the view caches by `(type, z, tile)` | view |
| 7 | superseded queries were not cancelled | `AbortSignal` on `read` and `edges`, handed to the engine | backend |
| 8 | opening cost a footer read over every payload file — 4,892 requests, 40 MB at ten million | the writer publishes every tile's statistics in the manifest | backend |
| 9 | every slice re-uploaded every GPU buffer and rendered twice | per-tile batches a renderer can append rather than replace | view |
| 10 | no `by_target` read: an edge whose source is off-screen was never drawn | `edges({ direction: 'dst' })` reads the target-aligned adjacency | backend |

### Pruning is the manifest's, at tile granularity

A read selects one tile with **one conjunctive range** on the aligned column — `dense_id` for a
vertex tile, `src_dense` or `dst_dense` for an adjacency — and never a disjunction of them. That is
the one shape the engine is measured to prune row groups on. `packages/corpus/src/identity.ts,
indexRanges` records DuckDB pruning a conjunctive range and declining a disjunction over a string
column, and `crates/fossil-graph/src/lib.rs` records 179 `BETWEEN … OR …` ranges evaluated per row
rather than skipped — which is why a batch of tiles is a batch of reads and not one read with an
`OR`.

What the planner prunes with is the tile manifest: a lower and an upper bound for every ordered
column of every tile. `cluster_id` is the one worth naming — communities are placed together, so a
filter on it prunes tiles a camera would otherwise read. The box is in the same manifest and prunes
nothing here: which tiles a camera sees is the view's cull, against the boxes `tileMatrix` lists.

**What would reverse it.** An engine that prunes a disjunction of ranges, measured: then a batch of
tiles becomes one read and the per-tile form costs round trips for nothing.

### The writer publishes what the reader used to read from footers

`packages/corpus/src/tile-manifest.ts, footers` reads every tile's footer while the corpus opens,
and does it there on purpose: a level that arrived as a promise would be a request between the camera
moving and an address being computable. The rule survives and the cost does not. **The writer already has every
number the footer sweep recovers**, so it writes them once, beside the bytes, and `open` reads one
file per type instead of one footer per tile.

It is a manifest in Iceberg's sense: a columnar file of per-tile statistics, one row per tile of
every artefact of the type — payload, each rung, each quotient, each adjacency orientation — carrying
the tile's address, its row group, its byte range, its row count, its box and its column bounds. A
row group that was never written, because the tile's vertices have no edges, has no row; the
adjacency's row-group ordinal stops being something a reader has to find out.

**What would reverse it.** A writer other than fossil's. The statistics are then a claim the reader
has to check rather than trust, and a guard over the footers is the check —
`packages/corpus/guards` is where it would live.

### Cancellation is a signal the engine honours

`read` and `edges` take an `AbortSignal` and hand it to the host's engine; a view that moved past a
tile aborts it. **The reader does not decide what is stale** — that is the view's cache — it only
makes a stale read stoppable.

**The signal has to reach the running query, not the queue.** A DuckDB-WASM connection runs one
statement at a time, so a view keeps one read in flight rather than deck.gl's six, and an abort that
only dropped queued work would leave the one read that matters — the running, stale one — to finish.
So `Engine.query` takes the signal and the host's engine interrupts the statement it is running —
[the ruling](#four-rulings-the-contract-rests-on) below, beside the Arrow-shaped answer.

**What would reverse it.** Reads short enough that cancelling costs more than finishing. A tile is
4,096 rows, so this is plausible, and it is one measurement: the wall time of a single-tile read
against the latency of a cancel on the host's engine.

## How the reader splits

`packages/corpus/src/corpus.ts` was 2,570 lines, and the seams above are where it came apart. Each
module follows one of the two references and none of them reaches 500 lines.

| module | follows | what it holds | out of `corpus.ts` |
| --- | --- | --- | --- |
| `open.ts` | Iceberg's `load_table` | the two shapes, the manifest read, lending, the catalog's holders and `close`, and the `Corpus` assembled from one factory per module | `open`, `vended`, `opened` |
| `tile-matrix.ts` | OGC 17-083r4 | the matrices from the manifest: `z`, shift, counts, the parent and the child range | `levelForCanvas`'s arithmetic, what `levelsOf` and `strideOf` spelled |
| `tile-manifest.ts` | Iceberg's manifest | reading the published per-tile statistics once per type | `tileBoxes`, `footers`, `bytesOf`, `runsOf`, `extent` |
| `expression.ts` | Iceberg's expressions | `Filter`, binding it to a matrix's columns, the inclusive and strict evaluators, and rendering the residual as SQL | the box predicate `boxOf` |
| `scan.ts` | Iceberg's `Table.scan` | `scan`, `plan`, `read` | the tile selection in `sampledRead` and `rows` |
| `frame.ts` | — | `frame` and its types, until step 5 retires them | `frame`, `Frame`, `FrameParams`, `FrameCost`, `CoarseSource` |
| `edges.ts` | CSR and CSC | `edges`, over the adjacency at `Z` and the quotient below it | `readEdges`, `adjacencyFor`, `neighbours` |
| `identity.ts` | — | `node`: the index seek, its key ranges, byte-order comparison | `findByIdentity`, `indexRanges`, `couldHold`, `vertexOf` |

`corpus.ts` keeps the surface's own types — `Corpus`, `SqlCorpus`, `CorpusTypes`, `CorpusRelation` —
and each member's types went with the member. `frame.ts` is the one module no reference names: the
composition `frame` runs has no seam of its own, and holding it apart is what lets step 5 delete a
file rather than carve one. `address.ts` stays the one bridge to
`crates/fossil-graph/src/plan.rs, ReadPlan`, and shrinks by everything a level was. `index.ts` stays
the barrel.

**What would reverse it.** A module that cannot be stated against its reference without importing
another module's internals. That is the sign the seam is wrong, and it is moved rather than the
module being allowed to grow.

## What dies, and in which order

| retired | folded into |
| --- | --- |
| `frame`, `Frame`, `FrameParams`, `FrameCost`, `Pixels`, `CoarseSource` | `scan` at a `z`: the view picks the zoom, and a tile's cost is its row count |
| `rows`, `RowsParams`, `RowsAnswer`, `Answer` | `scan` at `Z` plus `edges`, whose `declined` carries the `Gap`s an answer used to |
| `extent`, `Extent` | `tileMatrix(type).extent` |
| `neighbours`, `Neighbourhood` | `edges` from the tiles holding the seeds; a walk of more than one hop is the caller's loop |
| `levelsOf`, `LevelInfo`, `strideOf`, `strideBits`, `rowsAt` | `tileMatrix` |
| `corpus.addressing` and the `CorpusAddressing` family, `QueryFn` | internal; the engine is the one capability |
| `VertexLevels`, `write_levels`, `write_edge_levels`, every `l{k}/` | the cell pyramid |

The order is fixed by one rule: **nothing is deleted while something still reads it.**

1. **The writer publishes the tile manifest**, and a guard holds it against the footers. Additive; no
   reader changes.
2. **`corpus.ts` splits into the modules above**, behaviour unchanged, so the diff that moves code is
   not the diff that changes it.
3. **`tileMatrix`, `scan` and `edges` land** on those modules, reading the tile manifest. The
   conformance suite holds `scan` at `Z` against `rows` over the same box, and a rung read through
   `scan` against the aggregation obligations of [cells](/docs/design/cells).
4. **kanzo-ui moves `@kanzo-tech/graph` onto them.** That is kanzo-ui's phase, and fossil waits for it.
5. **The reader's retired members go**, with every type that only they named.
6. **The writer stops emitting the level files**, the manifest stops declaring them, and the fixture is
   regenerated — last, because until step 5 a reader still asks for them.
7. **The pages that describe `frame` are rewritten to what replaced it** — [one door](/docs/design/one-door),
   [the camera](/docs/design/camera) — and this page loses its `direction:`.

**What would reverse it.** A consumer outside kanzo-ui that reads `frame` or the level files. There
is none that this repository can find, and keasy consumes this repository by git tag, so step 5 is
preceded by asking rather than by a grep.

## Four rulings the contract rests on

**A filter on a payload column has no task below `Z`.** A cell's `count`, `mode` and `purity`
summarise every member, so a view that filters the rows — a crossfilter brush — has no precomputed
answer at a coarse zoom, and `plan()` gives it none: the view gets rows or nothing. Recomputing the
rung from the rows at `Z` would read every row under the camera and make a coarse read cost what a
fine one does, which is the property the tile matrix exists to prevent.

**What would reverse it.** A view that needs the filtered field at a zoom where the rows do not fit —
a crossfilter brush over a corpus of ten million is the likely first — and a writer willing to
summarise per filter value, which is a second pyramid per channel rather than a reader-side fallback.

**Rows and cells cross only while loading.** A cell tile is drawn until the row tiles under it
arrive, and then it goes: the two are never on screen together at rest. That is the one crossing
[cells](/docs/design/cells) admits, and it is the same condition stated there. The backend's part is
that both are addressable in one matrix and a parent is a shift of its child; when to swap is the
view's.

**What would reverse it.** A reader measured to be lost at the swap — a click or hover that lands on
a cell and resolves to a row, or the reverse, while the two are both drawn — which would mean the
loading window is long enough to be interacted with, and the parent has to stop answering input
before it stops being drawn.

**Below `Z`, edges come only from the quotient.** The level files are retired, relation levels
included, so a coarse zoom draws the rung's quotient where the writer published one and no lines
where it did not. The argument is [above](#the-sample-goes-below-z-there-are-only-cells); this is
the ruling.

**What would reverse it.** A coarse view whose lines are measured to be what its reader needs and
which no quotient can draw — real edges between real vertices at a far zoom — which is the
self-drawing edge level coming back as a third artefact beside the cells, not as a second pyramid of
rows.

**`Engine.query` takes an `AbortSignal` and returns Arrow-shaped data.** The signal reaches the
running statement, and the answer is a table a `Batch` reads, so no reader turns columns into objects
and back. It lands in `packages/types/src/engine.ts, Engine` in phase 4, and every host that
implements `Engine` moves with it — keasy among them.

**What would reverse it.** A host engine that can neither interrupt a statement nor answer in
columns. Then the reader converts at the boundary and drops a stale answer instead, and both costs
are measured rather than assumed.

## What this does not settle

**Where the tile manifest lives.** One file per vertex type, named from its YAML, is Iceberg's
manifest-list-to-manifest shape. Inline in the YAML is one fewer request and a larger document to
parse on every open. It is decided in phase 4 by one measurement: the open time of both at ten
million vertices.
