---
title: Its RDF meaning, as a mapping
description: mapping.ttl is an RML-Core mapping that says what the tables mean as RDF — classes, predicates, term types, datatypes, languages and annotations. A reader obtains triples from it as one seven-column relation over the tables, with no fossil code.
---

A graph is a property graph in Parquet, and its meaning as RDF is **`mapping.ttl`**, beside the graph
document. It is an RML-Core mapping in Turtle: for each vertex type, which class its subjects are
and which predicate each column is; for each relation, the predicate between the subjects its two
ends name; for each value, the term type, the datatype and the language. A reader who wants triples
runs it over the tables instead of re-deriving the interpretation. **Nothing in the graph's YAML says
any of it**: GraphAr has no word for a class, a predicate or a datatype.

The mapping is the writer's, not a reader's guess. The *content* — which class, predicate, term
type, datatype and language column — is the program's, so the run that writes the tables writes it.
The *mechanism* — parsing the mapping, writing it, rendering it as a relation — is rudof's, through
its `rml` crate.

## RML-Core, and why

The reference is RML-Core, a Draft Community Group Report of 16 March 2026 ("not a W3C Standard nor
is it on the W3C Standards Track"), with RML-IO for the logical source. R2RML is a W3C
Recommendation and has no per-row language tag: a term map's language is a specified tag, the value of
`rr:language` (R2RML §7.5). A language tag read
from a column is `rml:languageMap` in RML-Core, which "follows exactly the same syntax as R2RML", so
one vocabulary does the whole document. Only RML-Core's core is used: RML-LV's logical views are not,
and a join is a query.

## One example, read

The walking skeleton's mapping ([the graph it describes](/docs/format#the-walking-skeleton)) is
one triples map. This is the vertex map of a larger mapping that the `rml` crate's own test cases
read, with a datatype beyond GraphAr's:

```turtle
@prefix rml: <http://w3id.org/rml/> .
@prefix ex: <https://example.org/> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

<#Person> a rml:TriplesMap ;
  rml:logicalSource [ rml:source [ a rml:Source ] ; rml:referenceFormulation rml:SQL2008Table ; rml:iterator "Person" ] ;
  rml:subjectMap [ rml:reference "subject" ; rml:termType rml:IRI ; rml:class ex:Person ] ;
  rml:predicateObjectMap
    [ rml:predicate ex:birthYear ; rml:objectMap [ rml:reference "birth_year" ; rml:datatype xsd:gYear ] ] ,
    [ rml:predicate ex:postcode ; rml:objectMap [ rml:reference "postcode" ] ] .
```

Read: a row of the table `Person` is a subject whose IRI is the column `subject` and whose class is
`ex:Person`; its `birth_year` is a literal of datatype `xsd:gYear` under `ex:birthYear`; its
`postcode` is a literal of its natural datatype under `ex:postcode`. `birth_year` is an `int32`
property in the YAML, and the year lives only here.

## The logical source is a SQL name, and the host resolves it

RML-IO §3.1 gives a logical source "exactly one source (`rml:source`)", and for a relational source
the value of `rml:iterator` is "either a SQL query (`rml:referenceFormulation rml:SQL2008Query`) or
the SQL table name (`rml:referenceFormulation rml:SQL2008Table`)", the table name being a shortcut
for `SELECT * FROM {table}`. So the writer emits one source per logical source, and **an anonymous
`[ a rml:Source ]` is all it can honestly say**: the logical sources are SQL names, which the host
resolves to the relations that hold them when it builds the relation, and a source description naming
a file would claim what the host decides. How the source is reached is, in RML-IO's words, outside
its scope.

Two reference formulations are written: `rml:SQL2008Table`, named by a vertex type's table, and
`rml:SQL2008Query`, for a relation and for a multi-valued property. A table named inside a query is
resolved by the host the same way.

## What each part means

**The names of the triples maps** are fixed by the writer and are never an output: `<#Person>` for a
vertex type, `<#Person_nickname>` for a multi-valued or language-tagged property (`<#Type_property>`),
and `<#Order_placedBy_Person>` for a relation (`<#Src_label_Dst>`, the whole triple, so two relations
with one label cannot collide).

**Identifiers inside a query are always double-quoted** (`"Order"` is a keyword in SQL), except the
fixed aliases the query itself introduces (`subject`, `value`, `lang`, `source`, `target`, `s`, `d`,
`e`). `rml:reference` of a column is its bare name, delimited only when it is not a plain identifier.

**A type or a column that has no IRI is not mapped**: a graph of a program that names no shape has
tables and no RDF meaning, and a vertex map that would have no class and no column is omitted.

**A vertex type** is a triples map over its table. The subject map reads `subject` as an IRI and
types it with the class (`rml:class`, RML-Core §6.2); each single-valued property is a
predicate-object map reading its column.

**A relation** is a triples map over a query that joins the edge table to its two vertex tables on
the index, and reads the two subjects. For the relation `Order_placedBy_Person`:

```turtle
<#Order_placedBy_Person> a rml:TriplesMap ;
  rml:logicalSource [ rml:source [ a rml:Source ] ; rml:referenceFormulation rml:SQL2008Query ;
    rml:iterator "SELECT s.subject AS source, d.subject AS target FROM \"Order_placedBy_Person\" AS e JOIN \"Order\" AS s ON e._graphArSrcIndex = s._graphArVertexIndex JOIN \"Person\" AS d ON e._graphArDstIndex = d._graphArVertexIndex" ] ;
  rml:subjectMap [ rml:reference "source" ; rml:termType rml:IRI ] ;
  rml:predicateObjectMap [ rml:predicate ex:placedBy ; rml:objectMap [ rml:reference "target" ; rml:termType rml:IRI ] ] .
```

The index columns are read by the query and by no term map: a mapping whose term maps do not read an
index, a row position or a blank node is layout independent
([the round trip](/docs/format/round-trip)).

### A multi-valued property

A multi-valued property is a column of a list, and its logical source unnests the list once, so each
row is one element. A tagged one is a list of `(value, lang)` structs, and the object map reads the
value and the tag from the same row. A single-valued tagged property is a bare struct and is read the
same way through `col.value` and `col.lang`, with no unnesting:

```turtle
<#Person_nickname> a rml:TriplesMap ;
  rml:logicalSource [ rml:source [ a rml:Source ] ;
    rml:referenceFormulation rml:SQL2008Query ;
    rml:iterator "SELECT subject, n.value AS value, n.lang AS lang FROM (SELECT subject, unnest(\"nickname\") AS n FROM \"Person\")" ] ;
  rml:subjectMap [ rml:reference "subject" ; rml:termType rml:IRI ] ;
  rml:predicateObjectMap [ rml:predicate <https://example.org/nickname> ;
    rml:objectMap [ rml:reference "value" ; rml:languageMap [ rml:reference "lang" ] ] ] .
```

This is RML-Core as written. Its §8.5 makes the terms of a language map "the n-ary Cartesian
product combination of T × L" of the values and the tags of one iteration; a struct holds the value
and its tag as one element, so the product of one value and one tag is one term, and there is no
alignment of two lists to get wrong. An untagged one unnests the list the same way and reads the
value without a language map.

## Terms

- **The term type** is `rml:IRI` for a subject and for a value the shape declares an IRI, and a
  literal otherwise.
- **The datatype** is the shape's, verbatim: `rml:datatype xsd:gYear` stays `xsd:gYear` whatever the
  column's type. A value the shape declares an IRI is `rml:termType rml:IRI` and has no datatype.
  Where a shape declares none, the writer states one only where the column's type would lose it:
  `xsd:gYear` for a year, `xsd:time` for a time, and `xsd:decimal`, `xsd:time` or `xsd:hexBinary` for a
  column [the writer stored as text](/docs/format/conventions/datatypes). Everywhere else the object
  map states none, and the literal is the column's **natural** one: the natural mapping of SQL types
  to XSD of R2RML §10.2 — an integer type is `xsd:integer`, `float` and `double` are `xsd:double`,
  `boolean`, `date` and a timestamp are their XSD types, and a string, and anything else, is
  `xsd:string`. `rml` decides it by the engine's own type of the column.
- **A language-tagged value is an `rdf:langString`**: the lexical form is the value, and the tag is
  the column the language map names, lower-cased by the writer (RDF 1.1 Concepts §3.3: the value
  space of language tags is lower case).
- **A null makes no term** (RML-Core §12.2: "If the value is null, empty or missing, then no RDF term
  is generated"). A data error — an invalid IRI, an ill-typed datatype override, a tag that is not
  BCP 47 — is an abort in a processor (§4.3) and cannot be one in a query, so only the shape of an
  absolute IRI is looked at, a datatype override is trusted, and an empty or NULL tag makes no term.
  The writer is where those are refused.

## Annotations

What a type, a column or a relation is called and described as is carried as **plain triples about
the class and predicate IRIs the mapping names**, in the same document:

```turtle
<https://example.org/Person> rdfs:label "Person"@en ;
                             rdfs:comment "A person we hold a record of."@en .
```

RML-Core §3.2 allows a mapping graph to "contain documentation in the form of rdfs:label,
rdfs:comment and similar properties", and §12 holds the output dataset to the triples the triples
maps generate, so the annotations are not part of it: they are read by `Mapping.model()`, below, and
make no triple in the relation. A label on a predicate is one label, whichever class uses it; where
a class needs its own, that is a shape's `sh:name`, which this mapping does not carry.

They are statements about the vocabulary and not about the data, and a reader that loads
`mapping.ttl` into the same store as the data asserts them there.

## The bytes of the file are not reproducible

rudof's Turtle writer fixes neither the numbering of blank nodes nor the order of subjects, so two
runs of one program write the same mapping and different bytes. **A mapping is compared parsed**, as
the set of its triples maps and annotations, never as text; the writer's own tests do the same.

## What `rml` supports, and what it refuses

The supported subset is the one the writer emits. `rml` models constants, references, templates,
`rml:class`, language maps and constants, `rml:datatype`, `rml:baseIRI` on a triples map, and
referencing object maps joined on references. **It refuses the rest by name** — with an error
that says which construct, not read and dropped, because dropping it would change what the
mapping means: graph maps, the `rml:URI` and `rml:UnsafeURI` term types, a blank node map
without an expression, a datatype map that is not a constant, a template as a language map, a join
condition whose child or parent map is not a reference, and every reference formulation but
`rml:SQL2008Table` and `rml:SQL2008Query`.

**The base IRI.** RML-Core §4.1.1 requires one to be defined "within the mapping document for each
Triples Map or as execution environment", and fixes `http://example.org/` as the default when none is.
The writer always emits absolute IRIs, so for a mapping fossil wrote it never applies;
`Mapping.parse` takes a `base` for a mapping that does not. The triples map ids (`<#Person>`) are
names inside the document and never an output.

## Obtaining the triples

`@kanzo-tech/rudof-wasm` carries the mapping to a page:

```ts
import { Mapping } from '@kanzo-tech/rudof-wasm';

const mapping = Mapping.parse(text);                       // text of mapping.ttl; { base? } optional
await mapping.triples({                                    // creates or replaces the view `into`
  engine, into: `"${job}".triples`,
  tables: (t) => `"${job}"."${t}"`,                        // each table the mapping names → its relation
  signal,
});
mapping.model();                                           // what it says, per table, without a query
```

`triples` creates the view `into` as the mapping's triples, over the relations `tables` resolves,
and reads nothing: the view is a query, run when it is read. The names the page gives are read as SQL
object names, and a failure is reported before any statement is sent. The dialect is DuckDB's.

**The relation has seven columns**, the ones `shacl`'s SQL validator reads:

| column | what it holds |
| --- | --- |
| `s_type`, `s_value` | the subject's type, `I` for an IRI or `B` for a blank node, and its IRI |
| `p` | the predicate IRI |
| `o_type` | the object's type: `I` for an IRI, `B` for a blank node, `L` for a literal |
| `o_value` | the object's IRI, or its lexical form |
| `o_datatype` | a literal's datatype IRI — `xsd:string` for a simple one and `rdf:langString` for a tagged one — and `''` for an IRI |
| `o_lang` | a tagged literal's tag, and `''` for every other term |

The suffixes are SPARQL 1.1 Query Results JSON's names for a term's parts. Every column is `VARCHAR`
and none is null. No standard defines a triples table; the columns belong to rudof, which is both
their producer and their consumer. The output of a mapping is a set (RML-Core §12.1.1: "RDF graphs
MUST NOT contain duplicate triples"), and this relation may hold a triple twice, so a reader reads
it as a set.

`mapping.model()` answers, per triples map, what it says without running anything: its source, how
a row is named, its classes, and per column the predicate, the term type (RML-Core's default applied),
the datatype, the language — a constant tag or the column that holds it — and the annotations about
the class and the predicate. A reader that wants a label, a year axis or a language reads it here,
after its first paint if it likes; the graph's tables never need it.
