---
title: What a corpus is
description: A graph on disk that outlives the process that wrote it, read by code that was never compiled against it — one fossil.json, a Parquet file per vertex type, one per relation and one per multi-valued property. The artifact is the API.
---

A **fossil corpus** is a graph written to disk: a Parquet file per vertex type, a Parquet file per
relation, one per multi-valued property, and one small JSON manifest that names them. It is read by code that was not compiled
against the code that wrote it.

That last clause is the whole design. A corpus is not a serialisation of somebody's object graph —
it is the interface. **The seam between the two halves of fossil is the corpus on disk, not an
API.** A reader needs the manifest, a Parquet reader and the conventions on these pages, and nothing
else of fossil's.

<Callout title="Two products, one repository">
The other half of fossil is a statically-typed language that produces a graph, taught in
[the book](/docs/book/getting-started). Nothing here requires it: a corpus is readable by anyone with a Parquet reader, and the
conventions below are what makes that true instead of merely possible.
</Callout>

## One file is named in advance

A reader over HTTP cannot list a directory, so nothing is discovered by listing. `fossil.json` is the
one name known in advance, and it names every other file by its path relative to the corpus root.

```
<dest>/
  fossil.json                         the manifest, written last
  vertex/<Type>.parquet               one per vertex type
  edge/<Src>_<label>_<Dst>.parquet    one per relation
  property/<Type>_<name>.parquet      one per multi-valued property
```

**`fossil.json` is written last, and its presence is the commit.** A directory holding Parquet and
no manifest is a write that did not finish, and a reader treats it as no corpus at all. Nothing else
marks a corpus complete, and nothing else needs to: every file the manifest names is on disk before
the manifest is.

```jsonc
{
  "format": "fossil/1",
  "vertex_tables": [{
    "name": "Person",
    "iri": "https://example.org/#Person",
    "path": "vertex/Person.parquet",
    "key": "dense_id",
    "identity": "subject",
    "record_count": 1000000,
    "derived_from": ["@crm/people.csv"],
    "properties": [
      { "name": "dense_id", "type": "uint32", "role": "address" },
      { "name": "subject", "type": "string", "role": "identity" },
      { "name": "birth_year", "type": "int32", "nullable": true }
    ]
  }],
  "edge_tables": [{
    "name": "Order_placedBy_Person",
    "label": "placedBy",
    "path": "edge/Order_placedBy_Person.parquet",
    "source":      { "key": "src", "references": "Order" },
    "destination": { "key": "dst", "references": "Person" },
    "record_count": 2000000,
    "derived_from": ["@crm/orders.csv", "@crm/people.csv"],
    "properties": [
      { "name": "src", "type": "uint32", "role": "endpoint" },
      { "name": "dst", "type": "uint32", "role": "endpoint" }
    ]
  }],
  "property_tables": [{
    "name": "Person_nickname",
    "path": "property/Person_nickname.parquet",
    "source": { "key": "src", "references": "Person" },
    "record_count": 1500000,
    "derived_from": ["@crm/people.csv"],
    "properties": [
      { "name": "src", "type": "uint32", "role": "endpoint" },
      { "name": "nickname", "type": "string", "iri": "https://example.org/#nickname" }
    ]
  }]
}
```

The vocabulary is SQL/PGQ's rather than any graph-archive format's: a **vertex table** and an **edge
table**, each with a `key`, and an edge table's `source` and `destination` naming the key column and
the vertex table it `references`. A table's `name` is what a reader registers it under, and it is
unique across the corpus. An edge table's `label` is not: one label can join several pairs of types,
so `Src_label_Dst` is the name and `label` a field beside it.

**A multi-valued property is a table of its own**, a row per value: `src`, the `dense_id` of the
vertex the value belongs to, and the value under the property's name, which carries its `iri` and
term as a vertex column does. It is first normal form because a cell is one RDF term — R2RML maps
one cell to one term (§10.2) and an array is no Core SQL — and because a relational source already
spells several values as several rows. A single-valued property stays a column of its vertex table.
`property_tables` is absent when the program declares no multi-valued or language-tagged property,
and a writer refuses a program whose table names would collide.

**A language-tagged property is a property table too, whatever its cardinality**, with a third
column: `lang`, the value's BCP 47 tag, whose `properties` entry carries the role `language`. The
value column's `datatype` is `rdf:langString` and `term_type` `rr:Literal`; each row is one
`rdf:langString` literal, the value its lexical form and `lang` its tag, well-formed by RFC 5646
§2.2.9 as RDF 1.1 Concepts §3.3 requires. It is a property table because that is where the tag has a
fixed column name, and because one value per language is the ordinary case — SHACL's `sh:name`
«should only have one value per language tag».

| field | what it says | what a reader does with it before reading Parquet |
| --- | --- | --- |
| `format` | `fossil/1` | refuses any other value |
| `name`, `path` | the table and its file | registers one relation per table |
| `key`, `source.key`, `destination.key` | `dense_id`, `src`, `dst` | joins edges and properties to vertices without knowing column names |
| `identity` | `subject` | keys anything held outside the corpus |
| `record_count` | the rows in the file | sizes buffers, and checks a file it read in full |
| `derived_from` | the sources the table's rows were derived from, PROV-O's `prov:wasDerivedFrom` | names a table's inputs without the program |
| `properties` | every column, in order, with its type | knows the schema without opening a footer |
| `properties[].role` | what a column the writer emits IS | tells the writer's columns from the program's without a list of names |
| `properties[].term_type`, `.datatype` | the RDF term the shape declares for the values | states the column's RDF meaning without re-deriving it |
| `annotations` on a vertex table, an edge table or a column | what the type, the relation or the field is called and described as: ShEx 2.1's `Annotation`, verbatim | names them in a person's language without the program |
| `references` | the vertex table at each end | knows which relations join which types, and whose values a property holds |
| `properties[].stats` | the column's counts over every row of the table | knows nulls, distinct values, bounds and commonest values without a scan |
| `candidate_keys` | the columns never null and never repeated | knows a table's identifiers without counting |
| `inclusions` | columns whose every value is a value of another table's candidate key | finds a join the program did not declare as an edge |

`type` is one of `string`, `bool`, `int8` … `int64`, `uint8` … `uint64`, `float`, `double`, `date`,
`timestamp`, `time` and `decimal` — `corpus.bnf`'s spellings, written by
`crates/fossil-df/src/corpus/manifest.rs, data_type_name`. The JSON Schema of the whole document is
`crates/fossil-df/src/corpus/fossil.schema.json`. `iri`, `nullable`, `term_type`, `datatype`,
`derived_from`, `annotations`, `stats`, `candidate_keys` and `inclusions` are optional and absent when
there is nothing to say.

**`annotations` are the shape's and the program's.** Each is ShExJ's Annotation (ShEx 2.1 §5.9),
`{ "predicate": <IRI>, "object": <objectValue> }`, where the object is an IRI as a bare string or a
literal as `{ "value", "language"?, "datatype"? }` — `datatype` where ShExJ writes `type`, the same word
a column uses for a datatype IRI:

```jsonc
"annotations": [
  { "predicate": "http://www.w3.org/2000/01/rdf-schema#label",
    "object": { "value": "fecha de nacimiento", "language": "es" } }
]
```

A vertex table's are its type's, an edge table's its relation's, a column's its property's. A label
has one predicate, `rdfs:label`, and a description one, `rdfs:comment`, whichever document gave it:
SHACL's `sh:name` and `sh:description` on a property shape are written as `rdfs:label` and
`rdfs:comment` annotations, ahead of any the same shape carries under those predicates. They state
nothing about the data, and [the corpus as triples](/docs/format/reading/rdf) holds none of them.

**`stats`, `candidate_keys` and `inclusions` are the writer's count of what it wrote**, taken over
every row of every table, exactly:

```jsonc
"stats": { "null_count": 31, "distinct_count": 975, "min_value": "1817-11-30", "max_value": "1997-07-12",
           "top_values": [{ "value": "1898-06-13", "count": 2 }] }
```

`null_count` is the rows with no value and `distinct_count` the distinct non-null values — Parquet's
`Statistics` names. `min_value` and `max_value` are the least and greatest value, and `top_values` the
ten commonest non-null values that occur at least twice, most frequent first and ties by value. Every value
is the text [`triples`](/docs/format/reading/rdf) gives it, the natural lexical form of the column's
`type`; a value longer than 64 bytes is left out rather than cut, so `min_value` or
`max_value` is then absent, and so is a `top_values` that would hold it. A table's `candidate_keys` are
its columns of a keyable type that are never null and never repeated; `inclusions`, at the top of the
document, are `{ "from": { "table", "column" }, "to": { "table", "column" } }`, each a program's column
whose every value is a value of `to`, a candidate key or an `identity` column. They describe the corpus
as written: a corpus written from a sample of its sources counts the sample.

**`derived_from` names each source as the program wrote it** — `@crm/people.csv`, or a path relative
to the program — and never the location it resolved to, so a corpus carries no storage prefix and
repointing a connection does not change it. The list is sorted and holds each source once: a vertex
table's is every source its mappings read, through every join; an edge table's the same over the
mappings that write the relation; a property table's over the mappings that write the property.

**`term_type` and `datatype` are the shape's, verbatim.** A column whose shape declares a term
carries it as the standard IRIs: `term_type` is R2RML's `rr:IRI` or `rr:Literal`, and `datatype`
the datatype IRI the document wrote — `xsd:gYear` stays `xsd:gYear` whatever the column's `type`.
A column whose shape declares none carries neither, and its RDF meaning is
[the natural literal](/docs/format/reading/rdf) of its `type`, R2RML's default.

**`role` says what a column the writer emits IS**: `address` (`dense_id`), `identity` (`subject`),
`endpoint` (`src`, `dst`) and `language` (`lang`). They are `corpus.bnf`'s roles, and the writer reads them from there.
A column of the program's carries none, so the columns to leave out of a field listing are the ones
with a `role`. What a reader does with a role is the reader's decision. A corpus written before the
field existed carries no `role` anywhere; it is optional within `fossil/1`.

**A corpus carries no position.** It is the graph and not a picture of it: where a vertex is drawn
is the reader's choice, from two of the program's columns or from its own layout
([where x and y come from](/docs/design/position)).

## The conventions

Three things define a corpus beyond the manifest. Each is held by a guard below.

| | the convention | what it buys |
| --- | --- | --- |
| [Identity](/docs/format/conventions/identity) | `dense_id` is a gapless `0..V−1` across the whole graph, stored `uint32`, each vertex table one contiguous range of it and sorted by it; the identity is the subject IRI | one id space, so an edge's endpoints are two integers and a vertex buffer is indexed by id |
| [Adjacency](/docs/format/conventions/adjacency) | a relation is one table of `src`, `dst`, sorted by `(src, dst)` | the CSR a graph algorithm wants, read as it lies |
| Payload | plain Parquet, row groups of **122,880** rows, every page ZSTD, default statistics | an engine prunes row groups off the footer, and any Parquet reader opens the file |

The row-group size is DuckDB's own default, fixed by the writer rather than left to the Parquet
library, whose default puts a million-row table in one row group and leaves nothing to prune.

## Versions

`format` is the only version a corpus carries, and it is one string for the whole corpus: `fossil/1`.
A reader refuses any other before it reads a byte of Parquet, so a JSON file that is not a corpus is
stopped rather than misread.

**`fossil/1` is the format the reader and the writer of one release agree on.** Every reader of a
corpus is released with the writer, and a change to the format — a field, a column, a role — ships in
both at once, with no reader that knows two layouts. A field a reader does not know is ignored, so a
corpus written before a field existed reads as one that has nothing to say there. When a reader
outside that release exists, the next change that is not an addition is `fossil/2`
([the argument](/docs/design/corpus#one-format-changed-in-place)).

## Why a format and not a library

A library is a fine contract when there is one consumer and one language. This has neither: the
corpus is read from TypeScript over DuckDB-WASM, from native DuckDB, and from a notebook that knows
nothing about any of it. A shared crate fails three ways at once. It puts a compiler *and a version*
between writer and reader, which is the edge the two-core split removes. It gives a third party
nothing. And it makes one reader's idea of the manifest the manifest, where a document that
`JSON.parse` reads is everybody's.

The reference for the stance is **Iceberg, Delta Lake and Lance**: a manifest plus files, many
engines reading the same table, none of them the contract. The vocabulary is **SQL/PGQ**'s, because a
vertex table and an edge table with keys and references is what a property-graph query already
names — [the corpus](/docs/design/corpus#the-vocabulary-is-sqlpgqs-declared-and-not-executed) argues
it.

The guards below exist because of a lesson GraphAr taught. Every language's CI cloned its
shared corpus and no job wrote with one implementation and read with another; through that gap a
fourth implementation landed having re-derived the path arithmetic differently from the other three
*and* from the corpus on disk, green on both sides, because its tests asserted hand-written strings
instead of resolving against the artifact.

## The guards

```bash
node packages/corpus/guards/check.mjs /path/to/corpus
```

`node` and the `duckdb` binary. No fossil crate, no npm package, no install, no build step — copy
the `guards/` directory somewhere else and it runs, which is the position the third party this
format exists for is in. `--explain` prints what each one proves, `packages/corpus/guards/README.md` has
how each is proved to fire, and `packages/corpus/conformance/` holds a corpus that satisfies every
one of them, with the recipe that reproduces it.

The list is rendered from `packages/corpus/guards/guards.mjs` at build time, so it cannot name a guard
that does not exist, omit one that does, or paraphrase what one proves. **There is deliberately no
number in this sentence**: a count is the one part of a rendered list that stays wrong on its own.

<Callout type="warn" title="The price, stated where it is paid">
**There is no type. A guard checks what it was asked to check and nothing more.** That is the entire
difference between this and a compiler, and it is why every entry below publishes what it *cannot*
prove beside what it can. The second half is the one worth reading.
</Callout>
