description: An Apache GraphAr graph and the RML-Core mapping that says what its tables mean as RDF, written together under one location with fixed names. The artifact is the API.
---

A run answers `{ location, dropped }`. What it wrote is under `location`, and it is two things:

- **A graph**, in [Apache GraphAr](https://graphar.apache.org)'s format: YAML information files
  that describe it, and Parquet chunks that hold it — a table per vertex type and per relation,
  with the count and offset files GraphAr defines.
- **Its description as RDF**: `mapping.ttl`, an RML-Core mapping that says what the tables mean —
  which class a vertex type is, which predicate a column is, which term and datatype its values
  are.

It is read by code that was not compiled against the code that wrote it. That clause is the whole
design: a graph on disk is not a serialisation of somebody's object graph, it is the interface.
**The seam between the two halves of fossil is the files, not an API.** A reader needs a YAML
parser and a Parquet reader for the tables, and a Turtle parser for their meaning, and nothing else
of fossil's.

<Callout title="Two products, one repository">
The other half of fossil is a statically-typed language that produces a graph, taught in
[the book](/docs/book/getting-started). Nothing here requires it. The tables are GraphAr's, and the
conventions on these pages are what a fossil graph adds to GraphAr, each stated as fossil's own.
</Callout>

## Two names are fixed

A reader over HTTP cannot list a directory, so nothing is discovered by listing. The graph is named
`fossil`, so its graph document is `fossil.graph.yml`, and the mapping is `mapping.ttl` beside it.
Those are the two names known in advance. The graph document names every vertex and edge
information file, and GraphAr's own rules for paths give every count and chunk file from those.

```
<location>/
  fossil.graph.yml                          the graph document, written last: the commit
  <Type>.vertex.yml                         one per vertex type
  <Src>_<label>_<Dst>.edge.yml              one per relation
  vertex/<Type>/vertex_count                the type's row count, one int64
  vertex/<Type>/<group>/chunk0              the type's rows, one chunk
  edge/<Src>_<label>_<Dst>/ordered_by_source/
    adj_list/part0/chunk0                   the relation's (source, destination) pairs
    offset/chunk0                           where each source's edges begin
    edge_count0                             the part's row count
    vertex_count                            the source type's row count
  mapping.ttl                               what the tables mean as RDF
```

No entry points at `mapping.ttl`: the graph document carries no `extra_info`, and the two files are
written together and never move apart. The graph document carries no `prefix` either. Without one,
the data is under the directory that holds the document, which is GraphAr's default. A written
`prefix` is a path two readers would read differently: GraphAr's C++ library resolves a relative one
against the process's working directory, and `@kanzo-tech/graphar-duckdb` against the document.

**`fossil.graph.yml` is written last, and its presence is the commit.** A directory holding chunks
and no graph document is a write that did not finish, and a reader treats it as no graph at all.
GraphAr defines no commit; this is fossil's. Every other file, `mapping.ttl` among them, is on disk
before the graph document is.

`dropped` stays in the run's answer. The graph carries no account of what a run left out.

## The walking skeleton

The program in `examples/hello.fossil` reads five rows of CSV and writes five `Person` vertices.
This is the layout it has:

```
<location>/
  fossil.graph.yml
  Person.vertex.yml
  vertex/Person/vertex_count               one int64, little-endian
  vertex/Person/subject_name/chunk0        Parquet: _graphArVertexIndex, subject, name
  mapping.ttl
```

```yaml
# fossil.graph.yml
name: fossil
vertices:
  - Person.vertex.yml
version: gar/v1
```

```yaml
# Person.vertex.yml
type: Person
chunk_size: 5
prefix: vertex/Person/
property_groups:
  - prefix: subject_name/
    file_type: parquet
    properties:
      - name: subject
        data_type: string
        is_primary: true
      - name: name
        data_type: string
        is_primary: false
        is_nullable: false
version: gar/v1
```

```turtle
# mapping.ttl
@prefix rml: <http://w3id.org/rml/> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

<#Person> a rml:TriplesMap ;
  rml:logicalSource [ rml:source [ a rml:Source ] ;
                      rml:referenceFormulation rml:SQL2008Table ; rml:iterator "Person" ] ;
  rml:subjectMap [ rml:reference "subject" ; rml:termType rml:IRI ;
                   rml:class <https://example.org/Person> ] ;
  rml:predicateObjectMap [ rml:predicate <https://example.org/name> ;
                           rml:objectMap [ rml:reference "name" ; rml:datatype xsd:string ] ] .
```

Read through [`attachGraph`](/docs/format/reading/without-fossil)'s view of `Person`, the five
rows came back as `(0, https://example.org/user/1, Alice)` to `(4, https://example.org/user/5,
Eve)`: the index, the subject and the name, on DuckDB-WASM 1.4.3.

## How a program becomes a graph

| the program has | the graph has |
| --- | --- |
| a type written by a mapping | a **vertex type**: `<Type>.vertex.yml`, one property group holding every property of the type |
| the type's identity, `@subject` | the property `subject`, `is_primary: true`, first in the group |
| a single-valued property | a property of the group, with the [GraphAr type](/docs/format/conventions/datatypes) its value needs, `is_nullable` always written |
| a multi-valued property | a property of the same group with `cardinality: set`, a list in the chunk |
| a language-tagged property | a property of type `langString`, a struct of `value` and `lang` |
| a relation between two types | an **edge type** `<Src>_<label>_<Dst>`, one adjacency list, `ordered_by_source`, `directed: true`, and no property group |
| the shape's class, predicate, term and datatype | the [mapping](/docs/format/reading/rdf), and nowhere in the YAML |
| the sources a table was derived from | nowhere: the graph names no input |

The vocabulary is GraphAr's: a vertex *type* and an edge *type* with a `src_type`, an `edge_type`
and a `dst_type`. An edge type's name is `<Src>_<label>_<Dst>` because one label can join several
pairs of types. **Every table is one chunk.** Each `chunk_size` is at least the table's row count,
so the one file per table that a reader would expect is one chunk of GraphAr's; an edge type's
`src_chunk_size` and `dst_chunk_size` are the `chunk_size` of the vertex types at its ends, which
GraphAr's information model requires.

**A table is read in the order of its key**: a vertex type by its index, a relation by source and
then destination ([identity](/docs/format/conventions/identity),
[adjacency](/docs/format/conventions/adjacency)).

| | the convention | what it buys |
| --- | --- | --- |
| [Identity](/docs/format/conventions/identity) | a vertex's index is its row, `0 … count − 1` in its type; the global id is the reader's arithmetic over the types; the identity is the subject IRI | one dense id space without storing one, and an index that does not move when a type is read |
| [Adjacency](/docs/format/conventions/adjacency) | a relation is one `ordered_by_source` list of per-type indices, with its offset table | the CSR a graph algorithm wants, read as it lies |
| [Data types](/docs/format/conventions/datatypes) | GraphAr's types, `time` as a string, millisecond timestamps, `set` and `langString` | a graph every GraphAr reader opens, except where a tagged value is declared |
| [Statistics](/docs/format/conventions/statistics) | Parquet's footer statistics, and `fossil:stats` for what Parquet has no field for | an engine reads counts and bounds off the footer without a scan |
| Payload | plain Parquet, row groups of 122,880 rows, every page ZSTD | an engine prunes row groups off the footer, and any Parquet reader opens the file |

The row-group size is DuckDB's own default, fixed by the writer rather than left to the Parquet
library, whose default puts a million-row table in one row group and leaves nothing to prune.

## Whose rule it is

A fossil graph is GraphAr's, and every departure and addition is named. A claim about the tables
holds in GraphAr's words wherever GraphAr has them; the rest are fossil's, and a reader that ignores
them still reads the tables.

| | whose |
| --- | --- |
| Vertex, edge and property group documents, the chunks, the count and offset files | GraphAr's. The specification names the documents and what they contain; the paths of the chunk, count and offset files are conventions of GraphAr's code and not of its specification, and the specification names `<label>.vertex.yml` where C++'s writer writes `.vertex.yaml` |
| The internal vertex id, `_graphArVertexIndex` | GraphAr's: "starting from 0, corresponding to the row number of the vertex in the logical vertex table". The column names are in GraphAr's libraries, not its specification |
| The index being **gapless** | the specification's sentence, which GraphAr's paper does not keep; fossil's writer is gapless and its reader refuses a gap |
| The order of `vertices:` meaning anything | fossil's, and `attachGraph`'s |
| The global id | the reader's, and not stored |
| The commit: the graph document written last | fossil's |
| The names `fossil.graph.yml` and `mapping.ttl` | fossil's |
| `langString`, the struct's shape | fossil's, under the specification's user-defined types, which GraphAr's C++ and Java readers do not parse |
| `fossil:stats`: its key, its JSON Schema, its version | fossil's, in Parquet's `key_value_metadata` |
| Datatypes beyond GraphAr's, such as `xsd:gYear` over an `int32` | the mapping's, and only there |
| The seven-column `triples` relation | rudof's: its column names come from SPARQL 1.1 Results JSON, and no standard defines a triples table |
| A logical source in the mapping that names a GraphAr graph | none: the mapping's sources are SQL names the host resolves |

## Versions

**The format carries no version string of its own.** What identifies a fossil graph is the pair
`fossil.graph.yml` and `mapping.ttl` at a location: a graph document whose `name` is `fossil`, and
the mapping beside it. A directory holding GraphAr's documents under another name is a GraphAr
graph and not a fossil graph, and one holding `fossil.graph.yml` without `mapping.ttl` is a write
that did not finish. A reader opens `fossil.graph.yml` and refuses a location that has none.

The versions inside it are other people's and one of ours:

- `version: gar/v1` in every information file, which is GraphAr's, and the only one GraphAr defines.
  A graph with a tagged multi-valued property writes `gar/v1 (langString)` in the documents that use
  it, which is how GraphAr declares a user-defined type.
- `version: 1` inside the value of `fossil:stats`, which a reader of that key checks and refuses
  another ([Statistics](/docs/format/conventions/statistics)).
- the draft of RML-Core that `mapping.ttl` is written against, which is the vocabulary's namespace
  IRI, `http://w3id.org/rml/`, and no version.

A key in a document that GraphAr does not define is refused, by `graphar-info` and by
`attachGraph`, and not read past, so the writer writes none of its own. So is a `version` other
than `gar/v1`.

*Design question.* A change to a fossil convention that is not an addition — the order of the types,
the rule for the global id — has no place to say so: the graph document has no key of ours, and the
version of a fossil convention is not in any file. The first such change settles where it goes; the
candidate is `extra_info`, keyed by a namespace IRI and never by a word of fossil's.

## Why a format and not a library

A library is a fine contract when there is one consumer and one language. This has neither: the
graph is read from TypeScript over DuckDB-WASM, from native DuckDB, from Rust, and from a notebook
that knows nothing about any of it. A shared crate fails three ways at once. It puts a compiler
*and a version* between writer and reader, which is the edge the two-core split removes. It gives a
third party nothing. And it makes one reader's idea of the files the files, where a YAML document
and a Parquet file are everybody's.

The reference is **Apache GraphAr**: the
[format specification](https://graphar.apache.org/docs/specification/format) first, and where it is
silent, its C++ library and the files of its testing repository. It is the property-graph format
that a Parquet reader and a YAML parser are enough for, and the one that gives each vertex type a
table, which is what a SQL engine reads. Where fossil departs from GraphAr's libraries the page that
states the rule says so, and the departure that matters is on
[data types](/docs/format/conventions/datatypes#a-tagged-value-and-the-readers-that-refuse-it).

GraphAr is an Apache Incubator project, and its specification is shorter than its code: the paths
of the data files, the names of the index columns and the cardinality of a property are in the
libraries. The code that writes and reads a fossil graph is `graphar-info` and `graphar-parquet`
(Rust), and `@kanzo-tech/graphar-duckdb` (TypeScript), each of which names where it follows C++ and
where it follows the specification instead.
