Every relation is **one table**: `edge/<Src>_<label>_<Dst>.parquet`, whose first two columns are
`src` and `dst` — both `uint32`, both [global `dense_id`s](/docs/format/conventions/identity) — and
whose remaining columns are the relation's properties in the order the manifest lists them. The rows
are **sorted by `(src, dst)`**.

## Why the order is worth a convention

A sorted edge table is not merely convenient to scan — it **is** the CSR structure a graph algorithm
wants, offsets and values, already laid out:

```
edge/Person_knows_Person.parquet, sorted by (src, dst)     the CSR a reader already has
 row      src      dst                                      offsets[41000] = 0  first row of 41000
   0    41000     4118  ┐                                   offsets[41001] = 3  one past its last
   1    41000     8300  │ 41000, degree 3
   2    41000   912004  ┘                                   offsets[41002] = 3  41001 has no out-edges
   3    41002       77  ┐ 41002, degree 2                   offsets[41003] = 5
   4    41002    66051  ┘
   5    41003   130998  ] 41003, degree 1                   offsets[41004] = 6
                              targets = the dst column, read as it lies
```

The offsets are the run boundaries and the values are the `dst` column: no degree-counting pre-pass,
no scatter, no intermediate bag of pairs. And a file that claims the order and does not have it does
not fail — it builds a different graph, silently. **Wrong answers rather than slow ones**, which is
what makes it worth a convention. Guard: `sorted-by-key` — and every guard named on this page is
specified in full, with what it cannot prove, in [the guard index](/docs/format#the-guards).

Because `src` ascends and `dense_id` is the Hilbert rank of the position, a row group of an edge
table holds the edges out of one compact patch of the plane, and a filter on a range of `src` prunes
row groups off the footer. A range of `dst` does not: the destination order inside a run is
unrelated to the plane, so a filter on `dst` reads the table.

## One copy, one orientation

There is **no second copy sorted by `dst`**. The in-edges of a vertex are `WHERE dst = v` over the
same table, which a reader answers by scanning `dst`, or by building the CSC in memory from the
columns it already read — the same two columns with their roles swapped. A corpus that stored the
relation twice would carry it twice, and two copies of one relation can disagree about their rows
while agreeing about their counts.

**Both directions are a relation's answer.** "The papers by this author" is an in-edge from the
author, and following only `src` is a wrong answer rather than a partial one.

## Every endpoint is a vertex

Every `src` is a `dense_id` of the vertex table `source.references` names, and every `dst` one of
the table `destination.references` names. The corruption a renumbering introduces is exactly the
one where the counts match and the graph is wrong, and a count does not find it. Guard:
`no-dangling-endpoint`.

The manifest's `record_count` is the relation's row count, and a table whose rows fall short of it is
a corpus missing edges rather than a sparse graph. Guard: `declared-count`.

## What it costs to read one whole

A relation read whole is two `uint32` columns. Over a million vertices and two million edges, `src`
and `dst` are **16 MB of Arrow, read in 51–127 ms** by DuckDB-WASM in Node on one thread from a local
file; over 144,784 vertices in twelve types and 426,781 edges in fourteen relations, **3.4 MB in
24–38 ms**.
