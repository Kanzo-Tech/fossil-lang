A graph is written once and read many times, so each column is counted once, at write — not by
every reader at every open. A reader that wants nulls, bounds or distinct values of a column reads
them off the footer of the chunk, with no scan.

They are **Parquet's own `Statistics`**, in each chunk's footer, the one place a Parquet reader
already looks: per column chunk, `null_count`, `min_value` and `max_value` with
`is_min_value_exact` and `is_max_value_exact`, and `distinct_count`. Every column of every chunk
carries them — the properties and the reserved index columns, in vertex, adjacency and offset chunks
alike. A multi-valued column is counted over its **elements**, since Parquet counts leaf values.

**A chunk is one row group.** Parquet's statistics are per row group, so one row group per chunk makes
them the chunk's. A fossil graph has one chunk per table, so a chunk's counts are the table's.

**No key of fossil's is in a footer.** `key_value_metadata` holds what the Parquet writer puts there
(`ARROW:schema`) and nothing else.

**A dictionary-encoded Arrow column is written as its values.** An Arrow dictionary array's distinct
count is counted over its keys (apache/arrow-rs#11172), so the writer casts a dictionary column to its
value type before it encodes the chunk, and `distinct_count` counts values.

## What a reader may combine

A graph of several chunks, which a foreign writer may write, is read by these rules:

- **Nulls add up, and bounds fold.** `null_count` across chunks is a sum, and `min_value` and
  `max_value` a minimum and a maximum — the aggregates that distribute over a union. A bound the
  writer cut at 64 bytes is marked inexact, so a reader that keeps only exact bounds never shows a
  cut value.
- **A distinct count does not combine.** The distinct count of a union cannot be computed from the
  counts of its parts: it lies between the largest and the sum, and no more is known. Over one chunk
  it is a count; over several it is that bound, and a reader that needs the count counts again.

`@kanzo-tech/graphar-duckdb` answers these combined counts per column as `graphar_column_stats`.

## Reading them

DuckDB's own table function reads them over the chunk paths `graphar_chunks` answers, with no fossil
code:

```sql
SELECT path_in_schema, row_group_id, stats_null_count, stats_distinct_count,
       stats_min_value, stats_max_value, min_is_exact, max_is_exact
FROM parquet_metadata((SELECT list(path) FROM graphar_chunks WHERE type = 'Person' AND kind = 'vertex'));
```

**The candidate keys are not stored.** A reader derives them: the primary key, plus every column
with `null_count = 0` and `distinct_count` equal to the count whose GraphAr type can be a key
(`int32`, `int64`, `string`, `date`, `timestamp`), read from single-valued scalar columns only. A
graph carries no dependency between two columns: no reference format does.

**They describe the graph as written.** A graph written from a sample of its sources counts the
sample.
